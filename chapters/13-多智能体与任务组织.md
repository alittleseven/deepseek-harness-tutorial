# 第 13 章　多智能体与任务组织：subagent、skill、jobs、workflow

**学习目标**

1. 说出 subagent 的 provider 契约（`name` / `capabilities` / `inheritsParentContext` / `start` / `prepareContinuable?`）与六种提供方的能力差异；
2. 用 `completedTurnPrefix` 解释 fork 为何复制"父会话已完成轮次前缀"而 spawn 从零开始；
3. 复述 `tool-subagent` 的前台、后台 one-shot、continuable 三种委派模式各自的结算路径；
4. 描述 skill 的"先选候选再加载"两段式与本地根目录 rank 裁决规则；
5. 画出 `JobRegistry` 状态机，并解释 first-wins 结算与 owner 围栏的并发语义；
6. 说明 workflow 引擎的 worker_thread 隔离与"信任边界 = bash 同级"的立场。

**本章讲法**：演进/组织型——"一个 agent 不够时怎么办"：先雇人（子代理），再把会的东西写成手册（技能），把长活交给调度器（任务），最后把导演权交给脚本（工作流）。

## 13.1 一台 agent 忙不过来时

第 9 章我们认识了 agent：一个往复于"取输入 → 组装请求 → 调模型 → 执行工具"的轮次循环（见第 9 章）。它很好用，但长会话里很快会撞上四种墙：

- **上下文墙**：让同一个 agent 做"调研、写代码、跑测试、写总结"四件事，四份中间产物全堆进同一段历史，模型请求越来越贵；
- **能力墙**：某次对话里总结出的"项目构建三步法"，下次换会话就忘了；
- **时长墙**：一条 `pnpm install` 要跑十分钟，模型只能干等；
- **组织墙**：任务本身需要"拆成两路分头做，再合并"。

dsh 的答案不是把循环改大，而是**在循环之外长出四种组织形态**，各管一摊：subagent（另一个 agent）、skill（可复用的知识卡）、jobs（单个长任务的生命周期）、workflow（一段模型可写的编排脚本）。本章按"从内到外、从人到物"的顺序走一遍（表 13-1）。

**表 13-1　四种组织形态一览**

| 形态 | 解决哪堵墙 | 核心接口 | 运行位置 |
|---|---|---|---|
| subagent | 上下文墙（把活分出去） | `ctx.subagents` 提供方注册表 | 进程内（spawn/fork）与进程外（acp/codex/claude-code/dsh-sdk） |
| skill | 能力墙（把经验留下） | `ctx.skills` 分层注册表 + `SKILL.md` | 本地目录（含 bundled），模型经 `skill` 工具调用 |
| job | 时长墙（把长活挂后台） | `ctx.jobs`（`JobRegistry` 抽象 + 本地实现） | 进程内 |
| workflow | 组织墙（把编排写成脚本） | `ctx.workflowEngine`（脚本引擎 + worker_thread） | 独立 worker 线程 |

需要先钉住一个词：**注册表（registry）**。第 2 章的 Context/Service 是"一个键一个实现"（见第 2.3 节"注册与唯一性"），而本章的 subagent 注册表允许**多个按名注册的提供方同时共存**——这正对应 LLM 适配器的注册形态（见第 10 章），而不像 bash 那样只有一个执行器。dsh 官方文档把这定为 subagent 能力族的第一条设计事实（`docs/subsystems/subagent.zh.md`）。

## 13.2 子代理：provider 契约

**① 类比**：主管把一坨活交给同事。关键在"同事"是**另一个独立的工位**——有自己的工位日志（Session）、自己的工具台账（工具集）、自己的规范（系统提示词），不是在同一本笔记本上接着写。子代理（subagent）就是一个独立的子 Agent：它有自己的一份会话日志、自己的工具集合，任务完成后把**结果**交还，中间步骤不污染主管的上下文。

**② 精确定义**：子代理的"雇人方式"由提供方契约 `SubagentProvider` 统一（`packages/subagent/subagent/src/types.ts:285-323`）：

```ts
export interface SubagentProvider {
  /** Unique registry name (e.g. `spawn`, `fork`, `acp`). */
  readonly name: string
  /** The start-time features this provider supports (see {@link SubagentCapabilities}). */
  readonly capabilities: SubagentCapabilities
  /**
   * Whether the child sees the parent's completed-turn prefix. This is descriptive, not a
   * service-validated start capability: …
   */
  readonly inheritsParentContext: boolean
  start(request: ResolvedSubagentStartRequest): Promise<SubagentRun>
  prepareContinuable?(request: ContinuableCreateRequest): Promise<ContinuableCreateSpec>
}
```

四个字段四层意思：

- `name`：注册名，即 `ctx.subagents.start('fork', …)` 的第一个参数；
- `capabilities`：**启动时能力位**，四个布尔——`outputSchema`（结构化输出）、`depthLimit`（委派深度上限）、`toolFilter`（子代理工具过滤）、`persona`（子代理人格）(`packages/subagent/subagent/src/types.ts:86-91`)；
- `inheritsParentContext`：子代理是否"看见"父会话已完成轮次——**描述性标志**：服务不拿它做校验，真正消费它的是模型侧工具，用来生成诚实的说明书文字；
- `start` 与可选的 `prepareContinuable`：前一个负责一次性（one-shot）子代理，后一个只贡献"继续型（continuable）子代理的创建数据"——**方法存在即能力**（`packages/subagent/subagent/src/index.ts:433-446`）。

请求契约 `SubagentStartRequest`（`packages/subagent/subagent/src/types.ts:100-149`）的关键字段是 `prompt`（子代理收到的用户消息）、`parent`（发起方 agent，进程内提供方据它取工作目录、血缘与深度）、`signal`（**唯一取消通道**，发布前后都管）以及四个可选能力项。

**③ 最小示例**：一次代码级委派长这样（摘自服务入口 `SubagentRuntime.start`，`packages/subagent/subagent/src/index.ts:414-425`）：

```ts
async start(name: string, request: SubagentStartRequest): Promise<SubagentRun> {
  const provider = this.expectProvider(name)
  this.assertCapabilities(provider, request)          // 能力不足 → UNSUPPORTED_CAPABILITY
  assertSubagentMaxDepth(request.maxDepth)
  if (request.outputSchema !== undefined) assertObjectJsonSchema(request.outputSchema)
  const descriptor = snapshotSubagentDescriptor({     // 持久描述符（见下文）
    mode: 'one-shot', provider: name,
    ...request.label !== undefined ? { label: request.label } : {},
  })
  const resolved: ResolvedSubagentStartRequest = { ...request, descriptor }
  return observeRun(this.emitLifecycle, name, request.parent, await provider.start(resolved))
}
```

走读：服务先验"人能不能干"（`assertCapabilities`，`packages/subagent/subagent/src/index.ts:481-496`：请求要了哪个能力而提供方声明为 false，就抛 `UNSUPPORTED_CAPABILITY`——**fail loud，绝不接受"后来自行忽略"**）；再验深度与 schema；然后快照一份**持久描述符**存入请求，交给提供方。描述符是 `subagent/descriptor` 会话事件（log-only，不进模型历史、跨压缩保留），版本 `SUBAGENT_DESCRIPTOR_VERSION = 2`（`packages/subagent/subagent/src/descriptor.ts:47`），字段刻意**显式固化**（`mode/provider/label`），"决不使用可合并扩展的 `AgentOptions` 对象"（`packages/subagent/subagent/src/descriptor.ts:8-19`），这样任何无关扩展值都无法破坏后续恢复；快照用 `snapshotJsonValue` 提前脱钩（`packages/subagent/subagent/src/descriptor.ts:289`）。

注意 `start` 返回的 `SubagentRun`（`packages/subagent/subagent/src/types.ts:249-275`）里，`result` **永不 reject**：子代理失败会以 `stopReason: 'error'` 正常 resolve（`packages/subagent/subagent/src/types.ts:262-269`）。停因词表是闭集 `completed | aborted | error | max-tokens | refusal`（`packages/subagent/subagent/src/types.ts:200-211`）——"不把不干净的停止报成成功"是全程纪律。

描述符的字段取舍也值得读一眼（`packages/subagent/subagent/src/descriptor.ts:49-83`）：one-shot 带 `mode/provider/label`，continuable 再加 `agentProvider/agentModel/persona/toolFilter`；**刻意省略**两个字段——`subagentDepth`（持久 header 里的 `delegationDepth` 才是单调下限，见 13.3）与 `outputSchema`（那是一次 Activation 的结果契约，不是孩子的身份）。为什么舍？因为后者依赖前者：恢复一个子代理时，深度从持久 header 复原，schema 由当次调用提供，放进描述符反而制造两个真相源。

## 13.3 两条进程内路径：spawn 与 fork

**先分清两件事**：委托按"子代理在哪里跑"分两条路——进程内（同一个 Node 进程、共享 Cordis 上下文）与进程外（另起真实进程）。进程内又有两种活法：**spawn（新起）** 与 **fork（分叉）**，差异只有一个问题：**子代理的"记忆"从哪来？**

**spawn 的定义**：子代理从零开始，**永远看不到父会话**（`packages/subagent/subagent-spawn-in-process/src/index.ts:38-56`）：

```ts
class SpawnInProcessProvider implements SubagentProvider {
  readonly capabilities: SubagentCapabilities = { outputSchema: true, depthLimit: true, toolFilter: true, persona: true }
  // Context contract: a spawned child starts fresh — it never sees the parent conversation.
  readonly inheritsParentContext = false
  start(request: ResolvedSubagentStartRequest) {
    return startInProcessRun(request, {})   // Fresh child: no seed.
  }
  prepareContinuable(): Promise<ContinuableCreateSpec> {
    return Promise.resolve({})
  }
}
```

**fork 的定义**：子代理以"父会话**已完成轮次的平衡前缀**"为种子（seed）——这好比把会议室里已经散会的前几场纪要复印一份给新同事，手头正在开的这场不算。实现就是 `completedTurnPrefix`（`packages/subagent/subagent-fork-in-process/src/index.ts:48-57`）：

```ts
function completedTurnPrefix(parent: Agent): SessionEvent[] {
  const events = parent.session.events
  const lastEnd = events.findLast(e => e.type === 'turn/end')
  if (lastEnd === undefined) return []
  // seq === array index (the append contract), so slice up to and including it.
  return events.slice(0, lastEnd.seq + 1)
}
```

两条设计点值得停一停：

1. **为什么截止最后一个 `turn/end`**：当前在飞的轮次里可能有"模型调用工具但还没收到结果"的不平衡消息对，直接回放会造出一个非法子会话；文件头部注释明说"the current tool-call turn is unbalanced and cannot be replayed as a valid child session"（`packages/subagent/subagent-fork-in-process/src/index.ts:7-9`）。顺带一个优雅巧合：因为"seq 恒等于数组下标"（仅追加契约，见第 8 章），`slice(0, lastEnd.seq + 1)` 得到的种子天然从序号 0 连续——一份合法可回放的前缀。
2. **是复制，不是共享**：fork 把事件**拷贝**进子会话的头条，之后父子各自追加；子代理对自己的修改永不回流父会话。fork 的 `start` 因而只是 `const seed = completedTurnPrefix(request.parent); return startInProcessRun(request, { ...seed.length > 0 ? { seed } : {} })`（`:68-72`），并声明 `inheritsParentContext = true`（`:64`）。

**共享驱动 `startInProcessRun`**（`packages/subagent/subagent-in-process-driver/src/index.ts:102-163`）把两条路径余下的全部逻辑收拢为一个实现，README 的时序是：① 校验父深度与可选 `maxDepth`，子深度 = 父深度 + 1，持久化进子会话 header；② 直接调 `parent.ctx.agents.create`（把 signal 传进创建事务）；③ 在未发布的设置窗口内装好 persona / 工具限制 / 结构化输出运行时；④ 发布子 agent、拿到 `AgentHandle`，驱动 `child.followup(prompt)` + `child.whenIdle()`；⑤ 从子会话 `boundary`（seed 长度即激活边界）之后读结果——最后一条非空 assistant 消息，或结构化捕获值；停因来自完整子轮次（排除 fork seed）。**fulfill 前失败已经 quiesce 掉未发布的创建事务**（README "Start contract"），调用方绝不会拿到半个句柄。

还有一个容易漏的安全细节：**委派策略（delegated policy）**。进程内路径在委派边界固定子代理权限范围——`captureDelegatedPolicyOverrides` 快照父会话显式的 sandbox override，并且**只要审批能力被组合，就把子代理审批策略钉死为 `'never'`**（`packages/subagent/subagent/src/child-agent.ts:199-205`）；父方策略若是 ask，委派时无人看守，所以确定性拒绝而非等待。`appendDelegatedPolicyOverrides` 在未发布设置窗口内、fork seed 之后，把 `source: 'delegation'` 的 `sandbox/mode` 或 `approval/policy` 事件写进子日志（`packages/subagent/subagent/src/child-agent.ts:215-224`）——"fresh policy wins stale seed state"：种子里的旧策略永远不赢过当前委派策略。

深度是同一族机制的另一个例子：`startInProcessRun` 用 `delegationDepthOf` 读父深度（持久 header 的 `delegationDepth` 是权威，运行时的 `AgentOptions.subagentDepth` 只能加深不能降低——恢复的子代理因此保留自己的预算），父不在表里视为顶层深度 0；子深度 = 父深度 + 1 写进子 header，**随持久化存活**（`packages/subagent/subagent-in-process-driver/README.md` "Depth enforcement"）。这就是"一家三代"的账本：顶层 0、第一层子代理 1、层层下派，谁也别想靠"换个上下文"绕过递归预算。

## 13.4 进程外：把活外包给别的产品

进程内路径的前提是"子代理也在 dsh 里"。进程外路径则把活交给**真实的外面进程**：ACP 协议代理、Codex、Claude Code、以及完整 dsh 运行时。四个提供方共享一条纪律（表 13-2）：**能力位全 false、`inheritsParentContext = false`**——进程外的孩子无法兑现结构化输出/深度上限/工具过滤/人格（服务在 `start` 前就按能力位拒绝），父会话也不会跨进程边界传播，唯一继承的是工作目录（cwd）与血缘行号。CP 不能验证。

**表 13-2　六个内置提供方对照**

| provider 名 | 实现 | 子代理是什么 | 能力位 | 继承父上下文 |
|---|---|---|---|---|
| `spawn` | `subagent-spawn-in-process` | 同进程新子 Agent | 全 true | 否 |
| `fork` | `subagent-fork-in-process` | 同进程子 Agent + 父已完成轮次前缀 | 全 true | **是** |
| `acp` | `subagent-acp` | 任意 ACP 协议 Agent（子进程 RPC） | `NO_START_CAPABILITIES` | 否 |
| `codex` | `subagent-codex` | 真 `codex app-server --stdio` 子进程 | 同上 | 否 |
| `claude-code` | `subagent-claude-code` | 官方 Claude Agent SDK 驱动的真实 CLI | 同上 | 否 |
| `dsh-sdk` | `subagent-dsh-sdk` | 完整 dsh 运行时子进程（stdio JSON-RPC） | 同上 | 否 |

进程外各家的差异只在"怎么起、怎么停、怎么读答案"：

- **ACP**：`spawn({ command, args, cwd, env, permission })` 起子进程，经 ACP SDK RPC 完成初始化 + 建会话后才 fulfill；`start` 被拒绝时会先清理部分资源（`subagent-acp/src/run.ts`）；能力声明在 `packages/subagent/subagent-acp/src/index.ts:143-149`。
- **Codex**：每次 accepted run 起一个全新 `codex app-server --stdio` 进程，发布前必须已有 ephemeral thread（`packages/subagent/subagent-codex/src/index.ts:47-50`）。
- **Claude Code**：经官方 `@anthropic-ai/claude-agent-sdk` 驱动真实 CLI，SDK 拉起的进程纳入共享 subprocess owner，随宿主进程树一起治理（`packages/subagent/subagent-claude-code/src/index.ts:53-55`）。
- **dsh-sdk**：子代理是**完整的 peer harness 运行时**——自己的 `cordis.yml` 组合、会话持久化、模型路由与工具（`packages/subagent/subagent-dsh-sdk/README.md`）。`start` 完成 `initialize` 握手（配置的 provider/model 路由 + 可选 `maxTokens`）才算数；run id 在父命名空间铸造，子运行时自己的会话 id 只存在于子进程内。`dispose()` 走有界协议阶梯：`shutdown` 请求 → stdin EOF → SIGTERM → SIGKILL（README "Start and ownership"）。停因映射也严格：`completed→completed`、`max-tokens→max-tokens`、`aborted→aborted`，**其余一律 `error`**——"an unclean stop is never reported as success"。

一句话总结演进逻辑：进程内提供方"天生就知道一切"（能重载深度、能限制工具、能钉人格），进程外提供方"只递一句话"，所以能力位全 false。委派请求带能力项时，dsh 宁可当场拒绝，也不假装能办到。

## 13.5 模型如何发起委派：tool-subagent 三模式

前面的 `start()` 是服务级 API，模型并不直接调它——模型调的是注册在 `ctx.tools` 上的 **`subagent` 工具**（`tool-subagent`）。它注入 `['tools', 'subagents', 'systemPrompt']`（`packages/subagent/tool-subagent/src/index.ts:23`），配置要点有三个：`provider`（委派到哪个提供方）、`backgroundMode: 'one-shot' | 'continuable'`（默认 `one-shot`，`:85`）、`maxDepth`（默认 3，`:98`；也可设为 `'provider-managed'` 把递归预算交给出进程提供方）。

**先讲清"措辞"这个细节**（这也解释了 `inheritsParentContext` 为什么是描述性的）：工具描述随提供方标志动态生成（`providerWording`，`packages/subagent/tool-subagent/src/index.ts:211-236`）——fork 的说明是"它已看见本会话全部已完成轮次，只需补充新内容"；spawn 的说明是"它看不到本会话，请给完整自包含 prompt"。这份措辞是**给模型的说明书**，不是可校验的能力声明——但它必须诚实：如果给 fork 写"它看不到本对话"，模型就会把上下文复述一遍，白白烧掉父上下文。

三模式的分叉点在 `execute` 内部的 `resolveDelegationRun`（`packages/subagent/tool-subagent/src/index.ts:247-265`，三模式分叉实现见同文件 :387-432）：

1. **前台（frontground）**：默认。`await ctx.subagents.start(...)` 发布后，走 `settleForegroundRun`（`packages/subagent/tool-subagent/src/index.ts:167-197`）：先等 `run.result`，再 `run.dispose()`；两路都可能失败，用 `AggregateError` 合并，绝不让 dispose 的失败顶掉结果失败。子代理的**部分输出**在失败时仍会带回父会话（错误文案附上 partial text）。
2. **后台 one-shot**：`run_in_background: true` 且 `backgroundMode: 'one-shot'`。子代理不再挡在工具调用里，而是作为**一个 job** 投进 `ctx.jobs.start({ kind: 'subagent', owner: parent, run: … })`（`:400-422`）——把"一个命名的长任务"交给 jobs 管理（见 13.7），模型拿到 `{ kind: 'background', jobId }` 立即返回，用 `job_output` / `job_kill` 跟踪。
3. **continuable**：`backgroundMode: 'continuable'`。走 `ctx.subagents.startContinuable(...)`（`:392-398`），在 inbox 被接受时即返回 `{ kind: 'continuable', subagentId }`——孩子从此拥有自己的轮次，父方既不等待也不收集结果；后续靠 `send_message` / `interrupt_agent` / `list_agents`（`tool-subagent-control`）与子侧 `report` 工具（`tool-subagent-report`）对话。

一句话区分后两种：后台 one-shot 是"托管一个一次性任务"，continuable 是"领养一个可持续对话的子代理"。何时用后台、何时用 continuation 的判据（推断自两个 README 的定位差异）：只需一次结果 → one-shot；需要多轮往返/上下文延续 → continuable。

## 13.6 技能：把"会的东西"固化成 SKILL.md

**① 类比**：技能（skill）是给模型的"操作手册卡片"——卡片放在抽屉里（目录），卡片封面上写着名字和一句话简介（frontmatter），模型想看某张卡片就抽出来读正文。它是**可选指令，不是会话事件**：技能正文不写进会话日志、不参与"模型可见即已记录"的一致性约束，所以它的词汇表的家不在 core.md 而在 `docs/subsystems/skills.md`（文首明言 "Skills are optional instructions, not session events"）。

**② 精确定义**：`ctx.skills` 是一个**分层注册表**（`SkillRegistry`，`packages/skill/skill/src/index.ts:357`）：注册表按 scope 分层（宿主层 / preset 层 / 会话层），读取时合并全局层与观察者 scope 链，"最近层条目直接赢得重名"，**rank 只在单层内裁决**（`docs/subsystems/skills.md` "Layered registry"，`skill/src/index.ts` Service 类一节）。提供方接口是两段式的：

```ts
interface SkillProvider {
  readonly name: string
  readonly list: (options: SkillLookupOptions) => Promise<readonly SkillCandidate[] | SkillProviderObservation>
  readonly get: (candidate: SkillCandidate, options: SkillLookupOptions) => Promise<SkillDefinition | undefined>
}
```

"**先选候选再加载**"：`list()` 只交出候选（`SkillSummary`：名字、描写等调用无关字段），`get()` 才读全文且**从不缓存**（`packages/skill/skill/src/index.ts:501` 注释 "get 不缓存完整定义、每次重调胜出提供方"）——skiff 目录改了，模型下次抽卡立刻可见。`snapshot()` 返回 `{ skills, complete }`：只有全部提供方在无并发目录修订下完成发现，`complete` 才为 true，**不完整快照不缓存**（`:482`）。远端/异步初始化属于提供方 `list()` 的 await 阶段，注册本身是同步的。

**③ 最小示例**：本地发现的核心是"有哪些根目录、各带什么 rank"（`packages/skill/skill-filesystem/src/index.ts:241-261`）：

```ts
private async roots(cwd: string | undefined): Promise<SkillRoot[]> {
  const roots: SkillRoot[] = []
  if (this.includeDefaultRoots && cwd !== undefined) {
    const projectRoot = await findProjectRoot(resolve(cwd), optionalFileSystem(this.ctx))
    roots.push(
      { path: join(projectRoot, '.dsh/skills'), source: 'project-dsh', rank: PROJECT_DSH_RANK, projectRoot },
      { path: join(projectRoot, '.agents/skills'), source: 'project-agents', rank: PROJECT_AGENTS_RANK, projectRoot },
    )
  }
  roots.push(...this.customSkillDirs.map(path => ({ path, source: 'custom' as const, rank: CUSTOM_RANK })))
  if (this.includeDefaultRoots) {
    roots.push(
      { path: join(this.dshHome, 'skills'), source: 'user-dsh', rank: USER_DSH_RANK, skipSystem: true },
      { path: join(this.agentsHome, 'skills'), source: 'user-agents', rank: USER_AGENTS_RANK },
    )
  }
  if (this.bundledSkillDir !== undefined) {
    roots.push({ path: this.bundledSkillDir, source: 'bundled', rank: BUNDLED_SKILL_RANK, trustedHost: true })
  }
  return roots
}
```

rank 常量是 `100/200/300/400/500`（`PROJECT_DSH_RANK` 到 `USER_AGENTS_RANK`，`packages/skill/skill-filesystem/src/index.ts:36-40`），随包徽章（skill-badge）用 `BUNDLED_SKILL_RANK = 600`（`packages/skill/skill/src/index.ts:27`）。**数字越小离项目越近、优先级越高**；顺带一提 `findProjectRoot` 经 `ctx.fs` 向上找 `.git`，远程/沙箱工作区不会回退到宿主边界以外（`packages/skill/skill-filesystem/src/index.ts:937-947`）——这是"就近原则"与"不越界"的结合。

SKILL.md 的约定（`skill-filesystem`）：

- 两种形态：目录包 `<name>/SKILL.md`，或平铺 `<name>.md`；判断标准就是次路径是否为 `SKILL.md`（`segments[1] === 'SKILL.md'`，`packages/skill/skill-filesystem/src/index.ts:672` 与 `:683`）；
- 名字必须 kebab-case：`^[a-z0-9]+(?:-[a-z0-9]+)*$`（`packages/skill/skill/src/index.ts:20`）；
- frontmatter 必须含 `name`/`description`，缺失或非法 YAML 的整体被忽略并记 warn（`packages/skill/skill-filesystem/src/index.ts:803-813`）；
- 模型调用控制字段是 kebab-case：`disable-model-invocation` / `user-invocable`（`packages/skill/skill-filesystem/src/index.ts:996-997`），驼峰旧键直接拒绝（`packages/skill/skill-filesystem/src/index.ts:993-995`）——只给模型看的卡片可以在目录里但不在工具列表里出现。

模型侧（`tool-skill`）做了两件事：`skill` 工具本身（经 `isModelInvocable` 把关，`packages/skill/tool-skill/src/index.ts:138/:145`），以及**目录注入**：首个 `agent/pre-step`（`:177`）把排序后的 `name` 与 XML 转义 `description` 注入为持久的 `<system-reminder>` 用户消息——**没有正文、没有路径、没有来源**（条目只含名字与简介，`:226-235`）；且每次 pre-step 对目录条目算 digest，**变了才追加整目录替换**，没变不烧 token（`:328-334`）。目录的 `catalogDescriptionMaxLength` 默认 500（`:68`）。用户侧还支持在输入里显式调用（`user-invocable`），由另一个 pre-step 监听器在 `next()` 之后按 `invokedSkillNames` 注入正文（`:177-213` 一带，来源 `skill-invocation`）。

## 13.7 任务：jobs 的状态机与 owner 围栏

**① 类比**：job（作业）像厨房里的"订单号"：后厨（生产者）干重活，前台（运行时）只挂一块状态牌（正在做/停止中/完成/取消/失败），客人（模型）凭号查看或催单。干活的资源归生产者，身份与状态归运行时——这是 jobs 的核心分工。

**② 精确定义**：`JobRegistry` 是**抽象服务**（`packages/jobs/jobs/src/index.ts:62`），契约是 `start / get / list / read / kill / wait / onJobDone / onJobsChanged / attachController`。状态机是一个五值闭集（`packages/jobs/jobs/src/types.ts:17`）：

```ts
export type JobStatus = 'running' | 'stopping' | 'completed' | 'killed' | 'failed'
```

kind 由**声明合并**扩展（`packages/subagent/subagent/src/types.ts:23-26`）：内置 `bash` 与 `subagent` 两个 kind，插件可以往 `JobKindMap` 合并自己的种类。生产者契约 `JobStart`（`packages/subagent/subagent/src/types.ts:46-91`）：`kind`（id 前缀）、`label`、`owner?`、`run()` 返回 `JobHooks`——`cancel(reason)`（同步、幂等、最终结算 `done`）、`done: Promise<JobOutcome>`（**资源释放后** resolve，**不得 reject**）、`readOutput?()`（缺省 = 只有最终输出；每个 job 一个消费游标）。

**③ 最小示例**：`tool-subagent` 的后台分支恰好是一个标准用例（`packages/subagent/tool-subagent/src/index.ts:401-422`）：

```ts
const id = jobs.start({
  kind: 'subagent',
  label: args.description,
  owner: parent,
  run: () => {
    const controller = new AbortController()
    const start = ctx.subagents.start(config.provider, { ...request, signal: controller.signal })
    return {
      cancel: (reason?: string) => { controller.abort(reason ?? 'background subagent task killed') },
      done: settleStart(start, controller.signal),
      // No readOutput: the child session owns intermediate detail.
    }
  },
})
return { kind: 'background' as const, jobId: id }
```

**状态机如何转**（`jobs-local` 实现，README "Lifecycle"）：`start()` 预检通过后调 `run()` 一次（**抛错则什么都不注册**），然后提交 `status: 'running'`（`packages/jobs/jobs-local/src/index.ts:165`）。预检有两道门：owner 的 job controller 必须已挂载（否则 "background jobs unavailable: no job controller serves this agent…"，`:133`）；并发上限 `maxConcurrentJobsPerOwner`（默认 10）——超了直接拒绝并提示 `job_kill` 或等待（`:144-146`）。任何前置拒绝**不会留下 job id**。`kill()` 先调生产者 `cancel(reason)`（**抛错则任务继续运行、状态不变**），成功后置 `stopping` 并标记 reported（`:223-224`）。

**结算 = first-wins**（`packages/jobs/jobs-local/src/index.ts:416-450`）：第一个到达的终态（生产者结算 / `done` reject 转 `failed` / teardown 强制失败）只记录一次状态、释放等待者、通知监听器一次；之后迟到的生产者结果被 `if (isTerminal(job.status)) return` 直接丢弃。设计理由写死在注释里：teardown 的强制失败必须赢过迟到的生产者结算。**完成通知是结算的最后一步**（"completion is the last thing a settlement announces"）——因为收到通知的监听器可能同步开一个模型轮次，必须让所有其他观察者先看到已提交的状态。

**owner 围栏的并发语义**：所有访问按 owner（`SessionId`）围栏（`packages/jobs/jobs/src/index.ts:47-48`）。id 是**可预测**的（`bash-1`、`subagent-2`），所以文档明言"It is authorization — not secrecy — is the boundary"——围栏防的是"他人的账本"，不是"猜出 id"。owner 是活的 Agent 实例，其销毁会取消它名下的作业并等待 quiescence；**作业属于 owner+backend，不属于生产者 tool fiber**——生产者/控制器热重载不会停止已登记的作业（README）。模型面（`tool-jobs`）提供 `job_output`/`job_list`/`job_kill` 三个工具（`:303/:343/:363`），完成通知以 `background job <id> (<kind>: <label>) finished [status: …]` 形式投递；投递分两路——忙的 owner 注入 inbox（多个作业一起结算只花一步），空闲 owner 用唤醒 turn；`completionDelivery: 'quiet'|'wakeup'`（默认 wakeup，`:51`），`maxConsecutiveWakes` 默认 3（`:52`），加这个预算正是为了防"唤醒轮次又起后台作业、其完成又唤醒"的自激链。

## 13.8 编排：workflow 引擎与信任边界

**① 类比**：workflow 是给模型的一张"导演台本"：写一段脚本，脚本里写"第 1 幕：并行派 3 个 agent 调研；第 2 幕：把结果交一个 agent 汇总"。引擎就是那个按台本喊"开拍"的人，而每场戏（每个 agent 调用）仍由 13.2 的提供方契约承接。

**② 精确定义**：`WorkflowEngine` 是抽象服务（`packages/workflow/workflow/src/index.ts:157`），常驻键 `ctx.workflowEngine`；启动请求（`workflow/src/types.ts` 邻接 `runtime-types.ts`）为：

```ts
interface WorkflowStartRequest {
  script: string
  meta: WorkflowMeta          // name/description 必填，whenToUse?/phases?
  args?: unknown
  subagentProvider?: string   // 只由调用方指定，脚本不可见不可改
  maxTotalAgents?: number
  parent: Agent               // 脚本启动的每个子 agent 归属它
  signal?: AbortSignal
}
```

`WorkflowStopReason = 'completed' | 'cancelled' | 'error'`（闭合联合，`packages/subagent/subagent/src/types.ts:63`）；`WorkflowResult` 里 `value` 仅 completed 时有意义（`:72-87`）。错误码是机器可路由的闭集（`SCRIPT_PARSE/META_INVALID/INVALID_ARGUMENT/UNSUPPORTED_OPTION/UNSUPPORTED_SCHEMA/AGENT_CAP/ITEM_CAP/AGENT_START/AGENT_RESULT/RESULT_UNSERIALIZABLE/CANCELLED`，`:108-119`），且每个 `WorkflowError` 都带 `fatal` 标志：**fatal 错误必定逃逸 `parallel()`/`pipeline()`**（脚本的拼写错误或资源上限必须响亮地杀死整个脚本），普通子代理失败只把该项解析为 `null`（`:121-139`）；`isFatalWorkflowError` 用宿主 `instanceof` 判定，脚本 realm 伪造不了（`:146-148`）。

**③ 引擎机制**：每个 run 一个 **worker_thread**（`new Worker(entry, options)` 在 `packages/workflow/workflow-worker-thread/src/host.ts:149`）。`start()` 会**同步拒绝**坏 meta、不可解析脚本、不可用 provider 路由、超限的 per-run 限制，然后才建 worker 或发布 `workflow/start`（README "Run sequence"）——错误在开工之前响。`worker.terminate()` 是真正的终止手段（`packages/workflow/workflow-worker-thread/src/host.ts:200/:244`）。脚本面 hooks 五个：`agent(prompt, {label, phase, schema, provider, model})`（`packages/workflow/workflow-worker-thread/src/runtime.ts:249`；选项走白名单 `SUPPORTED_AGENT_OPTIONS`，`:39`，`effort/isolation/agentType` 被标 deferred 直接拒绝，`:369-371`）、`parallel(thunks)`（`:400`）、`pipeline(items, ...stages)`（`:427`，**无跨阶段屏障**）、`phase(title)`（`:469`）、`log(message)`（`:479`）。

**信任边界**——这是本章最重要的立场。引擎 README 在 "Trust and isolation boundary" 一节的原文：

> Workflow scripts are model-written and have the same trust premise as the model's existing bash access. `node:vm` inside a worker is an API-shaping mechanism, not a security boundary: an escaped script can recover Node capabilities with the host process's privileges.

翻译成人话：**脚本不是沙箱的边界，模型已有的 bash 级信任假设才是**。worker/vm 只提供三样东西：CPU 同步自旋与宿主事件循环的隔离（脚本死循环卡不死宿主）、terminate 兜底、空环境（无 `process.env` 凭据）与结构化克隆 + JSON 边界。这也解释了为何 `tool-workflow` 把它当普通工具用：系统提示段只在用户显式要求 workflow/大型编排时才出现，一两次委派建议用普通 subagent（README "system prompt"）。**与第 12 章的 seam 精神完全一致**：能力可以换、边界靠策略（见第 12 章）——workflow 引擎是"能力接缝"，不是"安全围栏"。

**jobs vs workflow 的判据**（README 与 `tool-subagent` 的交叉印证）：**一个**可命名的长任务 → jobs（生命周期管理）；**一组**带编排逻辑的任务 → workflow（脚本 fan-out）。交叠处恰好各取所长：`tool-subagent` 的 one-shot 后台分支把**单个**子代理放进 jobs；`tool-workflow`/`tool-ralph` 把**一批**子代理放进 workflow。`tool-ralph` 是固定前台工作流（`maxRounds` 默认 256、每轮一个全新子代理、只给不可变目标 + 上一轮结构化 handoff，`subagentProvider` 默认 `spawn`，README），是不需要模型写脚本的"表演性"编排。

## 本章小结

1. 子代理 = 独立子 Agent（自己的会话/工具/提示词），由 **provider 契约**（`packages/subagent/subagent/src/types.ts:285-323`）统一；能力位四布尔，**服务端 fail-loud** 检查，`result` 永不 reject。
2. 进程内二选一看"记忆从哪来"：spawn 零上下文；fork 以 `completedTurnPrefix`（截止最后 `turn/end`）**复制**父会话事件（`packages/subagent/subagent-fork-in-process/src/index.ts:48-72`）。委派边界还会把子代理审批钉成 `'never'`（`packages/subagent/subagent/src/child-agent.ts:199-224`）。
3. 进程外（acp/codex/claude-code/dsh-sdk）一律无能力位、无父上下文，dsh-sdk 例外地提供"完整 peer harness"。
4. `tool-subagent` 三模式：前台（result+dispose 双路失败合并）、后台 one-shot（进 jobs）、continuable（进 ContinuationManager，返回 `subagentId`）。
5. 技能 = 可选指令而非会话事件；两段式 list/get、rank 100→600 就近优先、`<available_skills>` 目录 digest 变更才重注入。
6. jobs 管生命周期（状态机五值、first-wins 结算、owner 围栏"授权而非保密"）；workflow 管编排（worker_thread 隔离、fatal 错误逃逸组合器、信任边界 = bash 同级）。

## 分层练习

**理解**：1. 对照表 13-2，说明为什么 `subagent-acp` 的 `capabilities` 全是 false，而 `spawn` 全 true——并指出服务端的拒绝时机（`packages/subagent/subagent/src/index.ts:481-496`）。2. 复述 `completedTurnPrefix` 为什么在最后一个 `turn/end` 截断（`packages/subagent/subagent-fork-in-process/src/index.ts:7-9, 48-57`）。

**应用**：3. 配置 `tool-subagent` 让"后台子代理"走 fork 提供方，说明此时模型看到的工具描述措辞会变成哪一句（`packages/subagent/tool-subagent/src/index.ts:211-236`）。4. 写一个 10 行的 SKILL.md 骨架（含 kebab-case 名字、frontmatter、`disable-model-invocation` 键），说明它会出现在 `<available_skills>` 目录里但不出现在 `skill` 工具调用结果里（`packages/skill/skill-filesystem/src/index.ts:996-997`）。

**综合**：5. 设计一个"主 agent 并行派 2 个子 agent 分头调研、再派 1 个汇总"的编排：分别写出用 workflow 脚本（agent/parallel）与用"前台 subagent ×2 + 后台 one-shot ×1"两套方案，从取消语义、错误传播（fatal vs null）、上下文成本三方面对比优劣。

**挑战**：6. 阅读 `packages/jobs/jobs-local/src/index.ts:416-450` 的 `settle`，论证"完成通知最后发布"为什么必须如此（提示：监听器可能同步开模型轮次）。
