## 15.1 全景：一张数据资产盘点表

### 15.1.1 一切都挂在 `$DSH_HOME` 上

先回答"放哪"的总开关。`packages/util/home-paths/src/index.ts:87-91` 的 `resolveDshHome` 按优先顺序决定 Harness 的数据根目录：显式配置 > 环境变量 `$DSH_HOME` > 默认值 `~/.dsh`（目录名常量 `.dsh`，`:12`；默认值实现在 `defaultDshHome`，`:61-63`）。`dshHomePath(...)`（`:98-100`）是唯一的拼路径入口——它先 `resolveDshHome()` 再往下拼段——因此**任何数据目录都必须经过它**，这保证了同一进程内所有组件对一个"家"的认知一致。`dshHomeDisplay`（`:110-112`）负责把绝对路径显示回 `~/.dsh` 或 `$DSH_HOME` 的友好形式。

### 15.1.2 数据资产盘点表

| 数据 | 格式 | 位置（默认组合） | 生命周期 / 写入者 |
|---|---|---|---|
| 会话事件日志 | 每行一个事件的 JSON 行文档，zstd 压缩（`.jsonl.zstd`） | `$DSH_HOME/sessions/<项目键>/<会话ID>/session.jsonl.zstd` | 与会话同生共死；append-only |
| 会话属性库（SQLite 后端） | SQLite 单文件（3 张 STRICT 表） | 配置 `path`（如 `$DSH_HOME/sessions.db`）；`:memory:` 表示不落盘 | 同上 |
| 投影检查点 | JSON（storage-json 每域一个文件） | `$DSH_HOME/storages/session_projcache.json` | 随投影单元注册/失效，可旧不可错 |
| workspace 注册表 | JSON | `$DSH_HOME/storages/workspace.json` | 长期；`WorkspaceRegistry` 维护 |
| 消息反馈（message feedback） | JSON | `$DSH_HOME/storages/` 下对应域文件 | 长期 |
| settings 用户设置 | YAML（或 JSON） | `$DSH_HOME/settings.yaml` | 长期；热重载（watch） |
| credentials 凭据 | YAML | `$DSH_HOME/.credentials.yaml`（0600 私有文件） | 长期；托管存储，不物化进环境 |
| 附件对象 | 二进制（图片等） | `$DSH_HOME/attachments/v1/objects/xx/<sha256>` | 随消息引用；回收机制（未验证） |
| spill 溢写文件 | 文本/binary | OS 临时目录下 0700 私有目录（或配置 `root`） | 进程级临时 |
| 匿名用户 ID | 单行 UUID 文本 | `$DSH_HOME/.anonymous-user-id` | 长期；首次启动 `wx` 独占创建 |

表中"默认组合"来自产品组合包：`packages/bundle/base/cordis.patch.yml:97-101` 给 `session-persistence-jsonl` 配置了 `root: !!js dshHomePath('sessions')`（即 `$DSH_HOME/sessions`）；`packages/bundle/web-app/cordis.patch.yml:55-58` 给 `storage-json` 配置了 `root: !!js dshHomePath('storages')`。这两行 patch 就是"数据放在哪"的最终裁决——**组合包配置即数据布局**，这也是后续每节"怎么迁移"的答案起点。

### 15.1.3 只有两样东西值得被"带走"

会话日志是唯一可整体迁移的资产：jsonl 后端下它就是**一个会话一个目录**，拷贝即迁移；SQLite 后端下就是一个 `.db` 文件。其余（settings、credentials、附件、注册表）都是机器/用户的本地事实，迁移 = 手动拷贝同名文件。`SessionPersistence.locate`（`packages/session/session-persistence/src/index.ts:96`）给出"这份会话数据在哪个后端本地文件"的权威答案，`supportsRawArtifacts`（`:102`）声明后端是否暴露逐会话的原始产物——jsonl 为 `true`（`packages/session/session-persistence-jsonl/src/index.ts:122`），SQLite 为 `false`（`packages/session/session-persistence-sqlite/src/index.ts:100`）。这一对开关直接决定了导出、备份工具能拿到的"原始物"粒度。

## 15.2 接缝与协调器：三层职责

### 15.2.1 接缝：新概念三步讲

**① 类比**：给一栋楼装水管。楼内住户（组件）只认水龙头接口（抽象类的服务面）；真正的水源（文件系统、SQLite）可以换，但换的时候不能砸墙——接口不变，协调器就是那个"换水源时负责停水、放水、试压"的物业。

**② 精确定义**：**接缝（seam）**是源码中"不改变调用方即可替换实现"的边界——一个抽象类型加一个稳定的构造/发现机制。本节的接缝是 `SessionPersistence` 抽象类（`packages/session/session-persistence/src/index.ts:84`，`extends Service`，即 Cordis 服务）：调用方永远只持有这个类型。

**③ 最小示例**（调用方视角——只调接口，不关心后端）：

```ts
const persistence = ctx.get('sessionPersistence') // 类型：SessionPersistence
await persistence.create(header)                  // 注册会话（可延迟物化）
await persistence.append(id, events)              // 落一批事件（保证 seq 连续）
const prepared = await persistence.prepare(id)    // 准备恢复用 Session（两阶段）
const inspection = await persistence.load(id)     // 载入只读视图并完成冷修复
const location = persistence.locate(header)       // 物理位置（SQLite 后端为 undefined）
```

### 15.2.2 抽象类：声明什么、默认什么

`SessionPersistence` 把能力切成三组（`session-persistence/src/index.ts`）：

- **读**：`locate`（`packages/session/session-persistence/src/index.ts:96`）、`readFrom`（`:220`，按 seq 读后缀，供增量获取）、`list`（`:228`，全部会话头）、`listSnapshots`（`:240`）、`readRaw`（默认实现 `:103-121` 直接拒绝——"未声明原始产物的后端不可读原文"）；
- **写**：`create`（`:133`，注释明确"后端可以延迟物理写入直到首次 append"——这解释了为什么**创建过但从未有事件的会话在 `list` 里可能缺席**）、`append`（`:143`，强制"首个事件的 seq 必须等于存储中的下一个 seq"）；
- **准备/载入**：`prepare`（默认实现 `:155-168`）与 `load`（`:183`）、`inspect`（`:200`）。

`prepare` 的默认实现值得走读（`packages/session/session-persistence/src/index.ts:155-168`）：它调用 `this.load(id)` 拿到"平衡后的只读事件列表"，随后 `structuredClone` 出种子，交给 `SessionStore.prepare(id, { seed, meta, seedSource: 'persistence' })`——这个 `seedSource: 'persistence'` 触发第 8 章的 `Session.fromRestore`（`packages/core/session/src/index.ts:495`、`SessionStore.prepare` 的 `:872-873`）：**恢复出来的 Session 不是"新造"的，而是从持久化种子再生**，元数据与事件被冻结原地，所有权移交。一句话：`prepare` = 读磁盘 + 造一个未发布的内存 Session 占位。

### 15.2.3 后端契约：`PersistenceBackend`

协调器不直接碰任何存储介质。它要求后端实现 `PersistenceBackend` 接口（`packages/session/session-persistence/src/coordinator.ts:127`），关键方法有：`appendBatch(meta, events, isMaterialized)`（整批落盘）、`commitRepair(meta, tornMarker, closers)`（把崩溃修复写回）、`loadStoredFrom(id, fromSeq)`（读后缀，钩子 `:109` 注释）、`readStoredRevision(id)`（读当前修订号）。**协调器会写穿全部数据，但"怎么写"完全由后端决定**——jsonl 后端写成行追加，SQLite 后端写成单事务。

### 15.2.4 协调器：`PersistenceCoordinator` 的五个语义

`PersistenceCoordinator`（`packages/session/session-persistence/src/coordinator.ts:588`）是真实服务实现：`JsonlSessionPersistence` 与 `SqliteSessionPersistence` 都把它作为内部字段组合（`packages/session/session-persistence-jsonl/src/index.ts:145,160`），并把 `create/append/prepare/load/inspect/readFrom` 逐方法转发（`:177-199`）。它的构造即"接线"：`installWritePath`（`packages/session/session-persistence/src/coordinator.ts:1086-1137`）订阅 `session/created`（`:1118`，认领新会话）、`session/event`（`:1123-1126`，事件入队写穿）、`session/flush`（`:1129`，冲刷）、`session/disposed`（`:1132`，退役），并对已存活的会话补种（`:1136`，覆盖 HMR 场景）。**这正是它与第 8 章 SessionStore 的关系：SessionStore 是事件生产者与总闸，协调器是其订阅者**。

五个操作语义（全部以会话为粒度的串行链 `serialize(id, …)` 执行，防止同一会话的并发写交错）：

| 操作 | 位置 | 语义 |
|---|---|---|
| `create` | `packages/session/session-persistence/src/coordinator.ts:633-658` | 快照元数据；`createCore` 双保险：内存已有 or 磁盘已有（`loadStored` 探测，`:653`）都拒绝——"会话 ID 即身份"，绝不复用；**纯惰性**：只登记意图，首次 append 才物化（`:657`） |
| `append` | `packages/session/session-persistence/src/coordinator.ts:669-710` | 整批先做无损 JSON 快照（`:671-678`，保证"校验的值=持久化的值"）；`appendCore` 里 `assertSupportedEvents`（`:684`）、**seq 连续性检查**（`event.seq !== state.cursor + i` 即拒绝，`:698-702`）、`appendBatch`（`:704`）、成功后推进 cursor（`:707-708`）——"落盘成功=cursor 前进"是跨后端统一的事务边界 |
| `prepare` | `packages/session/session-persistence/src/coordinator.ts:720-747` | 等待退役、检查会话非 live、`reserve` 一个"准备位"；完成后包装成 `SessionPreparation`，交出 `release` 闭包 |
| `load` | `packages/session/session-persistence/src/coordinator.ts:756-775` | 会话若 live 直接返回其快照（`loadLiveSnapshot`，`:760`）；否则 `reserve→prepareCore→commitPrepared→discard` 循环，直到拿到与磁盘修订一致的视图 |
| `commitPrepared` | `packages/session/session-persistence/src/coordinator.ts:934-963` | 见下 |

### 15.2.5 prepare/commitPrepared 为什么是两阶段

**① 类比**：去银行取大额现金。第一阶段"预约+复核"（冻结金额、核对存折），第二阶段"签字交付"（确认存折没被改动，才把现金递出来）。之间如果存折变了，预约作废重来。

**② 精确定义**：`prepare`（读与修复阶段）把磁盘上的日志读出来、**修复 torn tail、执行只读修复**，产出 `PreparedSessionSource`——一个"未经发布"的内存视图；`commitPrepared`（提交阶段）把该视图**与当前磁盘修订核对一致后**，才登记进 `states`（成为可被 append 接续的状态），或有需要时把修复写回磁盘。

**③ 为什么必须分两阶段**——走读 `commitPrepared`（`packages/session/session-persistence/src/coordinator.ts:934-963`）与 `isPreparedSourceCurrent`（`:966-971`）即可回答：

- 修复写回是"值造"操作。若在 `prepare` 里顺手写回，读一半崩溃会把"半修复"留下；推迟到提交阶段与状态登记原子完成，崩溃后重来只是重新 prepare。
- **修订核对**：`isPreparedSourceCurrent` 比较 `readStoredRevision(id)` 与 `source.revision`，不一致返回 `undefined`，调用方循环重试（`load` 的提交回调见 `packages/session/session-persistence/src/coordinator.ts:764`，核对在 `commitPrepared` 的 `:943`）。它防的是"外部写者（另一个进程/会话恢复）在我读完之后又写了日志"——两阶段让"读到的"与"提交的"之间有一道**修订一致性闸门**。
- **owner 守卫**（`:940`）：已有 live owner 的会话拒绝再次提交，防止两个内存状态同时认领一个磁盘会话。
- `commitRepair`（`:945-948`，后端实现见 §15.3.4/§15.4.4）只在 `source.tornMarker !== undefined || source.closers.length > 0` 时执行，且**修复后不直接采用旧内存视图**，而是返回 `undefined` 触发重载——因为"用修复前的视图配修复后的磁盘"必然错位。

写出路径同样体现"先入队、后落盘"：`write-behind.ts` 的 `SessionWriteBehind`（`packages/session/session-persistence/src/coordinator.ts:22`）提供 `enqueue`（`:45-56`）/`flush`（`:63-72`）/定时器（`:81-83`）/`drainBarrier`（`:118`），默认批量最大延迟 `DEFAULT_WRITE_BATCH_MAX_DELAY_MS = 200`ms（`packages/session/session-persistence/src/coordinator.ts:30`）。写穿队列把高频事件流聚合成批，而坐等 `SessionStore.flush`（`packages/core/session/src/index.ts:1022-1039`，用 `Promise.allSettled` 收集所有 `session/flush` 订阅者结果，`:1026-1035`）则提供"导出前一定已落盘"的强保证。

## 15.3 JSONL 后端：一个会话一个目录

### 15.3.1 目录布局与路径编码

默认根为 `$DSH_HOME/sessions`（`packages/bundle/base/cordis.patch.yml:101`）。从根往下，`format.ts` 定义了三级命名：

```text
$DSH_HOME/sessions/
├── --Users--me--workspace--/          # projectKey(cwd)：分隔符折叠为 '-'，两侧 -- 包裹
│   └── session-7d9cbae0/              # sessionDir：encodeSegment(id)
│       └── session.jsonl.zstd         # logPath：session + logSuffix
└── _no-cwd/                           # cwd 缺失时的兜底目录（projectDir，format.ts:176-179）
```

关键函数（`session-persistence-jsonl/src/format.ts`）：

- `encodeSegment`（`packages/bundle/base/cordis.patch.yml:121-136`）：把任意字符串变成安全的单段文件名。规则：`[A-Za-z0-9._-]` 原样保留，其余字符编码为 `~XXXX`（十六进制码点，大写）；`"."` 特判为 `~002E`、`".."` 为 `~002E~002E`——**防目录穿越**：任何 cwd/session id 都不可能拼出 `..` 目录段。
- `projectKey`（`:147-167`）：把 cwd 压缩成可读且唯一的目录名——`/`、`\`、`:` 连续段折叠为一个 `-`（Windows 路径因此与 POSIX 归一），非安全字符同样 `~XXXX` 转义，截断 251 字符，并整体包裹在 `--…--` 里。这个包裹不是装饰：它确保项目键永远不会等于 `_no-cwd` 这个保留名，也与 `session-*` 段不撞。
- `logSuffix`（`:24`）：`.jsonl.zstd` 或 `.jsonl`，压缩仅是后缀标注。

### 15.3.2 行格式：头行 + 事件行（+ 打包行）

文件第一行是 `HeaderLine`（`packages/bundle/base/cordis.patch.yml:33-44`，`toHeaderLine` 编 / `fromHeaderLine` 解，`:51/:71`，`isHeaderLine` 形状守卫 `:89`），之后每行一个事件（`eventLines`，`:221-224`）。有两个细节值得注意：

1. **版本拒绝**：`refuseForeignFormatVersion`（`packages/bundle/base/cordis.patch.yml:240-247`）解析到头行版本与当前构建不符时**拒绝加载**（而绝不尝试翻译）——日志是可失败资产，先拒绝再谈兼容。
2. **chunk 打包**：`assistant/chunk` 增量流每令牌一个事件，若逐行存储，JSON 信封的体积可达有效载荷的约 56 倍（`packages/core/session/src/chunk-rows.ts:6-7` 的实测注释）；因此打包为"行内行"——`packages/core/session/src/chunk-rows.ts:65-67` 定义的行类型把连续同块增量合并进**一条存储行**，读回时无损展开。**存储行是持久化词汇，不是会话事件**：它从不进入 `Session.events`，也没有 `SessionEventMap` 条目（`packages/core/session/src/chunk-rows.ts:10-14`）。加载时由 `SessionLogScanner`（`packages/session/session-persistence-jsonl/src/format.ts:272-378`，`scanLog` 入口 `:388`）统一解码展开。

### 15.3.3 物化：把"第一次 append"发布到磁盘

首次 append 走 `materialize`（`packages/session/session-persistence-jsonl/src/index.ts:514-526`）：编码全部内容（`encodeMaterialization`，`:619-626`，头行帧与事件帧分两次编码），然后按平台选择发布路径：

- **POSIX**（`materializePosix`，`packages/session/session-persistence-jsonl/src/index.ts:529-569`）：`mkdir 0o700`（`:536-540`，目录私有）→ `rejectExistingLog`（`:542`，已存在即拒绝）→ `writeSyncedTempFile`（`:543`，`'wx'` 独占创建 + `0o600` + fsync，`:606-616`）→ **用 `link`+`unlink` 发布而非 `rename`**（`:544-556`）：之所以不用 rename，是因为 `link` 在目标已存在时给出 `EEXIST`——**并发创建第二个会话时，后到者以 EEXIST 失败而不是覆盖先到者**；随后 fsync 父目录（`:560`）保证目录项持久。
- **Windows**（`materializeWin32`，`:573-591`）：Windows 没有"fsync 父目录"的 Node 合约（`packages/session/session-persistence-jsonl/src/win32.ts:1-12` 注释），因此改用原生原语：在目标目录内建 staging 对象，再以 `MoveFileExW(..., MOVEFILE_WRITE_THROUGH)` 发布（`:8,:30,:118`），且**不设替换、不做跨卷回退**——保证"要么没发布，要么已持久"。

### 15.3.4 追加、torn tail 与崩溃恢复

追加（`appendBatch`，`packages/session/session-persistence-jsonl/src/index.ts:422-429`）已物化则 `appendLines`（`:651-660`）：`open(path,'a')` → 记录写入前字节长 → `writeFile` + `sync` → **失败时 `rollbackAppend` 把文件 truncate 回写入前长度**（`:663-664`、`rollbackAppend` `:673-677`），从而把"追加失败"变成"追加从未发生"，日志保持完整前缀。

崩溃恢复典型路径：写入中途掉电，文件尾部出现半个 zstd 帧或半个事件。读侧由 `scanZstdFrames`（`packages/session/session-persistence-jsonl/src/zstd.ts:48`，魔数 `ZSTD_MAGIC = 0xFD2FB528` `:15`，启用校验和 `checksumFlag:1` `:19`）定位"最后一个完整帧边界"之后的 `tornStart`；`commitRepair`（`packages/session/session-persistence-jsonl/src/index.ts:436-444`）执行 `repair`——truncate 到损坏起点再 fsync（`:694-697`），并追加合成闭包事件（补偿缺失的 turn/step 边界）。列表时`listArtifacts`（`:472-509`）只读每文件头行（`:490-493`），且拒绝已存在同名会话的多余产物（`:500-503`）与后缀不符的压缩选择（`:482-485`）。

**小结 jsonl 端的耐久性设计**：独占创建（`wx`/`link`-EEXIST）防覆盖 → 临时文件 + fsync 防半写 → 目录 fsync / `MOVEFILE_WRITE_THROUGH` 防发布丢失 → 截断回滚防"追加失败留脏尾" → 帧扫描 + 修复防"半帧不可读"。每个环节都对应一次真实崩溃场景。

## 15.4 SQLite 后端：一个数据库一个仓

### 15.4.1 版本与身份：SCHEMA_VERSION=15、APPLICATION_ID=0x44534850

`session-persistence-sqlite/src/schema.ts` 开头是两份"身份"声明：

- `SCHEMA_VERSION = 15`（`packages/session/session-persistence-jsonl/src/index.ts:20`）——注释（`:15-19`）强调：它只管**表结构与读写语义**，与"事件词汇版本"（第 8 章 `SESSION_FORMAT_VERSION`，`packages/core/session/src/types.ts:56`，值为 0）**正交**：新增一种事件类型不需要迁移数据库，改表结构才需要，且**只拒绝、不迁移**。
- `SESSION_PERSISTENCE_SQLITE_APPLICATION_ID = 0x44534850`（`:23`）——即 ASCII `"DSHP"`，写进 SQLite 文件头的 `application_id` 槽（`:152`），用来区分"这是 Harness 会话库"与"另一个程序恰好叫这个名字的库"。

`configureDatabase`（`packages/core/session/src/types.ts:92-172`）的开门检查逐条拒绝（对照 `PRAGMA user_version` 与 `application_id`）：非空库但 `user_version=0`（无法判断归属）拒绝（`:105-107`）；版本不等于 15 拒绝（`:108-110`）；版本等于 15 但 `application_id` 不是 `0x44534850` 拒绝（`:111-114`）。**没有"自动升级"——升级路径由人（备份 → 新版本程序打开 → 若拒绝则迁移工具）负责**，这正是"怎么迁移"一问在 SQLite 侧的答案：先备份文件，再让新版本打开；版本兼容表由 `SCHEMA_VERSION` 单点裁决。

### 15.4.2 三张 STRICT 表（DDL 走读）

```sql
CREATE TABLE IF NOT EXISTS persistence_state (
  singleton INTEGER PRIMARY KEY CHECK (singleton = 1),
  store_id  TEXT NOT NULL
) STRICT;
CREATE TABLE IF NOT EXISTS sessions (
  id TEXT PRIMARY KEY, version INTEGER NOT NULL, created_at INTEGER NOT NULL,
  cwd TEXT, parent_session TEXT, seed_length INTEGER, origin TEXT,
  delegation_depth INTEGER, agent_preset TEXT,
  incarnation TEXT NOT NULL, revision INTEGER NOT NULL
) STRICT;
CREATE TABLE IF NOT EXISTS events (
  session_id TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  seq INTEGER NOT NULL, type TEXT NOT NULL, time INTEGER NOT NULL,
  data TEXT NOT NULL, source_event_seqs TEXT, surface_op TEXT, ignorable INTEGER,
  PRIMARY KEY (session_id, seq)
) STRICT;
```

（`packages/session/session-persistence-sqlite/src/schema.ts:116-147`）三张表各有职责：`persistence_state` 是**单行存储身份**——`store_id` 在首次打开时以 `INSERT OR IGNORE` 写入（`:148-150`），配合 `packages/session/session-persistence-sqlite/src/index.ts:160-164` 读出的 `file:<dev>:<ino>:<birthtimeNs>:store:<store_id>` 作为**修订身份**；`sessions` 一行一个会话，`revision` 是单调变更令牌（`SchemaRow` 注释 `:26-27`）；`events` 以 `(session_id, seq)` 复合主键保证**每会话 seq 唯一**，`data` 存 JSON 文本，`source_event_seqs`/`surface_op`/`ignorable` 是 surface 侧元数据（`EventRow` 注释 `:30-56`）。全部 `STRICT`（SQLite 严格类型），`ON DELETE CASCADE` 让删会话自动清事件——这不是可选优化，而是"会话即聚合根"的数据库表达。

### 15.4.3 appendBatch：一个事务完成会话行 + 事件行 + revision

走读 `packages/session/session-persistence-sqlite/src/index.ts:284-302`：

```ts
this.db.exec('BEGIN')
try {
  if (!isMaterialized) this.writeRow(meta)          // 首次：写/upsert 会话行
  for (const event of events) insertEvent.run(...)  // 逐事件插入
  this.db.prepare('UPDATE sessions SET revision = revision + 1 WHERE id = ?').run(meta.id)
  this.db.exec('COMMIT')
} catch (error) { this.db.exec('ROLLBACK'); throw error }
```

`writeRow`（`packages/session/session-persistence-sqlite/src/index.ts:385-411`）是 `INSERT ... ON CONFLICT(id) DO UPDATE`（`:390`）：会话头字段被覆盖更新，而 `incarnation` 每次写成新 `randomUUID()`（`:409`）、`revision` 初始 0（`:391`）。**单事务的原因**（这也是 SQLite 后端最核心的一条设计）：会话行、事件行、revision 三者**要么一起可见，要么一起不存在**——读侧永远不会看到"有事件无会话"或"修订号落后于事件"的中间态。`revision` 正是协调器 `isPreparedSourceCurrent` 所比对的"磁盘修订"（§15.2.5），它在每次成功 COMMIT 后 +1，配合 `incarnation`（换一次会话生命周期换一次身份）构成完整的"当前性"判据。

SQLite 后端没有"每会话一文件"：`locate` 直接返回 `undefined`（`packages/session/session-persistence-sqlite/src/index.ts:173-175`），`supportsRawArtifacts = false`（`:100`）。它也没有独立物化步骤——`appendBatch` 里写会话行就是物化（`:382-384` 注释）。

### 15.4.4 torn tail：行扫描而不是帧扫描

`scanRows`（`packages/session/session-persistence-sqlite/src/schema.ts:232-270`）按 seq 顺序扫描事件行，规则：已提交区出现 seq 洞=损坏，拒绝（`:257,:261`）；尾部出现洞=torn，**停止并记下 `tornFrom`**（`:258,:262,:269`）。`commitRepair`（`packages/session/session-persistence-sqlite/src/index.ts:309-338`）在同一事务里 `DELETE` 洞区、`INSERT` 合成闭包事件（`:316-325`，注释 `:330` 说明 DELETE+INSERT 不可能碰撞），然后同样走"修复后重载"（§15.2.5）。journal 默认 `wal`（`packages/session/session-persistence-sqlite/src/index.ts:106`），其余回滚日志模式留给网络挂载等 WAL 不适用的文件系统（`packages/session/session-persistence-sqlite/src/schema.ts:58-67` 注释）。

### 15.4.5 两后端取舍表

| 维度 | jsonl.zstd | SQLite |
|---|---|---|
| 可读性/可调试 | 每行可读、可 grep、可 diff | 需客户端工具 |

## 15.5 投影、查询与会话标题

### 15.5.1 投影：新概念三步讲

**① 类比**：把会话事件流想象成商店流水账（"卖了什么、多少钱"逐笔记）。**投影（projection）**就是账本旁边的"分类合计表"：每来一笔流水，合计表就地更新一格；合计表可以随时抄一份存起来（快照），也可以被"删掉重算"（只要流水还在）。**缓存**则是在页脚写着"合计截至第 N 笔"的复印件——旧一点没事，绝不会错。

**② 精确定义**：投影 = 以"已提交事件序列"为输入的**纯函数折叠**，由四件套 `ProjectionDefinition`（`packages/session/session-projection/src/index.ts:42-74`）声明：`key`（单元在投影映射表中的槽位）、`init()`（空日志初态）、`apply(state, event) → next`（**纯转移**：不关心的事件必须原引用返回，注释 `:53-55` 明言"引用不变=零下游工作"）、`view(state)`（内部状态→对外读数）、`stateVersion`（序列化语义版本：变更即作废旧缓存，`注释 :65-71`）。多单元共享的状态机集群叫注册表 `SessionProjectionRegistry`（`:171-184`）：它订阅 `session/event`，每个事件驱动所有单元（drive，`:405-425`）；`drive` 的要点是 **late build**（迟注册单元先从历史折叠，`:411`）、**`Object.is` 判变化**（`:415`）、变了才通知监听者（`:418-423`）。`register` 还带**引用计数**（`:211,:217-218`，注释 `:137-153`）：同一 key 可被多个预置多次注册，最后一个注销才真正释放；同 key 不同 `stateVersion` 直接拒绝（`:208-210`）——"语义不同的单元不能共占一个槽"。

**③ 最小示例**——`session-title` 服务注册的 `title` 单元（`packages/session/session-title/src/index.ts:309-317`），全项目最短的投影单元：

```ts
projectionCtx.sessionProjections.register<'title', string | null>({
  key: 'title',
  init: () => null,
  apply: (state, event) => (event.type === 'session/title' ? event.data.title : state),
  view: (state) => state,
  stateVersion: 1,
})
```

十行之内定义了一个"标题=最后一次 `session/title` 事件"的投影：`apply` 对无关事件返回原引用，对目标事件取新值——恰好是 §15.5.1 定义的最小实现。

**快照与缓存**：`snapshot`（`packages/session/session-title/src/index.ts:248-255`）给出所有单元的一致切面；`checkpoint`（`:271-282`，`structuredClone` 出可持久化状态）；`restore`（`:355-385`）带**可用性校验**（基础 seq 高于某锚点且不可用时抛错，`:367-371`）；`restoreFloor`（`:300-310`）实现"one-below 锚点"——只重放比缓存基线新的部分，旧的直接丢弃。持久缓存由 `SessionProjectionCache`（`packages/session/session-projection-cache/src/index.ts:71`）承担：**fail-soft**（注释 `:68`——写失败只丢缓存不丢正确性），`turn/end` 与 `session/disposed` 是两个强制写点（`:206-207,:226`），流内由 `writeEveryEvents`/`writeIntervalMs` 节流（`:213,:219`）。落盘位置随 storage-json：`session_projcache.json` 与 `workspace.json` 同根（`packages/session/session-projection-cache/src/spec.ts:7-8`）。

### 15.5.2 查询：corpus、filters、tracing

`session-query` 把"读会话"变成可编程 API：`SessionCorpus`（`packages/session-query/session-query/src/corpus.ts:32`）提供 `listSessions`（`:58`，**live 会话优先**、按时间倒序）、`load`（`:88`）、`projectMany`（`:128`，跨会话批量投影）；`filters.ts` 提供结果/事件两级过滤与文本过滤器编译（`:18,:32,:45,:75,:105`）；`tracing.ts` 提供事件记录与调用轨迹（`eventRecords` `:27`、`traceEvent` `:65`、`traceSession` `:113`）。全文检索走 SQLite FTS5 索引（`packages/session-query/session-query-sqlite/src/schema.ts:127-136`，`unicode61` 分词 `:135`；`temp.live_docs` 为 live 会话的内存影子表 `:158-166`，schema 版本 8 `:8`）。

两条产品缺省值得记住（`packages/bundle/base/cordis.patch.yml:124-125`）：**默认 `path: ':memory:'`、`openAt: never`**——全文搜索默认关闭（`searchSessions` 抛 `SESSION_QUERY_SEARCH_DISABLED`），但精确读取、筛选、轨迹追踪照常可用；部署方按需打开，并处理 FTS5 语法当作普通数据、谓词预算 14/13 等规格（`packages/session-query/session-query-sqlite/README.zh.md:9`、`:19`、`:30`）。

### 15.5.3 会话标题

`session/title` 是一类**只进日志**的事件（`packages/session/session-title/src/index.ts:60`，消息扩展 `:100`），由 `SessionTitleService`（`:261`）管理：配置三项必填（`fallbackMaxWords`/`fallbackMaxBytes`/`maxTitleBytes`，`:263-267`）约束 LLM 生成与截断；`title` 投影单元（§15.5.1 示例）从日志折叠出当前标题；`get`（`:348`）与 `rename`（`:363-379`，内部 `session.append('session/title', …)` `:374`）是读/写两面对外 API。**标题不进独立存储**——它就在事件流里，这正是"投影用于读、日志用于存"的教科书示范。

## 15.6 存储域、workspace、附件与 spill

### 15.6.1 storage：域 + 可换后端

**① 类比**：`storage` 是"带表结构定义和换介质能力的迷你数据库"——域（domain）定义表结构与校验，后端（backend）决定存在哪（一个 JSON 文件/一张 SQLite 表），`storage` 服务做路由。

**② 精确定义**：`StorageBackend`（`packages/storage/storage/src/backend.ts:17-27`）按 `KvUnitDescriptor`（`:46-55`，含 unit 名与表名，须匹配 `UNIT_NAME_RE` `:10` 的 `[a-z][a-z0-9_]*`）打开 `KvUnit`（`:66`）；`KvUnit` 的契约是**单次调用在介质上原子且 durable**（`:57-65` 注释：崩溃后重开必能观察到已 resolve 的写），且**不序列化并发写——顺序由上层域层负责**（每单元一条写链）。域即 `DomainSpec`（`packages/storage/storage-domain/src/spec.ts:35-44`）经 `defineDomain`（`:79-99`）注册的 `{name, version, global, tables}` 声明；`packages/storage/storage-domain/src/domain.ts:5` 的写序注释是灵魂：**先持久、再改内存、最后发 `domain/changed`**——持久写失败则内存不动，读与事件永远一致（`emit` `:253`；事件类型 `packages/storage/storage-domain/src/events.ts:46`）。

产品里域的真实落点：`packages/bundle/web-app/cordis.patch.yml:55-62` 挂 `storage-json`（`root: !!js dshHomePath('storages')`，每域一个人可读文件，`packages/storage/storage-json/src/index.ts:2-4`）与 `storage-domain`（`backend: json`）。

### 15.6.2 workspace 注册表

`WorkspaceRegistry`（`packages/workspace/workspace/src/index.ts:92`）依赖 `storageDomain` 与 `sessionPersistence`（`inject` `:93`）。初始化时打开 `workspace` 域（`packages/workspace/workspace/src/spec.ts:67-70`，`name: 'workspace'`、`version: 2`），域状态为 `workspaceDomainState`（`:51-56`，含 `pendingMutation`）：**第一次启动、域里还没有数据时，从 `sessionPersistence.list()` 引导**（`packages/workspace/workspace/src/index.ts:129-133`）——用磁盘上已有的会话头反哺出注册表初始行，使得"历史会话突然有了工作区归属"。每行记录（`workspaceRecord`，`packages/workspace/workspace/src/spec.ts:21-27`）是长期稳定性数据，`pendingMutation`（`:37-40`）是"落地前"的未完成意图，崩溃后以此对账。

### 15.6.3 attachment：内容寻址

**① 类比**：Git 对象库。文件内容哈希成名字，同名即同物，天然去重；"引用"是一个哈希字符串，任何人不改内容就无法伪造引用。

**② 精确定义**：**内容寻址（content addressing）**=以内容摘要（SHA-256）作为对象标识与存储路径。`attachment-local/src/store.ts` 中 `ID_PATTERN = /^sha256:([a-f0-9]{64})$/`（`packages/workspace/workspace/src/spec.ts:19`），`objectPath`（`:36-37`）把哈希拆成 `objects/xx/<sha256>` 两级目录（前两字符分桶，避免单目录膨胀）。`saveImageFile`（`:136-194`）用 `link` 做去重写入（`:158`），已存在则以 `EEXIST` 校验而非覆盖（`:161-163`）——与 §15.3.3 同款"后到者失败"哲学。

**③ 最小示例**（目录对照）：`attachments/v1/objects/ab/abcd…`（64 位哈希前两位 `ab` 分桶）+ 消息里的 `attachmentId: "sha256:abcd…"`。限额见 `packages/attachment/attachment-local/src/index.ts:15-21`：单图 5 MiB、单消息 20 张、单消息合计 100 MiB、单图 4000 万像素；根目录固定 `<DSH_HOME>/attachments/v1`（`:53`），媒体类型白名单 `:59`。读取时 `readImageFile`（`packages/attachment/attachment-local/src/store.ts:204-221`）缺对象抛 `ATTACHMENT_NOT_FOUND`（`:216`）并做完整性校验（`:220`）。附件**不进会话日志**——日志只存引用（`packages/bundle/base/cordis.patch.yml:104-105` 注释），这正是"日志 append-only、正文可去重"的分工。

### 15.6.4 spill：大家伙请出内存

spill 解决"工具结果太大塞进上下文"：`LocalSpillStore`（`packages/spill/spill-local/src/index.ts:37`）把全文写盘，返回一个引用；`spill-policy`（`spill-policy/src/index.ts`）按 `maxInlineBytes`（`:66`）做预算：超限的结果替换为"头尾预览 + 溢出通知"（`preview` `:95`、`spillNotice` `:105`、`spillReplacement` `:130`）。两个易被忽略的细节：**通知字节先预留**（`:170-171`——预览预算 = 上限 − 通知长度，保证替换结果永远不超过上限）；**未配置 `maxInlineBytes` 即整体 no-op**（`:20,:111-113`）。落盘位置：默认取 `privateRoot()`（`packages/spill/spill-local/src/index.ts:47`）——在 OS 临时目录下 `mkdtemp` 出**0700 且不可预测**的进程私有目录（`packages/spill/spill-local/src/store.ts:20-29`），写入用 `'wx', 0o600`（`packages/spill/spill-local/src/store.ts:100-106`）：spill 文件可能含未脱敏的工具输出，权限位是最后防线。

## 15.7 settings 与 credentials：配置与秘密的分家

### 15.7.1 为什么必须分开

**① 类比**：办公室的"排班表"（谁都能看、常改、贴墙上）与"保险柜钥匙"（只有当事人能碰、绝不贴墙）。settings 是排班表，credentials 是保险柜。

**② 精确定义**：settings 是**多命名空间的结构化配置**（命名空间模式 `/^[a-z][a-z0-9-]*$/`，`packages/settings/settings/src/index.ts:19`；作用域 `SettingsScope` `:103`；冲突抛 `SettingsConflictError`，码 `SETTINGS_CONFLICT` `:164-166`）；credentials 是**名称→秘密值**的解析链（`packages/credentials/credentials/src/index.ts:60`，四方法 `resolve/describe/set/unset` `:73-99`）。

**③ 它们分开的三个工程理由**（都能在源码/注释里找到出处）：

1. **生命周期不同**：settings 文件被 watcher 热重载（`packages/settings/settings-file/src/index.ts:64-65`，watch 默认开、debounce 100ms），凭据则在**进程启动瞬间被快照**（`packages/util/launch-environment/src/index.ts:78-103`）——运行中改 `.env` 不会生效，改 settings 会。把一个热一个冷混在一起，用户必踩坑。
2. **暴露面不同**：Web 的 Models 页允许用户编辑 settings 文档（`packages/bundle/base/cordis.patch.yml:74-78` 注释），而凭据只写托管文档、**绝不物化进进程环境**（`packages/credentials/credentials-local/src/index.ts:30-32` 注释）；settings 可以被展示、回显，凭据只能"有/没有"。
3. **信任层级不同**：凭据解析是**固定优先级**的（环境 > 托管文件 > 项目 .env > 用户 .env，`packages/credentials/credentials-local/src/index.ts:5-10` 注释），且**继承环境永远赢**——因为 `DEEPSEEK_API_KEY=x dsh` 这种命令行注入必须压过磁盘文件（`:12-17` 注释）；settings 则是可合并、可冲突检测的文档。

### 15.7.2 settings-file 走读

`resolveSpec`（`packages/settings/settings-file/src/index.ts:55-62`）：显式 `path` 优先，否则 `<harness home>/settings.yaml`（即 `$DSH_HOME/settings.yaml`，`packages/bundle/base/cordis.patch.yml:74` 注释确认）；扩展名限定 `.yaml/.yml/.json`。`persistSection`（`packages/settings/settings-file/src/index.ts:210-231`）是写路径核心：先 `mkdir 0o700`（`:214`）——"harness home 装的是用户私有文档"；再 `withFileLock`（`:215`）保证跨进程互斥；写前 `reconcileFromDisk`（`:222`）做**读-改-写合并**——把 watcher 视野外的手工编辑折叠进来，绝不覆盖用户的并发修改；最后 `writeFileAtomic(…, { mode: 0o600, dirMode: 0o700 })`（`:227`）原子发布，且**0600：可能含个人值的文档永不组可读**（`:226` 注释）。读侧，**已存在但解析失败 = 启动失败**（`:235-238` 注释：绝不静默忽略或覆盖损坏的文档）。

### 15.7.3 credentials 四级分层与安全动机

解析顺序（`packages/credentials/credentials-local/src/index.ts:309-317` 的 `resolve`）：① 继承环境（`env`）→ ② 托管文件 `$DSH_HOME/.credentials.yaml`（`file`）→ ③ `<invocation cwd>/.env`（`project-env`）→ ④ `$DSH_HOME/.env`（`user-env`）。环境层由 `launch-environment` 的 `SOURCE_ORDER = ['process', 'project-env', 'user-env']`（`:19`）与 `createLaunchEnvironmentSnapshot`（`:78-103`）实现——注意它把 `process.env` 排最前，与凭据层"环境赢"一致。`describe`（`:319-331`）只对继承环境标记 `writable: false`（`:322-326`）——这正是"保险柜钥匙有两把：一把只能看不能换（环境），一把存进保险柜（托管文件）"的代码表达。

**最小示例**（`$DSH_HOME/.credentials.yaml`）：

```yaml
# 由 dsh credentials set 写入；不要手改权限位
deepseek-official:
  apiKey: sk-…
# 解析顺序：env > 本文件 > ./.env > $DSH_HOME/.env
```

安全动机不只是"0600"：

- **写**：`set` 拒绝空值（`packages/credentials/credentials-local/src/index.ts:336-339`），文件经 `mkdir 0o700` + `writeFileAtomic { mode: 0o600, dirMode: 0o700 }`（`:383,:394`）；
- **读前检查**：`assertOwnerOnly`（`:103-122`）在非 Windows 上对既有文件做权限审计——组/其他位有任何读权限（`GROUP_OTHER_BITS = 0o077`，`:88`）即拒绝启动，并给出 `chmod 600` 的修复文案（`:117-120`）；Windows 跳过（`:113`）因为 ACL 语义不同；
- **隔离**：凭据文件与设置文件、会话日志分开目录，复制/打包时天然区别对待。

|---|---|---|
| 目标（goal） | 事件 `goal/change` → `'goal'` 投影单元；`GOAL_CHANGE_VERSION=1` | `packages/goal/goal/src/index.ts:205-206`（单元注册）、`packages/goal/goal/src/runtime.ts:8`、`packages/goal/goal/src/fold.ts:134`（`decodeGoalChange` 严格校验：版本不匹配即抛错，`:137-139`） |

## 小结

1. 一切持久化都挂在 `$DSH_HOME`（配置 < `$DSH_HOME` < `~/.dsh`）之下；数据资产 = 会话日志 + 投影检查点 + 若干持久域 + 配置文件 + 附件/spill 文件，**每种数据的格式与位置都由组合包 patch 裁决**（`packages/bundle/base/cordis.patch.yml`、`packages/bundle/web-app/cordis.patch.yml`）。
2. 落盘是"接口（`SessionPersistence`）—协调器（`PersistenceCoordinator`）—后端（`PersistenceBackend`）"三层；协调器订阅第 8 章的 `session/*` 事件组，把事件流变成"seq 连续、批事务、可修订核对"的持久流。
3. `prepare`/`commitPrepared` 两阶段 = 读+修复 与 提交+登记分离，中间以**磁盘修订号**为闸门：先读后写、写前核对、修复后重载、owner 唯一。
4. jsonl.zstd 后端"一个会话一个目录"，用独占创建/临时文件/目录 fsync/截断回滚把每次崩溃都算清楚；SQLite 后端用 `SCHEMA_VERSION=15`+`APPLICATION_ID=0x44534850`+3 张 STRICT 表+单事务 append+`revision`/`incarnation` 提供事务级一致；**两者可经 patch 切换，业务代码不变**。
5. 投影是"事件流 → 可读值"的纯折叠，配 fail-soft 缓存（旧不错、可重放）；标题、目标都是投影单元，标题永不单独存储。
6. settings（热、可展示、可合并）与 credentials（冷、只读解析链、0600/0700）的分离由生命周期、暴露面、信任层级三条理由支撑；凭据解析顺序固定为"环境 > `$DSH_HOME/.credentials.yaml` > `cwd/.env` > `$DSH_HOME/.env`"。

**理解**

1. 一个会话创建后没有任何事件就退出。jsonl 与 SQLite 后端分别在磁盘上留下什么？为什么 `list` 可能看不到它（提示：`packages/session/session-persistence/src/index.ts:126-129` 的"可延迟物化"）？

3. 说明 `SCHEMA_VERSION=15` 与 `SESSION_FORMAT_VERSION=0`（`packages/core/session/src/types.ts:56`）各管什么，为什么正交。

**应用**

**综合**
