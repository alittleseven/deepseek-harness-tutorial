# 第 14 章　长程会话治理：compaction、plan-mode、todo、context 与 guard

**学习目标**

1. 复述 compaction 的五步 surface 契约，并解释"旧事件仍在日志里、却从模型可见性中消失"的机制；
2. 说出 `compaction-basic` 的两条自动触发链（`agent/pre-step` 压力、`agent/request-error` 溢出）与手动入口 `/compact`；
3. 描述 plan-mode 的软约束立场：`plan/mode` 状态、`exit_plan_mode` 评审出口与"plan 不是安全边界"的双轨设计；
4. 说明 `todo_write` 为什么是"整表替换、last-write-wins"，以及单主与 `allowParallelInProgress` 的取舍；
5. 区分两类守卫：`repeat-tool-reminder` 的建议性提醒与 `timeout-policy` 的强制超时；
6. 概括 context 四件套（AGENTS.md、时间、tmux、会话引用）各自注入什么、何时注入；
7. 概览 commands、feedback、goal 三个用户交互收尾部件各自的事件接入点。

**本章讲法**：排障/控制型——问题清单驱动。长会话会得四类病（上下文爆炸、跑偏、重复失控、失忆），本章按"病"逐条开药：每节先描述症状与机制，再定位药方接入的**事件或工具**，最后说清它**动了谁**（模型上下文、会话日志、还是工具执行信号）。

## 14.1 问题清单：长会话的四类病

第 8、9 章建立的心智是：会话日志是事件流，模型每轮从"表面"读取消息（见第 8 章）。会话越长寿，四类病越常见：

- **病一：上下文爆炸**。历史事件无限累积，请求越来越大；到极限时模型直接报 `CONTEXT_WINDOW_EXCEEDED`，轮次硬失败。
- **病二：跑偏**。模型拿到 `read_file` 就动手改代码，用户其实只想先看方案；或者它已经干完一大半，用户才发现方向不对。
- **病三：重复与失控**。同一个工具被连续调用七八次还不收敛；任务清单越写越长、过期条目没人清理；某条工具调用悬挂十分钟。
- **病四：失忆**。模型不知道项目根在哪、现在几点、自己在哪个 tmux 窗格、这次会话是上一段会话的续篇。

dsh 对每种病各有一组治理手段，接入点各不相同（表 14-1）。

**表 14-1　问题清单与治理手段**

| 病 | 治理手段 | 接入点（事件/工具） | 动了谁 |
|---|---|---|---|
| 上下文爆炸 | compaction、tool-result-pruner | `agent/pre-step`、`agent/request-error`、`/compact` | 会话表面（模型可见事件序列） |
| 跑偏 | plan-mode | `command/run`（`/plan`）、工具 `exit_plan_mode` | `plan/mode` 会话事件 + 提问通道 |
| 任务清单失控 | `todo_write` | 工具 `todo_write` | `todo/write` 会话事件 + 投影 |
| 重复调用 | repeat-tool-reminder | `tools/post-execute`、`agent/pre-step` | 模型上下文（建议） |
| 工具悬挂 | timeout-policy | `tools/execute`（around 包装） | 工具执行信号（强制） |
| 失忆 | context 四件套 | `agent/pre-step` 等 | 模型上下文（注入） |
| 收尾 | commands / feedback / goal | `command/run`、`feedback/record`、`goal/change` | 会话事件 |

本章按病情的"紧急程度"排序：先救火（压缩），再纠偏（计划），再治重复（任务清单、守卫），再补记忆（上下文），最后是收尾三件套。每节的落点都回到表 14-1 的"动了谁"一列。

## 14.2 病一·上下文爆炸：compaction 的五步表面契约

### 14.2.1 类比与精确定义

**① 类比**：单位开长会，前两个月的记录堆满会议室。秘书的做法是：把旧记录压成**一页纪要**贴在墙上，厚本子归档到档案室——档案室还在（随时可查、可审计），但会议上的人只看得见墙上那页。compaction（压缩）就是"贴纪要"。

**② 精确定义**：压缩 = 把会话日志表面上一段旧的范围，替换为**一个由模型生成的摘要节点**；这个替换是"表面操作"（`surfaceOp`），被替换的旧事件仍留在原始日志中，但不再出现在派生的模型消息里。组件上，`CompactionEngine`（`ctx.compaction`）只定义"做什么"，三种操作全部抽象，由后端决定"怎么做"（`packages/compaction/compaction/src/index.ts:96`）：

```ts
abstract class CompactionEngine {
  abstract compactIfNeeded(agent, trigger: 'pressure' | 'context-overflow', signal): Promise<CompactionResult | null>
  abstract compactNow(agent, signal): Promise<CompactionResult>
  abstract compactRegion(start, end, agent, signal?): Promise<CompactionResult>
}
```

三个抽象方法对应三种用途：`compactIfNeeded` 考虑自动压缩（压力触发可按阈值、溢出触发可强制做一次有意义的均衡缩减）；`compactNow` 在**低于**自动压力时也显式压缩一段有用的旧范围；`compactRegion` 强制压缩 `[start, end]` 的指定表面段（`packages/compaction/compaction/src/index.ts:113/:139/:164`）。三个角色分属三个包：`dsh-compaction` 定义服务与 `compaction/*` 事件，`dsh-compaction-basic` 提供"token 压力 + 预算保留 + 模型摘要"实现，`dsh-command-compact` 是消费方（`/compact` 命令）——这正是第 12 章"Service Definition / Provider / Consumer 三角色"在压缩能力上的又一次复现。

**③ 一个必须钉住的概念：表面（surface）**。第 8 章讲过，会话日志的"表面"是对模型可见的事件序列；`SurfaceEventType` 是**闭集**——只有 `user/message`、`assistant/message`、`tool/result` 三种事件可以携带 `surfaceOp`（`packages/core/session/src/types.ts:343-346`）。这意味着：`compaction/*` 事件**永远不可能出现在表面上**，压缩对模型的可见效果只能由一个 `user/message` 的替换操作完成。这正是下面五步契约的由来。

### 14.2.2 五步表面契约走读

README 把一次成功压缩描述为五步（`packages/compaction/compaction/README.md`）：

1. 追加 `compaction/start`（仅日志事件）——**取锁**；
2. 对选定范围做模型摘要；
3. 追加 `compaction/summary`（仅日志）——携带摘要、范围、被遮蔽（shadowed）的 seq 列表、token 数与 provider/model 调用信封；
4. 追加**一条** `user/message`，来源为 `compactCheckpointSource(compactionId)`，带 `surfaceOp: { op: 'replace', start, end }` 承载摘要——**这是本次操作中唯一的表面变更**；
5. 追加 `compaction/end`（仅日志）——**放锁**。

两个设计要点值得逐句读：

- **替换必须发生在锁内**：第 4 步在第 1、5 步之间，`compaction/end` 是最后一个事件。因此若在 `compaction/start` 与 `compaction/end` 之间崩溃，留下的是"有 start 无 end"的**可检测孤儿锁**，而不是"声称压缩完成、实际表面从未被遮蔽"的假 `compaction/end`。下一会话能根据"最后一个未配对的 `compaction/start` 与最晚 `session/end-seed` 的相对位置"判定它是否还是活锁（README Blocking 一节）。
- **表面位置而非 seq 区间**：`compactRegion` 的范围是"表面位置跨度"。一次替换落地后，新摘要节点带着高 seq 出现在被遮蔽范围的位置上，表面顺序不再等于 seq 顺序——所以 `compactRegion` 若传非表面节点、起止倒置或已有压缩在进行，都直接抛错（`packages/compaction/compaction/src/index.ts:164` 附近的契约）。

压缩后模型看到什么？`deriveMessages()` 把摘要渲染成一条 user 角色消息，后面跟保留的尾部节点；被遮蔽事件仍在原始日志，回放（replay）是确定的——这正是"旧历史还在、但对模型不可见"的准确含义。

### 14.2.3 触发链：两条自动路 + 一条手动路

后端 `compaction-basic` 在构造时按 `auto ?? true` 决定是否注册自动压缩（`packages/compaction/compaction-basic/src/index.ts:129`），默认开启。两条自动触发链都挂在事件上：

**① 压力触发（`agent/pre-step`）**。每轮组装请求之前调用 `compactIfNeeded(agent, 'pressure', signal)`（`packages/compaction/compaction-basic/src/index.ts:147-166`）。阈值由 `thresholdTokens = contextWindow × thresholdRatio` 计算（`packages/compaction/compaction-basic/src/config.ts:144`），默认启用 `auto`（`packages/compaction/compaction-basic/src/config.ts:95`）；触发失败只记警告"continuing the turn"，**不会**中止轮次——压缩是尽力服务，不是护栏。摘要本身直接走 `ctx.llm.stream()`（不是轮次步骤），所以对摘要调用的拦截发生在 `llm/stream`（见第 10 章）。

**② 溢出修复（`agent/request-error`）**。当模型请求失败且 `failure.code === CONTEXT_WINDOW_EXCEEDED` 时，对同一目标按策略尝试 `compactIfNeeded(agent, 'context-overflow', signal)` 后重试（`packages/compaction/compaction-basic/src/index.ts:179-194`）；每条目标策略带 `maxOverflowRetries` 上限（默认 1），且收到一条 `assistant/message` 成功响应即重置该序列，另在 `agent/status` 变为 idle 时清空溢出记账。注意它的语义：**溢出修复是"最后手段"**，不是每轮都跑。

**③ 手动路（`/compact`）**。`dsh-command-compact` 消费方把人类命令映射为 `ctx.compaction.compactNow()`（`packages/compaction/command-compact/src/index.ts:66`）。`compactNow` 会在让步前**同步预留空闲轮次准入**、没有可压缩范围时什么都不写、压缩前先记录一条 `turn: null` 的 `compaction/*` 尝试事件、并在释放前等待持久化检查点；预期内的运行期失败抛 `ManualCompactionError`，其 `code` 是**闭集** `busy | changed | summary | commit | persistence`（`packages/compaction/compaction/src/index.ts:27-34`）。闭集的意义：调用方可以安全地 `switch` 或枚举每个失败分支，而不是匹配任意字符串。

### 14.2.4 摘要生成的三个工程约束

`packages/compaction/compaction-basic/src/summarizer.ts` 处理"把旧段压成摘要"这件脏活，三个约束值得写进教材：

- **复用 KV 缓存**：摘要请求把压缩点之前的回放作为**前缀**（`packages/compaction/compaction-basic/src/summarizer.ts:111-116`），让摘要生成与后续正常请求共享前缀缓存，避免压缩本身制造新的 token 开销；
- **排除噪音**：摘要排除推理内容与工具调用记录——它们对"这段历史在做什么"的贡献最小、token 占比最大（`packages/compaction/compaction-basic/src/summarizer.ts` 的排除逻辑）；
- **配对边界**：压缩边缘不能切断未配对的工具调用。`toolPairingBalancedBefore/After`（`packages/compaction/compaction/src/tool-pairing.ts:117/:129`）负责"吸附"与校验边缘：安全边缘上没有跨界的、未应答的 assistant 工具调用，否则视为损坏的表面状态直接拒绝。

选择范围时还有两道闸：`selectCompactableRange` 选可压缩段（`packages/compaction/compaction-basic/src/region.ts:98`），累计达到 `retainTokens` 就停止——**保留最近的尾巴**不被压缩（`packages/compaction/compaction-basic/src/region.ts:118`）；`assertNoActiveCompaction` 保证同一时刻只有一个压缩在跑（`packages/compaction/compaction-basic/src/region.ts:305`）。

**相关但独立**：`ToolResultPruner`（`packages/compaction/compaction-tool-result-pruner/src/index.ts:44`）与 `pruneSession`（同文件 `:136`）做的是另一类"减法"——不压缩历史，而是把体积巨大的工具结果（如整页终端输出）修剪后再落入日志。

### 14.2.5 最小示例

```yaml
# composition 片段：开启自动压缩（默认即 true），只在手动需要时显式配
- id: compaction-basic
  name: '@deepseek-ai/dsh-compaction-basic'
  config:
    auto: true
```

用户侧体验：长会话中模型请求开始逼近窗口上限时，dsh 自动在步骤间隙压掉旧段；用户也可随时输入 `/compact`，dsh 会先记录压缩锁、再产出摘要、最后以一条 `user/message` 替换可见范围，返回一句"已压缩：遮蔽 N 个表面节点（seqs a-b，约 X tokens）"式的日志（见 `_registerAutomaticCompaction` 的 `logResult`，`packages/compaction/compaction-basic/src/index.ts:139-145`）。

**接入点小结**：`agent/pre-step`（压力）、`agent/request-error`（溢出）、`command/run`（`/compact` 手动）、`session/event`（`assistant/message` 重置记账）。**动了谁**：会话表面的可见范围；原始日志一字未删。另注意：摘要生成、阈值比例的具体默认数值属实现细节（本教程未逐字段摘取），机制已确认；真实模型摘要链路的输出质量未实测。

## 14.3 病二·跑偏：plan-mode 的"先图纸、后施工"

### 14.3.1 类比与精确定义

**① 类比**：施工队进场前先交设计图纸，业主在两栏选项上签"批准"才准动工；图纸评审期间，施工队只做勘察测量，不允许动砖。

**② 精确定义**：plan 模式（计划模式）= 会话级"先规划后执行"阀门。`plan/mode` 事件形如 `{ active: boolean }`，是**仅日志、整值替换**的会话事件；开启后，模型在每轮看到部署方配置的引导文案（`plan:policy`，提示词顺序号 50），注册唯一的出口工具 `exit_plan_mode`——只有用户经提问通道明确批准计划，该轮才在下一轮转入执行（`packages/plan/plan-mode/README.md`）。

状态管理的核心是 `foldPlanMode(events)`：折叠整个（或前缀）事件流，**最后一个 `plan/mode` 胜出**，无则视为未激活（`packages/plan/plan-mode/src/index.ts:129-138`）。正因为状态从会话日志折叠而来，resume、fork、压缩之后计划模式状态自动恢复，不需要额外持久化。`ctx.planMode.set(agent, active)` 的时机语义也由此而来：agent 空闲时立即追加事件；正在运行中则挂起为"待生效选择"，在下一个被接受的轮内 `pre-step` 生效，返回值区分 `committed`/`queued`/`cancelled`/`noop`（README durable state 一节）。

**③ 软约束立场（必须钉住）**：README 开篇明言——"Plan mode is soft guidance; sandbox mode and approval policy enforce restrictions independently and do not read or write plan state." 翻译成教材语言：**计划模式不是安全边界**。它只是改变模型的行为引导；真正的硬限制由沙盒模式与审批策略独立执行（审批态见第 11 章"工具执行流水线"，沙盒提供方见第 12 章"能力接缝"），且沙盒/审批**不读也不写**计划状态。审查时请记住这把尺子：plan 管"模型想怎么做"，sandbox/approval 管"模型被允许怎么做"，两条线正交。

### 14.3.2 exit_plan_mode：唯一出口的走读

这个工具是整套 plan 模式的门闩，其 execute 路径（`packages/plan/plan-mode/src/index.ts:305-380`）逐段读：

1. **前置校验**：无调用 agent 直接拒绝；不在 plan 模式（`foldPlanMode` 为 false）直接拒绝——工具 schema 始终注册（保持工具定义跨状态切换稳定），但只在计划模式内可用；
2. **计划格式校验**：`!/^#\s+\S/.test(args.plan.trim())` ——计划必须"以一个命名它的 `#` 标题开头"，否则报错（`packages/plan/plan-mode/src/index.ts:327`）。这条校验把"计划"和"随便一段话"区分开，也为 UI 渲染标题做准备；
3. **提问通道评审**：`ctx.userQuestions.ask` 发起评审，问题"Approve this plan and leave plan mode?"，选项 `Approve`/`Keep planning`，并把 `intent: { kind: 'plan-review', approve: 'Approve' }` 传给提问（`:334-348`）。intent 只是**呈现提示**——有能力的前端把计划渲染成评审决策卡，但模型读到的答案与普通问题一致；
4. **评审被取消**：用户关闭评审窗口去说话（`ASK_CANCELLED`）不是失败——工具明确告诉模型"留在计划模式、停下、等用户消息"（`catch` 分支）；
5. **disposed 检查**（`:365-367`）：评审可能比插件 fiber 活得久（用户看了很久才点批准），期间插件若被重载，批准就无法落地，于是果断抛错让模型重新呈现计划；
6. **批准落地**：只有 `selected` 恰好是 `Approve` 且无自定义文本时才放行；否则把用户的反馈文本抛给模型（"用户选择继续计划；反馈：…"）。批准后并不立即改状态，而是把"关闭计划"记为**静默挂起选择**，在下一个被接受的轮内 `pre-step` 再追加——保持本批工具调用期间的计划引导不中断。

### 14.3.3 入口与退出

命令入口由 `ctx.commands` 提供（`/plan`，`packages/plan/plan-mode/src/index.ts:293-301`）：

- 裸 `/plan`：开启计划模式；
- `/plan off`：**保留的精确参数**，直接退出且不向模型发消息；若还有挂起的进入选择，一并取消；
- `/plan <文本>`：先开启，再把 `<文本>` 经 `agent.steer()` 提交为下一步的普通用户消息——即"我想进计划模式，顺便说一下背景"。

### 14.3.4 最小示例

```yaml
- id: plan-mode
  name: '@deepseek-ai/dsh-plan-mode'
  config:
    section: |
      You are in plan mode. Explore and design before presenting the complete
      plan through exit_plan_mode.
```

典型回合：用户输入 `/plan 重构 git 日志展示` → 模型每轮看到 section 引导 → 模型调研后调用 `exit_plan_mode` 提交计划 → 用户点"Approve" → 下一轮模型开始执行。若用户回一句"先改数据库再改 UI"，评审取消路径生效，模型收到"留在计划模式等待消息"。

**接入点小结**：`command/run`（`/plan` 进出）、工具 `exit_plan_mode`（评审出口）、`ctx.userQuestions`（交互通道）。**动了谁**：`plan/mode` 会话事件与系统提示词（`plan:policy`），以及一次用户交互；它不写 todo、不碰沙盒与审批（代码层面无耦合，双向搜索为空；plan 与 todo 的语义衔接为产品行为，属推断）。

## 14.4 病三·任务清单失控：todo_write 的整表替换

### 14.4.1 类比与定义

**① 类比**：车间白板。工单只能整板擦掉重写——没有"加一行""改一行"的橡皮擦。好处是板上内容永远等于老板最后写的那版；坏处是每次都得重抄全表。

**② 精确定义**：`todo_write(todos: [{ content, status }])` 是模型维护自己任务清单的**唯一**通道（`packages/todo/tool-todo/src/index.ts:149` 的 `defineTool`）。每次调用，模型必须提交**整个列表**——没有部分更新、没有单条目编辑；每次调用往调用方 agent 的会话日志追加一条 `todo/write` 事件（完整列表快照），当前清单 = 最近一次 `todo/write`（重放时 last-write-wins）。`status` 取闭集 `pending | in_progress | completed`（`STATUSES`，`packages/todo/tool-todo/src/index.ts:26`）。

三条关键语义：

- **单主（single owner）**：清单只属于调用工具的那**一个** agent 会话，无子代理/共享/蜂群作用域；没有 `exec.agent` 的调用者（非 agent 上下文）直接被拒——"清单属于谁"是刻意收紧的范围限制（README Single owner 一节）。
- **并进是部署选择**：`allowParallelInProgress` 必须显式配置（`packages/todo/tool-todo/src/index.ts:42`）。`true` 表示"允许并行工单"（配合并发子代理、后台命令）；`false` 时模型一次标记超过一个 `in_progress` 会被拒：`Error: invalid todos: at most one task may be in_progress (got <n>)`（`:108`）。注意"持久日志不变量**不**跟随该开关"：日志在允许并行期间写下的多 `in_progress`，部署收紧后仍须能重放——所以日志层不检查活动计数。
- **校验 fail loud**：空 `content`、重复 `content`、`content/status` 之外的键，一律拒绝而不是静默展平——保证"日志快照 = 模型自以为写下的内容"（README Validation 一节）。

### 14.4.2 返回值与投影

工具返回 `{ todos, counts: { pending, inProgress, completed } }`（`packages/todo/tool-todo/src/index.ts:217-220`），模型看到固定句式 `Updated todo list: <pending> pending, <inProgress> in progress, <completed> completed.`——结果小且形状稳定，不随清单增长。

更重要的一层是**会话投影**（session projection）：组合装 `ctx.sessionProjections` 时，本包注册 `todos` 投影单元——`init` 为 `null`（尚无写入）；`apply` 从每个 `todo/write` 取整表、并在每个 `turn/start` 清成 `null`（**standing plan 只活到下一轮开始**，`turn/end` 保留完成的清单），`view` 为恒等，`stateVersion = 2`（README Session projection 一节）。翻译一下：**"正在做的事情"随轮次开始而清空，是给每轮一个全新起点；"已经完成的事情"留到轮次结束，供本轮复盘。** UI 从事件流订阅渲染那条计划条，不需要读模型上下文。

### 14.4.3 最小示例

```
模型调用：todo_write([
  { content: '读调研报告 E', status: 'completed' },
  { content: '写第 14 章初稿', status: 'in_progress' },
  { content: '重测汉字数', status: 'pending' },
])
返回：Updated todo list: 1 pending, 1 in progress, 1 completed.
日志：追加 todo/write 事件（整表快照）
```

**接入点小结**：工具 `todo_write`（`tools/execute` 内）。**动了谁**：`todo/write` 会话事件（供 UI/重放）与投影视图；模型上下文**不**会因为清单而多出常驻文本（只在其调用参数中保留整表，直到压缩）。`allowParallelInProgress` 的设置与真实任务并发是否匹配需要部署方自行对齐（README 明说该工具无法观测运行期并发）。

## 14.5 病三续·重复调用与悬挂：两类守卫（guard）

本节先立一个词：**守卫（guard）**——指挂在工具执行链上的"看门"插件：它不改变工具做什么，只决定"要不要放行/提醒/定时"。第 11 章的工具流水线里已有单调守卫与审批（见第 11 章）；本节的两件套治的是"重复"与"悬挂"。

### 14.5.1 repeat-tool-reminder：建议性提醒

**① 类比**：教练在场边喊"你已经挥了三次同一种拍子"——**不抢球拍**，听不听由球员决定。

**② 精确定义**：repeat-tool-reminder 守卫对"同一工具连续重复调用"计数，在**第 3、5、8 次……**（`thresholds` 默认 `[3,5,8]`，`packages/guard/repeat-tool-reminder/src/index.ts:46`）时把一条提醒**加进模型上下文**，参数预览截断在 500 字符（`argumentsPreviewChars: 500`，`:49`）。它从不替换工具返回的 `content`，而是以 `additionalContexts` 的形式**前置**提醒，并保留下游每个上下文的来源与元数据（`:213-222`）——这就是"建议性"：提醒进入模型视野，是否收敛由模型决定，调用本身从未被拦截。计数链用按 agent 的 `WeakMap`（`:173`）：提醒在 `tools/post-execute`（`:213`）回调里附加；另有一条 `agent/pre-step` 钩子（`:229-231`）——**一旦消息流里出现用户来源的消息就把该 agent 的计数链删掉**：用户插话后语境已变，跨插话的重复不算循环。

配置遵循 fail-loud 契约：`thresholds` 非空、每项为 ≥2 的整数、不得重复，否则启动时直接抛错（`validateThresholds`，`packages/guard/repeat-tool-reminder/src/index.ts:130-138`）——配置错误大声失败，而不是悄悄"修复"成别的阈值。

### 14.5.2 timeout-policy：强制超时

**① 类比**：烤箱定时器。到点**自动断电**——不是"建议你关掉"。

**② 精确定义**：timeout-policy 是 `tools/execute` 的 around 包装（`packages/guard/timeout-policy/src/index.ts:54-76`）：解析工具声明的 `timeoutMs` 预算；**没有预算的工具不动**（直接 `next()`，零配置、不干预）；有预算的用 `deadline(exec.signal, timeoutMs, TOOL_TIMEOUT)` 建立截止信号（`:21` 的 `TOOL_TIMEOUT` 常量），把派生信号换到 `exec.signal` 上分发，`finally` 中恢复上游信号——所以 `post-execute` 监听器永远看不到本插件那个可能已中止的超时信号。

超时发生后返回**结构化结果** `toolTimeoutResult(timeoutMs)`（`packages/guard/timeout-policy/src/index.ts:41-46`）：模型看到的是一条 `isError` 的 `Error: tool call timed out after Nms`，携带 `error.code = TOOL_TIMEOUT`——该码既是内部 `deadline` 分类码，也是替换结果的错误码，重试/沙盒插件与回放都能按码路由。嵌套超时（外层包装器先响）经 `timeoutOf` 按码隔离，不会被误读为本插件的超时。

**建议性 vs 强制性**：reminder 不动执行只动"视野"；timeout 不动"视野"只动执行信号。一个治"停不下来"，一个治"卡死了就不该等"。

### 14.5.3 最小示例

```yaml
- id: timeout-policy
  name: '@deepseek-ai/dsh-timeout-policy'   # 零配置；只对声明了 timeoutMs 的工具生效
- id: repeat-tool-reminder
  name: '@deepseek-ai/dsh-repeat-tool-reminder'
  config:
    thresholds: [3, 5, 8]     # 默认值；非法配置启动即抛错
    argumentsPreviewChars: 500
```

**接入点小结**：`tools/post-execute` + `agent/pre-step`（提醒）、`tools/execute` around（超时）。**动了谁**：模型上下文（提醒，建议）与工具执行信号（超时，强制）。

## 14.6 病四·失忆：context 四件套

模型每轮"重新上岗"，不记得项目规范、现在几点、自己在哪个终端、这次对话的前世。四个包各补一块：

### 14.6.1 agent-instructions：AGENTS.md 加载链

**① 类比**：新员工入职发《员工手册》——不是让他背，而是放桌上随时翻。

**② 精确定义**：agent-instructions 从会话工作目录找到项目根（`findProjectRoot`，`packages/context/agent-instructions/src/index.ts:125`，从 CWD 向上定位第一个项目根），在 `agent/pre-step` 时把项目根起沿目录链加载的 `AGENTS.md` 内容注入模型（`:322`）。它回答"这个项目的规矩是什么"。与第 2 章 Context 注入口不同，它注入的是**指令文本**，随提示词进入模型视野，不写会话事件。

### 14.6.2 time-context：现在几点

**① 类比**：会议室挂钟——模型自己不看表，得有人把时间念给它听。

**② 精确定义**：time-context 在 `agent/pre-step` 注入当前时间信息（`packages/context/time-context/src/index.ts:170`），格式用时区化的 `Intl.DateTimeFormat`（`:115`）与 `formatDuration`（`:41`，把"10 秒前"算成可读时长）。去重语义很细：**同一轮内不重复注入**——注入前先在开放轮次里倒查本插件最近的注入事件（`precedingStepContextTime`，`:75-89`），存在即跳过；跨轮则按最近一次注入与最小注入间隔去重（`latestInjectionTime`，`:92-95`）。一个轮次里多次工具调用不会导致时间戳刷屏。它解释"为何 `git log --since='5 minutes ago'` 这类查询是合理的"——模型真的知道当下。

### 14.6.3 tmux-context：我在哪个终端

**① 类比**：给模型一张"工位铭牌"——但这块铭牌**只有你真坐在工位上才贴**。

**② 精确定义**：tmux-context 通过 `tmux display-message` 读取当前窗格与会话信息（`packages/context/tmux-context/src/index.ts:7-14`，实际执行见 `:118-120`）注入上下文。边界条件写在注释里：**仅继承了 `$TMUX` 环境变量不算在 tmux 里**（`:87-88`——例如 VS Code 集成终端也会继承它）——必须确实运行在 tmux 会话中才注入，避免"套壳环境"骗过检测。它让模型能说"你在窗格 0：dashboard"而不是被动猜。

### 14.6.4 session-reference：会话引用

**① 类比**：会议纪要里"详见 3 月项目会记录"的链接——但**只允许链接到直接相关的几份**，且不展开全文。

**② 精确定义**：session-reference 用 `dsh-session:` URI 在上下文中引用其他会话（`packages/context/session-reference/README.md`），`maxReferences` 默认上限 3，**防递归**（A 引 B、B 引 A 不会死循环），且**只投影**直接的用户、助手消息与压缩检查点——工具结果等噪音不进投影。它解决"上次那个会话我调研过 X"，同时克制地避免引用膨胀。

### 14.6.5 最小示例

```markdown
# 项目 `deepseek-harness` 的 AGENTS.md（节选）
- 构建：pnpm build；测试：pnpm test
- 修改源码前先读 docs/development.md
- 提交信息用 <type>(<scope>): <subject> 格式
```

模型每轮开跑前的上下文里多了以上四块，于是它能问出"现在 14:03，5 分钟前还改过 `time-context`"这类时间-空间自洽的问题。

**接入点小结**：全部挂在 `agent/pre-step`（及同一事件派生的注入点）。**动了谁**：模型上下文（system/instruction 注入），不写会话事件、不写文件。

## 14.7 收尾三件套：commands、feedback、goal（概览）

治理长会话还有三个与"人"交互的部件，本章只做概览（接入点见 `packages/interaction/commands/src/index.ts:23`、`packages/feedback/command-feedback/src/index.ts:16`、`packages/goal/goal/src/index.ts:183`）：

- **commands**：把用户输入的命令文本结构化为 `command/run` 事件（插件注册 `commands` 服务并与之配对），是 `/plan`、`/compact`、`/feedback` 等命令路由的基础设施；
- **feedback**：`/feedback` 命令把用户的评价记录为 `feedback/record` 事件（**仅日志**，不干预流程），供后续回放与评测使用；
- **goal**：`GoalService` 承载"用户给 agent 设定一个目标"：`goal/change` 事件记录目标变更，**revision 栅栏**保证旧目标不会覆盖新目标；目标**激活不持久化**（重启后不自动恢复）；`defaultMaxGoalRounds`（默认 256）给目标驱动的自主轮次设**封顶**——目标在，跑道有尽头。

三者共同点：都是"人把意图写进日志"的通道，与 14.2–14.6 的自动化治理形成对照——自动治理管的是"会话自身的健康"，这三件套管的是"会话与人的约定"。

## 14.8 小结

回到表 14-1 的问题清单，本章的治理手段可以收束为三条设计主线：

1. **log-only 事件 + 唯一表面变更**：`compaction/start…end`、`plan/mode`、`todo/write`、`feedback/record` 都是仅日志事件；对模型可见性的改变（compaction 的替换、plan 状态的折叠、todo 的投影）各自只经**一条**受控通道，原始日志永远可重放、可审计（第 8 章的事件流模型是这一切的地基）。
2. **软约束与硬约束分离**：plan-mode 是"软引导"（安全边界在沙盒与审批，二者不读 plan 状态）；repeat-tool-reminder 是"建议"（只进上下文、不拦调用）；timeout-policy 才是"强制"（动执行信号、给结构化错误码）。判断一个治理手段的力度，看它**动了谁**。
3. **状态从日志折叠、随时可恢复**：`foldPlanMode` 从事件流折叠出计划状态，todo 投影从 `todo/write` 折叠出清单，压缩检查点从 `compactCheckpointSource` 识别——没有一样依赖内存里的"当前值"，全是纯重放量。

## 分层练习

**理解**：1. 对照五步 surface 契约，说明"为什么 `compaction/end` 必须是最后一个事件、崩溃后如何检测孤儿锁"（`packages/compaction/compaction/README.md`）。2. 说出 `SurfaceEventType` 闭集包含哪三类事件，并解释 `compaction/summary` 为什么不能携带 `surfaceOp`（`packages/core/session/src/types.ts:343-346`）。3. 复述 plan-mode "soft guidance" 的含义，并说明 sandbox/approval 与 plan 状态为什么"不读不写"。

**应用**：4. 某长会话反复报 `CONTEXT_WINDOW_EXCEEDED`，请设计排查顺序：先看 `maxOverflowRetries`、再看 `thresholdRatio`，说明每一步依据哪条触发链（`packages/compaction/compaction-basic/src/index.ts:144-194`）。5. 配置 `allowParallelInProgress: false` 后，一次工具调用标记了两个 `in_progress`，请写出模型收到的完整错误文本，并解释为何日志层不检查活动计数（README Configuration 一节）。6. 给一条需要 90 秒的 `pnpm install` 工具声明 `timeoutMs` 并说明超时后模型的错误消息与错误码（`packages/guard/timeout-policy/src/index.ts:41-46`）。

**综合**：7. 设计一个"runbook"：用户在 `/plan` 模式下批准计划后，模型开始执行却中途连续调用 `read_file` 七次——画出 plan-mode、todo_write、repeat-tool-reminder、timeout-policy 四者各自在这个场景中做了什么、没做什么，并指出谁负责把用户"方向错了"的反馈传回模型。8. 讨论压缩发生在 plan 评审期间会怎样（提示：`foldPlanMode` 从日志折叠、压缩是表面替换）：计划状态会丢失吗？给出你的推理与依据。

**挑战**：9. 阅读 `packages/compaction/compaction/src/tool-pairing.ts` 的 `toolPairingBalancedBefore/After` 与 `packages/compaction/compaction-basic/src/region.ts:98-118`，论证"压缩边界必须避开未配对的工具调用"与"保留最近尾巴"两条规则如何共同保证压缩后模型仍能继续对话（提示：`deriveMessages()` 的渲染顺序）。10. 对比"todo 投影在 `turn/start` 清空"与"goal 激活不持久化"，从"跨轮状态的生命周期"角度论述二者设计取向的异同（哪个是每轮重置、哪个是会话级重置，各自防止什么问题）。
