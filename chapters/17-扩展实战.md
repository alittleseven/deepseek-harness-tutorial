# 第 17 章　扩展实战：从 0 到 1 编写一个自己的插件

> **本章学习目标**（读完本章，你应该能够）：
> 1. 说清 dsh 的"可编程扩展点"全景：配置文件、动态插件、hooks 桥、preset 四条路径各自的编写者、生效时机与信任等级；

## 17.1 全景：除了一张 cordis.yml，你还有三条路

前十六章里，我们扩展 dsh 的方式始终是"改配置"：写一行 Entry、叠一层 patch、加一个 bundle。配置是**声明式**的——你描述"要什么"，系统在启动时把它变成活插件（第 5 章）。但有一类需求配置表达不了：*我的产品要一个带审计的只读文件工具，它得在每次工具调用发生时把一条记录写进日志*。这需要**代码**。本章就把 dsh 给代码编写者的全部入口摊开，然后亲手写一个。

先给全景。除配置文件外，dsh 提供三条"写代码"的路径：

| 扩展路径 | 编写者 | 生效时机 | 本质 | 本章出处 |
|---|---|---|---|---|
| **动态插件** | 模型（经六动词工具） | 对话中，即时 | 在宿主进程的 vm 沙箱里求值宿主代码，以 cordis 插件挂进运行时 | 17.2 |
| **hooks 桥** | 你（写脚本） | 每次命中事件时 | 把 Claude Code / Codex 的 hook 协议翻译成内部事件 | 17.3 |
| **preset** | 你（写组合文件） | 会话创建时 | 能力套餐：工具 + 提示段 + 运行时配置的一次性挂载 | 17.4 |
| 配置文件（对照） | 你（写 YAML） | 启动时 | 声明式插件树 | 第 5/6 章 |

三个词先混个脸熟：**动态插件（dynamic plugin）**、"**桥（bridge）**"与"**预设（preset）**"——本节之后的三小节分别用三步法讲透它们。此刻只需记住一句判断：**路径越是"让代码跑起来"，信任要求越高**。配置行是声明；动态插件则是把一段任意 JS 放进宿主进程——它到底能碰到什么、护栏在哪里，是 17.2.3 的主题。

## 17.2 动态插件：模型在对话里写插件

### 17.2.1 三步认识"动态插件"

**① 类比：带操作台的沙盘车间。** 想象一个车间：墙上挂着车间目录（有哪些机器、每台机器什么接口），操作台上有"登记台"与"启动按钮"，还有一只透明罩（把工人和机器隔开）。模型就是那位工人——它不能直接搬动机器，只能：查目录 → 在登记台交一份"我要装一台新机器"的图纸（机器代码）→ 按启动按钮 → 观察运行 → 关机或拆走。图纸登记时**不运转**，按了按钮机器才活。

**② 精确定义。** > **动态插件（dynamic plugin）**：由模型通过 Cordis 工具集提交代码、在宿主进程内用 `node:vm` 沙箱求值、以 cordis 插件形态临时挂载的扩展单元。它有稳定的 `pluginId`（进程内唯一）、不可变的 `packageId`（每次提交是一个新包），生命周期为 **inspect → define → run → stop / undefine**。宿主侧代码（host half）在宿主进程的沙箱里跑，浏览器侧代码（client half）在客户端沙箱里跑；本章只见宿主侧。

机械细节：`pluginId` 由 `mintPluginId` 生成，格式是 `<语义前缀>-<序号>`（`packages/extensions/cordis-host-runner/src/registry.ts:154-159`，如 `audit-0`；`packages/extensions/tool-cordis/README.md:12` 抽象地写作 `dyn-<n>`，正文以源码为准）；`packageId` 是 `pkg-<序号>`（`packages/extensions/cordis-host-runner/src/registry.ts:165-167`）。

**③ 最小示例。** 下面是 `cordis_define` 的一次调用（参数形状按 `packages/extensions/tool-cordis/src/index.ts:149-236` 的 schema 转述，非逐字摘录）：

```json
{ "plugin": { "kind": "new", "idPrefix": "hello" },
  "name": "say hello", "purpose": "print on activation",
  "code": { "host": "console.log('hi from host')" } }
```

返回 `{ pluginId: "hello-0", packageId: "pkg-0" }`——注意此时**什么都没运行**；随后 `cordis_run` 传入这对 id 才激活。一个插件（`hello-0`）可以有多代包（`pkg-0`、`pkg-1`……），激活哪一代由 run 的参数决定，这保证"换代码"在语义上是**追加**而不是就地修改。

### 17.2.2 六动词逐一核对

检索这套工具集的注册代码（`packages/extensions/tool-cordis/src/index.ts`），`inject = ['tools', 'systemPrompt', 'dynamicCordisRunner', 'cordisInspect']`（`:27`）——它自己就是三个普通插件：工具、提示段和运行器服务的消费方。六个动词分两类：

**只读三动词（inspect 族）**——只查不改：

| 动词 | 注册行 | 执行体 | 作用 |
|---|---|---|---|
| `cordis_inspect_list` | `packages/extensions/tool-cordis/src/index.ts:42` | `:54` | 列出全部 provider 及其只读方法、输入输出 schema；描述里明确告诫"不要猜名字，也别把 inspect 方法当业务服务调用"（`:45-47`） |
| `cordis_inspect_query` | `packages/extensions/tool-cordis/src/index.ts:61` | `:82-92` | 按 provider+method 查询具体方法 schema，供 define 前确认参数形状 |
| `cordis_inspect_self` | `packages/extensions/tool-cordis/src/index.ts:97` | `:113-144` | 自省：列出当前已定义的插件、各自的活动包与状态（含 `packageId` 时要求 `pluginId`，`:116`） |

**写三动词**——define 与 run 分离，stop 与 undefine 分离：

| 动词 | 注册行 | 执行体 | 行为要点 |
|---|---|---|---|
| `cordis_define` | `packages/extensions/tool-cordis/src/index.ts:149` | `:217-236` | 只登记：`name`、`purpose`、`code.host/client` 两半分别**语法预检（precheck）**后入库。执行体返回 `pluginId/packageId` 并渲染"尚未运行，请用 cordis_run 激活"（`:219-222`）；README 复述同一契约："Nothing runs; the user sees a card"（`packages/extensions/tool-cordis/README.md:12`） |
| `cordis_run` | `packages/extensions/tool-cordis/src/index.ts:241` | `:287-325` | 激活一个包。宿主侧实现见 `packages/extensions/cordis-host-runner/src/index.ts:248-312`：先 `resolvePlan`；同一插件已有待决请求时直接返回 `transition-in-flight`（**单飞**，`:264`）；需要审批则进入 `awaiting-approval` 并发出 `cordis/request-run` 事件（`:291`），由 UI 卡片裁决后才真正启动 |
| `cordis_stop` | `packages/extensions/tool-cordis/src/index.ts:330` | `:343` | 暂停运行（可再 run）；实现层强调幂等——"not running" 不算错误（`packages/extensions/cordis-host-runner/src/index.ts:456-479`，停止前的单飞检查 `:459`） |
| `cordis_undefine` | `packages/extensions/tool-cordis/src/index.ts:352` | `:373` | 永久移除：先停后删 |

**激活时的宿主侧动作**（`packages/extensions/cordis-host-runner/src/index.ts`）：`startHost`（`:883`）里 `createSandbox`（`:898`）→ `evaluateHostCode`（`:899`，携带配置默认 **5000ms** 的 `vmTimeoutMs`，`:128`）→ 成功后 `commitActivation`（`:981-992`）把新 fiber 挂进上下文树；`runResponse`（`:994-1008`）负责把结果回写。加载失败则回滚，且正在运行的**旧包不停**——这就是第 3 章 fiber 语义在动态场景的应用：激活是一次新的 fiber 加载，失败只影响新 fiber。

**自省桥接**：`cordis_inspect_self` 需要的"哪个插件引用了当前消息流"由 `referencedPluginIds` 从最近消息里抽取（`packages/extensions/tool-cordis/src/index.ts:497-506`），并在 `agent/pre-step` 钩子（`:381-398`）把 `@pluginId` 注入执行上下文——模型不必记住 id，插件 id 是"按引用可达"的。这一整套与第 9 章的轮次结构紧密咬合。

### 17.2.3 宿主侧的护栏，以及"安全边界 = 无"

动态插件代码在沙箱里运行，但沙箱里**有什么**直接决定它的力量。构造沙箱的白名单在 `packages/extensions/cordis-host-runner/src/sandbox.ts`：

```ts
// packages/extensions/cordis-host-runner/src/sandbox.ts:18-43（逐字摘录首尾）
export const HOST_BUILTIN_INSPECTION = [
  { name: 'ctx', … 'ctx.get(name): unknown | undefined; ctx.on(name, listener): () => void;
           ctx.provide(name, value): () => void; ctx.effect(callback): () => void' … },
  { name: 'harness', … 'harness.handle(method, handler); harness.defineTool(definition);
           harness.registerTool(ctx, tool)' … },
  { name: 'console', … }, { name: 'btoa' … }, { name: 'atob' … },
  { name: 'TextEncoder', … }, { name: 'TextDecoder', … },
]
```

注意两件事：`ctx` 的四个方法（get/on/provide/effect）直接来自第 2 章容器；`harness.defineTool/registerTool` 让动态插件**注册模型可见的新工具**——这正是"扩展点"二字的分量。`NODE_API_REDIRECTS`（`packages/extensions/cordis-host-runner/src/sandbox.ts:96-108`）把 Node 全局改道：`require` → 抛错并提示改用 `ctx.fs/web/bash`，`setTimeout` → 定时器服务，`fetch` → `ctx.web`（`nodeApiTraps`，`:111-119`）。这层改道是"**引导**"而非"**阻断**"：`evaluateHostCode` 用 `runInContext(..., { timeout: vmTimeoutMs })` 包装 `(async () => { … })()`（`:227-238`），vm 的 `timeout` 只约束**同步段**，await 之后的异步逃逸（推断：依据 node:vm 语义，仓库未另行说明）。

更重要的护栏在 `packages/extensions/cordis-host-runner/src/guard.ts`：宿主把挂载的插件包进一个**白名单 façade**（文件头注释 `:1-8`），`guardedPlugin`（`:802`）对非白名单方法返回"不提供服务"。两个细节值得记住：façade 的 `set` 直接拒绝赋值——"façade 不是真 ctx，别往一次性对象上藏状态"（`:769-771`）；`in` 运算符反映**可达性**（声明的服务，无论当前是否存活）（`:773-774`），所以 `'fs' in ctx` 为真不等于 `ctx.fs` 可安全调用（要配 `get` 的空值检查，见 `HOST_BUILTIN_INSPECTION` 首行注释）。

**那么安全边界是什么？** 答案是：没有。官方信任声明写得很直白：

> "The sandbox isolates globals but is not a security boundary… Treat this toolset like bash access."（`packages/extensions/tool-cordis/README.md:21-23`）
> "The sandbox is containment for honest code, not a security boundary——宿主侧辅助器在沙箱全局上是可达的，代码能触达 Node。"（`packages/extensions/tool-cordis/README.md:102`）

白名单薄到只防"糊涂代码"，不防"恶意代码"。把动插件交给谁跑，等于把 bash 交给谁跑。于是全景的信任梯度可以排出来了：**配置文件 < preset < hooks 脚本 < 动态插件**——前两者你写完才生效；hook 脚本每次由你控制命令；动态插件则让**模型**即时决定执行什么。用哪条路，先问自己"写它的人值不值得这份信任"。

## 17.3 hooks 桥：把别人的钩子协议翻译成内部事件

### 17.3.1 三步认识"桥"

**① 类比：口译员。** 你雇了一位只说法语的员工（dsh 的扩展点），来了一批只说英语的访客（你已有的 Claude Code / Codex hook 配置）。口译员（桥插件）不创造新业务，只做两件事：把访客的句子（`hooks.json`/`settings.json` 中的命令）翻译成法语请求，把员工的回答翻译回英语。访客说的法语单词（原生插件）完全不用翻译——桥只是"**兼容路径**"。

**② 精确定义。** > **桥（bridge）**：一个把外部世界的钩子协议（hook protocol）映射到宿主内部拦截点（interception points）的插件。协议公共部分抽成共享库 **hook-protocol**——它"**不是 cordis 插件**：不注册任何东西、不注入任何东西，是一堆方言无关原语的**库**"（`packages/hooks/hook-protocol/README.md:5`）。桥负责的是两个方言：`hooks-claude-code` 与 `hooks-codex`。

**③ 最小落地。** 一次命中分四步（对照 `packages/hooks/hook-protocol/README.md:14-18` 的共享/方言分工表）：① 桥按方言构造 stdin 载荷与 env；② `runHook(bash, hook, opts, now)` 经 `ctx.shell` 执行命令（`:14`）；③ `parseHookOutput` 把退出码/输出解码为中性 `HookOutput`（`packages/hooks/hook-protocol/src/codec.ts:65-67`："两种方言都把 exit 2 视为 block，stderr 作为理由"）；④ `mergeHookOutputs` 合并多钩子决定（`:16`）。记录：`appendHookInvoked`（`packages/hooks/hook-protocol/src/events.ts:75`）与 `appendHookResult`（`packages/hooks/hook-protocol/src/events.ts:92`）以 `hook/invoked`、`hook/result` 会话事件落盘，stderr 摘要有 500 字符上限（`packages/hooks/hook-protocol/src/events.ts:53`）。

### 17.3.2 runHook 永不 throw，merge 取最严格

桥的健壮性契约是两句话。第一句在 `packages/hooks/hook-protocol/src/runner.ts`：

```ts
// packages/hooks/hook-protocol/src/runner.ts:96-100（逐字摘录）
} catch (error: unknown) {
  // The executor rejects only on infrastructure faults (unusable workdir,
  // missing shell). A hook that cannot run is a non-blocking error: no exit
  // code, the failure on stderr for the record. The turn proceeds.
  const message = error instanceof Error ? error.message : String(error)
  return { output: parseHookOutput(undefined, '', message), … }
```

`runHook`（`packages/hooks/hook-protocol/src/runner.ts:67`）签名上是 `Promise<HookResult>`——**外部没有失败态**：基础设施故障变成 `exitCode: undefined` 的非阻塞错误，轮次继续；超时默认 10 分钟（`DEFAULT_HOOK_TIMEOUT_MS = 600_000`，`:20`，桥配置可改默认，见 `packages/hooks/hooks-claude-code/src/index.ts:76`）。第二句在 `merge.ts`：头注释即规范——"`deny > ask > allow`；第一个 `continue:false` 是粘滞的；理由以 `\n\n` 连接"（`packages/hooks/hook-protocol/src/merge.ts:3-6`）。实现是给每种决策打分（`deny/block=3, ask=2, approve/allow=1`，`:37-50`），取最高分者的理由入选（`:91-94`）。于是"多个钩子"的语义是**最严格者胜**，而不是"少数服从多数"。

### 17.3.3 两个桥，和"为什么要有桥"

`hooks-codex` 实现的是 Codex 的**刻意子集**：十个钩子点只做五个（PreToolUse、PostToolUse、SessionStart、UserPromptSubmit、Stop）；匹配器**只用正则**（`packages/hooks/hooks-codex/src/index.ts:130`，"Codex 总是把 matcher 当正则，没有字面量快路径"）；stdin 载荷 snake_case 且无尾换行；**没有**预工具审批/改写路径——PreToolUse 只能 deny（`:224-229`）（见 `packages/hooks/hooks-codex/README.md:5-11`）。`hooks-claude-code` 则更接近完整方言（`configPath/pluginRoot/projectDir` 配置，`packages/hooks/hooks-claude-code/src/index.ts:53-77`）。

两桥 README 的定位句一字不差地给出了设计判断：

> "A native cordis plugin could do everything this bridge does — more powerfully, with typed returns and no serialization boundary. **The bridge exists only as a compatibility path**…"（`packages/hooks/hooks-claude-code/README.md:7`；`packages/hooks/hooks-codex/README.md:15` 同义）

结论很明确：**桥是为"已有外部钩子资产"准备的过渡路径**；要从零扩展 dsh，直接写原生插件（本章的主角）——它没有序列化边界、返回类型安全、能同时做工具 + 提示段 + 监听器。

## 17.4 preset：能力套餐，一次挂载处处加入

### 17.4.1 三步认识"preset"

**① 类比：主题皮肤与能力套餐。** 开机时系统自动安装的"标准办公包"：它不是每次会话现装，而是装一次（驻留），之后每个新会话"加入"它，看到同一批软件与壁纸。你换套装（recompose），新会话用新套装；已经开工的会话维持原样——因为**换工具会让学生（模型）之前领到的作业变废**。

**② 精确定义。** > **预设（preset，配置档案/能力套餐）**：一个目录，内含组合文件 `agent.cordis.yml`（+元数据）。组合文件就是一张 patch 式入口清单（`packages/preset/agent-presets/src/discovery.ts:26` 定义文件名 `COMPOSITION_FILE = 'agent.cordis.yml'`；用户自建目录默认 `.agent-presets`，`:41`）。预设由 roster 服务**每进程一次性挂载**到 standing 作用域："a **preset** is a directory holding one `agent.cordis.yml`; the roster mounts it **ONCE per process** under a standing scope, and each session that names it joins by having its agent scope key parented to the mount's"（`packages/preset/agent-presets/README.md:5`）。加入的机制是作用域父链，因此视图解析序是 **agent → preset → global**（近者遮蔽远者，`packages/preset/agent-presets/README.md:7`）。

**③ 最小示例。** 直接看仓库里被第 7 章 7.4.2 走读过的 standard 组合文件（测试夹具，源码逐字）：

```yaml
# packages/preset/agent-presets/tests/fixtures/system/standard/agent.cordis.yml:1-12
# Shipped preset: one tool plus its guidance section.
- id: alpha
  name: ../../plugins/contribute.js
  config:
    tool: alpha

# A row switched off in the composition stays off without failing the mount.
- id: alpha-extra
  name: ../../plugins/contribute.js
  disabled: true
  config:
    tool: alpha-extra
```

它和 5.2 节的 Entry 清单同构——preset 的组合文件就是"给一个 agent 准备的插件子树"。

### 17.4.2 preset 的两个动作、两个约束

**什么时候加入**：唯一受支持的调用点是 agent 工厂的 `setup(agentCtx)` 钩子——"只在 agent 还未公布时安装加入；组合被拒绝则整个创建回滚，不留半个组合会话"（`packages/preset/agent-presets/README.md:31`）。子代理不重新挂载自己的 preset，而是 **`composeFrom` 加入父代理所在组合**——"通过 `composeFrom()` 加入，绝不通过 `mount()`；每个模型可见的行都在 agent 平面，全局层是空的，未加入任何组合的子代理对模型**一个工具都没有**"（`packages/preset/agent-presets/README.md:35`）。实现上 `composeFrom` 是同步 bind（`packages/preset/agent-presets/src/index.ts:316-325`），`mount` 是单飞 ensure + bind（`:275-288`）。

**两个约束**（这是 preset 与"随便改插件"的根本差异）：

1. **只能切换"空白"代理**。`recompose`（`packages/preset/agent-presets/src/index.ts:458-472`）先把新 mount 确保成功、再移动父链绑定——失败则代理保持原样。但网关在线上强制：会话已有产出时，切换请求被拒绝为 `agent-preset-locked`（`packages/host/apiproxy/src/api-proxy.ts:3102-3104`；语义注释在 `packages/host/apiproxy/src/api/agent-presets.ts:62-69`，"swapping them would leave logged tool calls the new composition cannot make"）。产品规则而非机械限制：换工具会让已记录的工具调用变成新组合无法执行的历史。
2. **创作只有复制**。`copy()` 是包内唯一写操作：整目录复制现有 preset（组合、元数据、技能目录、资源）到第一个 user 根（`packages/preset/agent-presets/src/index.ts:380-393`）；**没有组合文本跨过这个接缝**，所以"复制品和源一样可加载"（`packages/preset/agent-presets/README.md:24`）。组合挂载后的 `write()` 是空操作——"nothing in this package writes a composition"（`packages/preset/agent-presets/src/mount.ts:110`，见 `packages/preset/agent-presets/README.md:131`）。

**preset 里能放什么**：插件行本身。最有代表性的是 persona——`packages/preset/persona/src/index.ts` 是"**scope-only**"插件（头注释 `:1-13`：只为所在作用域注册提示段；全局挂载会撞注册、fail loud），`apply`（`:60-67`）把 `text/complete/includeRuntimeContext`（Config，`:36-51`）注册成 `deployment:persona` 提示段（渲染序规则见 10.2）。在 preset 组合文件里加一行 `persona`，就等于给套餐配了主题皮肤。

**什么时候用 preset，什么时候写插件**：preset 解决"**给一批会话配同一套可见能力**"（工具集、提示段、运行时配置），且要能从日志重建（7.4 的"模型可见 ⟺ 已记录"）；插件解决"**新增一种能力本身**"。本章的审计工具是能力本身，所以走插件路线；如果你要为每类项目配不同工具集，才轮到 preset。

## 17.5 立项：三选一

写一个扩展之前，先回答"我要的到底是什么"。按需求形态三选一：

| 我想要…… | 扩展形态 | 生效点 | 为什么 |
|---|---|---|---|
| 一种**新能力**（新工具、新提供方、新服务） | 插件 + 工具/service | 每次调用 | 工具是模型唯一的行为出口（第 11 章） |
| 一组**对现有能力的裁剪/补强**（观察、限制、改写） | 插件 + 监听器/拦截 | 每步/每次调用 | 事件与 waterfall 是框架的开放接缝（4.7/4.10） |
| 给**一批会话**配同样能力 | preset | 会话创建 | 一次挂载、处处加入（17.4） |
| **兼容已有外部配置** | hooks 桥 | 每点命中 | 兼容路径，非首选（17.3.3） |

**本节立项：`dsh-audit-cat`——带审计的只读文件工具。** 需求清单（都来自本书已学机制）：

1. 工具 `audit_cat`：读取一个文件，返回路径、大小、内容——只读，不碰写；（工具形态，11.2）
2. 审计：每次 `tool/call` 与 `tool/result` 发生时向 `<auditDir>/<sessionId>.log` 追加一行；（监听器形态，4.7）
3. 给模型一段使用指引；（提示段形态，10.2）
4. 审计器以"服务"形式暴露给同插件其他代码。（服务形态，2.2）

三合一的好处：四个机制（工具、事件、提示段、服务）各用一次，正好把 17.1 表格的"插件"一行演示完整。项目三件套：`src/index.ts`、`cordis.patch.yml`、`tests/audit-cat.spec.ts`。

## 17.6 写代码：dsh-audit-cat 逐段走读

> 本节代码为**本章示例**（自写），非仓库源码；每个 API 调用都在括号里标注所依据的仓库源码位置。完整项目文件：

```
dsh-audit-cat/
├── src/index.ts            # 插件本体
├── cordis.patch.yml        # 开发期挂载（17.7.1）
├── package.json            # 分发期打包（17.7.2）
└── tests/audit-cat.spec.ts # vitest 用例（17.8）
```

```ts
// dsh-audit-cat/src/index.ts —— 示例插件：只读文件工具 + 会话事件审计
import { join } from 'node:path'
import { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'   // 11.2：defineTool 与 ToolDefinition

export const name = 'audit-cat'
// 依赖注入：fs（12.2 的 seam 词汇层）、tools（注册工具）、systemPrompt（提示段）
export const inject = ['fs', 'tools', 'systemPrompt'] as const

export interface AuditCatConfig {
  /** 审计日志目录；缺省为会话工作目录下的 .dsh/ */
  auditDir?: string
}

export function apply(ctx: Context, config: AuditCatConfig = {}) {
  const auditDir = config.auditDir ?? '.dsh'

  // ---- ① 服务：闭包实现的 auditTrail，用 provide 挂到 ctx ----
  const calls = new Map<string, { sessionId: string; name: string }>()
  const trail = {
    recordCall: (sessionId: string, callId: string, name: string) => calls.set(callId, { sessionId, name }),
    async recordResult(sessionId: string, callId: string, isError: boolean) {
      const call = calls.get(callId)
      if (!call || call.sessionId !== sessionId) return   // 跨会话/未知 callId 一律忽略
      const line = `${new Date().toISOString()} ${call.name} ${isError ? 'ERROR' : 'ok'}\n`
      const target = await ctx.fs.resolve(join(auditDir, `${sessionId}.log`), { cwd: sessionCwd })
      let prior = ''
      try { prior = await ctx.fs.readText(target) } catch { /* 首次写入，文件不存在 */ }
      await ctx.fs.writeText(target, prior + line)          // 读-拼接-写；见 17.9 第 5 坑
      calls.delete(callId)
    },
  }
  // provide 返回 disposer；包进 effect 后随插件卸载自动撤销（2.3.2 / 3.3）
  ctx.effect(() => ctx.provide('auditTrail', trail), 'audit-cat.provide')

  // ---- ② 提示段：让模型知道有这个工具（10.2：section 的 name/order/text） ----
  ctx.effect(() => ctx.systemPrompt.section({
    name: 'audit-cat.guidance',
    order: 120,   // 约定：工具指引用 100-199（packages/core/system-prompt/src/index.ts:58-59）
    text: 'audit_cat is a read-only tool: it prints a file\'s path, size and content, '
        + 'and every call is recorded in the session audit log.',
  }), 'audit-cat.section')

  // ---- ③ 工具：audit_cat ----
  ctx.effect(() => ctx.tools.register(defineTool({
    name: 'audit_cat',
    description: 'Read a file and return its path, size and content. Read-only; call is audited.',
    parameters: {
      file_path: { type: 'string', required: true, description: 'Path relative to the session cwd.' },
      max_bytes: { type: 'number', required: false, description: 'Read at most this many bytes (default 4096).' },
    },
    output: {
      schema: { type: 'json' },
      render: (_args, value) => [{ type: 'text', text: JSON.stringify(value, null, 2) }],
    },
    isConcurrencySafe: () => true,          // 只读工具允许并行（schema.ts:594-615 的软验证）
    async execute(args, exec) {
      // 关键：解析基准是会话 cwd，不是 process.cwd()（见 17.9 第 5 坑）
      const cwd = exec.agent?.session.header.cwd ?? '.'   // SessionHeader.cwd，types.ts:61-98
      const target = await ctx.fs.resolve(args.file_path, { cwd })       // fs/index.ts:116
      const info = await ctx.fs.stat(target)                               // fs/index.ts:152
      const content = await ctx.fs.readText(target)                        // fs/index.ts:176
      const bounded = args.max_bytes !== undefined ? content.slice(0, args.max_bytes) : content
      const result = { path: target.targetKey, size: info.size, content: bounded }
      ctx.emit('fs/observed', target, { kind: 'present', version: info.version }, exec)
      return result
    },
  })), 'audit-cat.tool')

  // ---- ④ 监听器：会话事件 → 审计（4.7：注册即 effect；4.10：session/event 作用域到会话） ----
  ctx.effect(() => ctx.on('session/event', (session, event) => {
    // 事件形状见 agent-loop/tool-calls.ts:262-292 与 llm/message.ts:279
    if (event.type === 'tool/call') {
      trail.recordCall(session.id, event.data.callId, event.data.name)
    } else if (event.type === 'tool/result') {
      const isError = event.data.message.content[0]?.type === 'error'   // 防御式读取
      void trail.recordResult(session.id, event.data.callId, Boolean(isError))
    }
  }), 'audit-cat.audit')
}
```

**逐段走读**（对照仓库里同构的官方实现）：

**① 注入与插件头**。`name/inject` 与 `tool-fs` 完全同构（`packages/fs/tool-fs/src/index.ts:21-23`）。这里 `inject` 写全依赖：没有 `fs` 就没有文件能力；没有 `systemPrompt` 就注册不了段。注意 `apply` 里我们**没有** `declare module` 扩充 `Context`——想获得类型化 `ctx.auditTrail`，需要按 12.12 的方式声明（`declare module '@deepseek-ai/cordis' { interface Context { auditTrail: … } }`），示例为了短小用闭包 `trail` 直接传递，这是**取舍**不是漏写：对外可见的服务才值得配声明。

**② 服务 = 闭包 + `provide`**。`ctx.provide` 返回 disposer（2.3.2），把它包进 `ctx.effect` 后，插件 fiber 卸载时自动撤销——这正是"监听器/服务注册即 effect"（4.7）的又一处体现。`calls` 用 `Map<callId, …>`：`tool/call` 先记，`tool/result` 再查——事件对天然成对（`packages/core/agent-loop/src/tool-calls.ts:262-267` 写 call，`packages/core/agent-loop/src/tool-calls.ts:269-289` 写 result，两者都含 `turn/step/callId`，见 `packages/core/session/src/types.ts:279` 的 `'tool/call'` 映射）。`recordResult` 里 `call.sessionId !== sessionId` 的防御：`session/event` 是**带作用域**的事件（4.10），监听器只收到本会话的事件，这个检查是免检的（留作注释性防御，不产生成本）。

**③ 提示段**。`systemPrompt.section({ name, order, text })` 的字段来自 `packages/core/system-prompt/src/index.ts:53-68`；`order: 120` 遵循文件内注释"工具指引用 100–199"（`:58-59`）。段文本在每次组装时求值（10.4 的 assemble），模型每轮都能看到（见 17.9 第 2 坑的边界）。

**④ 工具**。`defineTool` 的参数（`packages/core/tools/src/schema.ts:483-535`），返回 `ToolDefinition`；`render` 是纯函数（`:545-617` 里 `output.render`）；`isConcurrencySafe: () => true` 走的是软验证路径——参数不合法时返回 `false` 而非抛错（`:594-615`）；**参数校验**由 defineTool 包在 `execute` 外层（`:585-588`，不合法抛 `ToolArgsError`），所以我们的 `execute` 里拿到的 `args` 已通过 schema。`ctx.fs.resolve(path, { cwd })` 是 seam 词汇层 API（`packages/fs/fs/src/index.ts:116`），返回 `FsTarget`（`targetKey` 是同一文件同一键，`:114-121`）；`stat`（`:152`）、`readText`（`:176`）都接受 signal 取消。`fs/observed` 的 emit 模仿了 `packages/fs/tool-fs/src/read.ts:160-162`——只读工具也可以发布观察事件，让策略层记录"这份文件被模型看过"（12.2.3 的事件层解耦）。

**⑤ 监听器**。`ctx.on('session/event', …)` 的声明在 `packages/core/session/src/index.ts:76`（`Scoped<Session>`，事件带会话作用域）；分发在 `session.append` 里按作用域收集回调（`:641-646`）。`event.data.message.content[0]?.type === 'error'`——`tool/result` 的负载里 `message` 是 `createToolResultMessage` 造的（`packages/llm/llm/src/message.ts:231-245`），`content` 是块数组；取 `isError` 必须防御式读取（可能为空数组）。

**性能注记**：`recordResult` 的读-拼-写使第 n 次写入成本 O(n)，整个会话 O(n²)。示例换取"实现最短"；工程版应改用 append 语义或队列批量落盘（见 17.11 综合题）。

## 17.7 挂载：一处 patch，三种装法

### 17.7.1 开发期：`--patch` overlay

和第 5 章 5.4.4 一样，插件行就是 patch 条目（`packages/bundle/base/cordis.patch.yml:1-13` 的头注释再次确认语义："A patch replaces the targeted row's whole `config` rather than merging into it；last write wins per row"，`5.4.3` 已讲）：

```yaml
# dsh-audit-cat/cordis.patch.yml —— 本章示例
- insert:
    - id: audit-cat
      name: /abs/path/to/dsh-audit-cat/src/index.ts    # 绝对路径！见下文
```

关键约束在官方文档里："**插件路径必须是绝对路径**。patch 文件只贡献配置，不会改变 loader 解析模块路径时使用的 profile 目录"（`docs/user/develop/basic/index.zh.md:56`）。启动命令：

```sh
pnpm dsh web --patch ./dsh-audit-cat/cordis.patch.yml
```

`--patch` 在 CLI 是可重复单值收集（`apps/cli/src/args.ts:51-61`，帮助示例 `:68`），多个 overlay 按 argv 顺序叠在 profile 层之上（`:84-102` 的 `resolveBoot`；与 `--dump-config` 互斥，`:89-100`）。

### 17.7.2 分发期：打成包，用 `dsh plugin` 装

把插件发布为 npm 包并在 profile 上登记（官方流程 `docs/user/develop/basic/publish.zh.md`）：`package.json` 声明入口与 `dsh` 字段。

```json
{ "name": "dsh-audit-cat", "version": "0.1.0",
  "main": "src/index.ts", "files": ["src"],
  "dsh": { "bundle": { "patch": "cordis.patch.yml" } } }
```

patch 里按**包名**而非源码路径引用："插件行按包名而不是相对源码路径引用这个包，这样 Node 的模块解析才能找到已安装的代码"（`docs/user/develop/basic/publish.zh.md:56` 段）。然后：

```sh
dsh plugin --profile demo add ./dsh-audit-cat
```

**叠层归属**（第 6 章 6.5 的补丁栈总图，官方一句话版）："each bundle in the profile's listed order, then the profile's `cordis.patch.yml`, then the home-level one, then any `--patch` overlay"（`docs/architecture.md:27`）。我们的插件行无论走哪条路，最终落在 user/patch 层，处于 bundle 之上——**bundle 之上永远还能 patch**（7.6）。

### 17.7.3 轮次里验证

启动 `dsh` 后对模型说"用 audit_cat 读一下 README.md"。预期三件事：① 工具出现在可用列表（`ToolRuntime` 构造时通过 `ctx.systemPrompt.tools` 接线每步装配，`packages/core/tools/src/index.ts:832`）；② 一条 `tool/call` + 一条 `tool/result`（`packages/core/agent-loop/src/tool-calls.ts:262-289`）；③ 会话目录 `.dsh/<sessionId>.log` 里出现两行：`… audit_cat ok`。若第 2 步失败而第 3 步出现"ERROR"，说明读文件失败但审计生效——错误同样被记录，这是监听器形态天然的好处。

## 17.8 测试：仿仓库的 FakeFs 范式

仓库自测工具插件的写法在 `packages/fs/tool-fs/tests/tools.spec.ts`：一个**内存文件系统假件**（`class FakeFs extends FileSystem`，`:38`，覆写 `resolve/stat/readText/writeText` 等，全量存 `Map`）；`setup()` 用 `new Context()` 依次 `await ctx.plugin(...)` 排列 SystemPrompt、ToolRuntime、FakeFs、策略与待测插件（`:102-108`）；辅助函数 `call(ctx, name, args)` 直接调 `ctx.tools.execute`（`:113-118`），`text()` 取文本块（`:123-125`）。**没有 mock 框架、没有网络**——因为工具就是纯函数式流水线（11.6 的 dispatch 是瀑布不依赖载体）。

我们的用例（示例代码，写法照抄仓库）：

```ts
// dsh-audit-cat/tests/audit-cat.spec.ts —— 本章示例（未验证：未在本机运行）
import { FileSystem } from '@deepseek-ai/dsh-fs'
import { SystemPrompt } from '@deepseek-ai/dsh-system-prompt'
import { ToolRuntime } from '@deepseek-ai/dsh-tools'
import { apply as auditCat, name } from '../src/index.ts'
import { Context } from '@deepseek-ai/cordis'
// FakeFs 精简自 packages/fs/tool-fs/tests/tools.spec.ts:38-100
class FakeFs extends FileSystem {
  files = new Map<string, { content: string; size: number }>()
  async resolve(path: string, opts?: { cwd?: string }) { return { targetKey: `${opts?.cwd ?? ''}/${path}`, version: 'v1' } as never }
  async stat() { return { size: 1 } as never }
  async readText(t: { targetKey: string }) { return this.files.get(t.targetKey)?.content ?? '' }
  async writeText(t: { targetKey: string }, content: string) { this.files.set(t.targetKey, { content, size: content.length }) }
}
async function setup() {
  const ctx = new Context()
  await ctx.plugin(SystemPrompt); await ctx.plugin(ToolRuntime)
  await ctx.plugin(FakeFs); await ctx.plugin({ name, apply: auditCat })
  return { ctx, fs: ctx.fs as FakeFs }
}
it('reads a file and returns path/size/content', async () => {
  const { ctx, fs } = await setup()
  fs.files.set('ws/README.md', { content: 'hello', size: 5 })
  const result = await ctx.tools.execute({ callId: 'c1', name: 'audit_cat',
    arguments: { file_path: 'README.md' }, agent: { id: 'a1' } as never })
  expect(result.content[0].text).toContain('hello')
})
it('records a tool/result into the session audit log', async () => {
  const { ctx, fs } = await setup()
  ctx.emit('session/event', { id: 's1', header: { cwd: 'ws' } } as never,
    { type: 'tool/call', data: { callId: 'c1', name: 'audit_cat' } } as never)
  ctx.emit('session/event', { id: 's1', header: { cwd: 'ws' } } as never,
    { type: 'tool/result', data: { callId: 'c1', message: { content: [{}] } } } as never)
  expect([...fs.files.keys()]).toContain('ws/.dsh/s1.log')
})
```

**用例解析**。用例 1 走工具正路：FakeFs 预置内容 → `ctx.tools.execute` → 断言返回文本包含 `hello`。用例 2 走事件正路：因为 `session/event` 是框架层面的事件（`packages/core/session/src/index.ts:76`），测试里用 `ctx.emit` 直接发——这同时验证了监听器注册与作用域（4.7：`ctx.on` 在插件 apply 后即生效）。两例合计覆盖了"服务（Map 记账）+ 工具（execute）+ 监听（emit）"三个接线点；若监听器没接上，用例 2 会断言失败——**这正是把监听器放进同一个测试文件的原因**。

## 17.9 踩坑实录：五个"我以为"与源码事实

**坑 1：监听器"突然失效"。** 现象：插件热更新后审计不写了。原因：`ctx.on` 的注册跟随**当前 fiber** 的生命周期（4.7："注册即 effect"；3.5 的注册 API 一律登记到当前作用域）。改代码时如果忘了把注册放进同一个 `apply`、或把它写在了别的 fiber 里，卸载即注销。查法：`cordis_inspect_self` 看插件状态；定位：3.6 的依赖串会连带卸载。

**坑 2：改了工具 schema，模型却还用旧描述。** 现象：加了 `max_bytes` 参数，模型一直传 `maxBytes`。原因有二：① 工具 schema 经 `ToolRuntime` 的 `view().visible` 投影进**每次**组装的消息（`packages/core/agent-loop/src/agent.ts:230` 每步 `systemPrompt.assemble`；`packages/core/system-prompt/src/index.ts:488-500` 收集 providers 并 `structuredClone` 参数），所以"新 schema 下一轮就见效"；② 但**当前轮**的工具列表已由本轮提示词定格，且历史上已记录的 `tool/call` 仍以旧参数形状校验（`packages/core/tools/src/schema.ts:585-588` 的 `validate` 抛 `ToolArgsError`）。结论：加参数要向后兼容，别改既有字段语义（11.2.2 的 schemaOf 白名单投影：模型只见 name/description/parameters 三分，`packages/core/tools/src/index.ts:1256-1266`）。

**坑 3：patch 改了没反应 / 热重载不覆盖。** 现象：`--patch` 指向的文件改了，进程纹丝不动（或反而"整行被替换"）。原因：patch 的语义是**整行替换不是合并**（`packages/bundle/base/cordis.patch.yml:1-13` 头注释；5.4.3），你只改 `config` 里一个字段，其他字段会被覆盖成默认；而**热重载只监视 profile 的 `cordis.patch.yml` 与 home 层补丁**（6.7 的 watchUserPatches），`--patch` overlay 递进来的文件不在监视清单里（推断：依 6.7 监视范围）。对策：开发期把插件行写进 profile 自己的 `cordis.patch.yml`，享受 HMR；分发 overlay 只用于临时叠层。

**坑 4：preset 切换被拒 `agent-preset-locked`。** 现象：想把已开始对话的会话换到新 preset，网关直接拒绝。原因：只允许"空白"代理切换（`packages/host/apiproxy/src/api-proxy.ts:3102-3104`；`recompose` 的实现 `packages/preset/agent-presets/src/index.ts:458-472`）；且**已产出会话永久保留它加入的那一代组合**（代际由组合文件 mtime+size 定，`packages/preset/agent-presets/README.md:31` 与 `packages/preset/agent-presets/src/index.ts:538-560` 的 stamp；超代不回收，`packages/preset/agent-presets/README.md:150`）。对策：换 preset 要在会话开始前；想改已产出会话的能力，去做 patch（6.7 热重载）而不是换 preset。

**坑 5：`process.cwd()` 是错的基准。** 现象：服务重启后审计文件跑到了别处。原因：工具执行时 `exec.agent.session.header.cwd` 才是会话的工作目录（`packages/core/session/src/types.ts:61-98`），官方工具层明确"把回退留给提供方，而不是在工具边界读 `process.cwd()`"（`packages/fs/tool-fs/src/session-cwd.ts:6-7`）；`sessionCwd`（`:23`）还处理 `..` 穿越的规范化。我们的示例 `resolve(…, { cwd })` 用的就是这个契约（12.2 的 seam：`resolve` 接受 `{ cwd, signal }`，`packages/fs/fs/src/index.ts:116`）。同理：**只要走 `ctx.fs`，就不该再直接碰 Node 文件 API**——那会绕过策略与沙箱（12.2.4/12.6）。

## 17.10 小结

1. 可编程扩展点有四条路：配置文件（声明式）、动态插件（模型写代码）、hooks 桥（翻译外部钩子）、preset（能力套餐）；**信任梯度：配置 < preset < hook 脚本 < 动态插件**。
2. 动态插件六动词：三个只读 inspect（list/query/self），写侧 define 只登记 + run 激活、stop 暂停、undefine 删除；包不可变、id 稳定（`<前缀>-<序号>`），宿主侧有 vmTimeoutMs（默认 5000ms）与白名单 façade，但**不是安全边界**——"像信任 bash 一样信任它"。
3. hooks 桥 = 共享原型库（hook-protocol，非插件）+ 两个方言桥（CC/Codex）；`runHook` 永不 throw（故障 = 非阻塞），`mergeHookOutputs` 最严格者胜（deny > ask > allow，首个 continue:false 粘滞）；桥只是兼容路径，原生插件更强。
4. preset = 目录 + `agent.cordis.yml`，standing 作用域**每进程挂载一次**，会话经作用域父链加入，视图序 agent → preset → global；只有 `setup()` 一个支持调用点、子代理用 `composeFrom`、只能切空白代理（网关 `agent-preset-locked`）、创作只复制、代际按 mtime+size、超代不回收。
5. 一个插件可以同时是"服务 + 工具 + 提示段 + 监听器"；四个接线点分别对应 provide（2.3）、defineTool（11.2）、section（10.2）、`ctx.on`（4.7），全部"注册即 effect"。
6. 测试范式：FakeFs 内存假件 + `new Context()` 排插件 + `ctx.tools.execute` 直调，无 mock、无网络；事件路径用 `ctx.emit` 直接驱动。
