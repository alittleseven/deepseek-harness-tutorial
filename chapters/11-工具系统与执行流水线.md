# 第 11 章　工具系统与执行流水线

> **本讲法**：本章属"数据流旅程"型。我们挑一次真实工具调用——一条 `tool/call` 日志从诞生到回填给模型的九站旅程——逐站下车看代码。旅程的高潮在"包装"：工具主体像被层层快递盒包起来的货物，超时、检查点都是盒子，而打开盒子只发生在 `tools/execute` 一站。两位新主角也在此首讲：决定"哪些工具属于谁"的作用域（scope）注册，与"只拦不放"的单调守卫（monotonic guard）。
>
> **前置**：第 2 章（Context 与 Service、effect）、第 4 章（事件五模式，尤其 waterfall）、第 8 章（会话日志与无损 JSON）、第 9 章（轮次中工具调用的发起）。第 10 章已告诉你"工具 schema 会流入提示词组装"，本章讲这之后发生的一切。

**学习目标**。学完本章，你将能够：

1. 用 `defineTool` 写出最小工具，说明它从注册到进入提示词、再到被轮次调用的路径；
2. 解释 `tools/pre-execute` 的 allow / deny / ask 语义、单调守卫"只拦不放"性质，及 `tools.restrict` 与守卫的职责分工；
3. 说清作用域化注册如何让"每个 agent 看到不同工具集合"（注册视图向下继承、事件放行向上）；
4. 复述 around 包装（`tools/execute`）的约束——只能替换 `signal`、不能改身份——并举例说明超时包装；
5. 说明 post-execute 收尾职责、`finalizeContent`"只换内容"边界，与 executionMode 的 fail-closed 规则（仅精确 `true` 并行）。

## 11.1 旅程地图：一次 `tool/call` 的九站

一条 assistant 消息里的 tool-call 块（`{ id, name, arguments }`，见第 9 章）只是**意图**；真正执行它的是第 9 章预告的 `executeToolCalls`（`packages/core/agent-loop/src/tool-calls.ts:59-101`）。官方把这条流水线画成 Mermaid 图（`docs/tool-execution-pipeline.zh.md:10-60`），下面这张"旅程地图"是它的九站版本，每站标注本章落点：

| 站 | 名字 | 干什么 | 本章小节 |
|---|---|---|---|
| ① | 循环调度 | 按 `executionMode` 分组、排队启动本次 step 的工具调用 | 11.8 |
| ② | 持久记录 | `session.append('tool/call', …)`——**先记录、后执行** | 11.8（见 8.3） |
| ③ | 创建执行 | 铸造 token、参数无损快照并冻结、快照 finalizer、折叠检查 | 11.5 |
| ④ | pre-execute 瀑布 | 可重排的 allow / deny / ask 门禁（waterfall，见第 4 章） | 11.5 |
| ⑤ | 单调守卫 | 只拦不放的最终审查（deny or abstain） | 11.5 |
| ⑥ | around 包装 | `tools/execute` 瀑布：超时、检查点等"盒子" | 11.6 |
| ⑦ | 工具主体 | `tool.execute()` 返回规范值，render 出模型可见内容 | 11.2、11.6 |
| ⑧ | post-execute 瀑布 + finalizeContent | accept / block / 替换 / 加上下文，最后只换内容 | 11.7 |
| ⑨ | 结果通知 | 冻结的 `tools/result` 观察事件，随后 `tool/result` 持久事件 | 11.7 |

九站中 ②④⑥⑧ 是事件（第 4 章），③⑤⑦⑨ 是注册表自己的代码。旅程总入口是 `ToolRuntime.execute`（`packages/core/tools/src/index.ts:1342-1344`），它把整条流水线拆成三段：**prepare**（③④⑤）→ **dispatch**（⑥⑦）→ **finalize**（⑧⑨）。为何这样拆，11.4 见分晓。

出发前先看两件"货物"：工具（11.2）与其仓库（11.3）。

## 11.2 工具是什么：`defineTool` 与 `ToolDefinition`

### 11.2.1 三步认识"工具（tool）"

**第一步，直觉类比。** 把模型想象成只写工单的经理：它不能亲自干活，只能填固定格式的工单（工具调用参数）；业务部门（注册的同进程代码）照单执行，完活回传**交付说明**（模型可见文本）。工单格式（参数 schema）先给经理过目——这就是"工具 schema 注入提示词"（第 10 章）。

**第二步，精确定义。** 工具（tool）= 一份 `ToolDefinition`（`packages/core/tools/src/index.ts:222-288`），四部分：

1. **模型可见契约**：`name`、`description`、`parameters`（即 `ToolSchema`，第 10 章组装进提示词的那份）；
2. **同进程执行函数**：`execute(args, exec)`（`packages/core/tools/src/index.ts:235`）——只返回规范 JSON 值，异步工作须观察或转发 `exec.signal` 并等活干完才结算（`:226-234`）；
3. **规范输出声明**：必填的 `output { schema, render, presentationMeta? }`（`:224`，`ToolOutputDefinition` 见 `:211-219`）；
4. **可选元数据**：`timeoutMs`（`:248-255`，协作式超时预算，**永不送给模型**）、`isConcurrencySafe`（`:256-269`，仅精确 `true` 才并行）、`finalizeContent`（`:236-247`，同步"最后一步内容变换"，见 11.7）、`presentCall` / `presentResult`（`:270-287`，给 UI 的纯函数卡片意图）。

**第三步，最小示例。** 仓库官方 README 有个 23 行最小工具（代码正文见 `packages/core/tools/README.zh.md:68-90`，含 Markdown 围栏 `:67-91`）：

```ts
import { readFile } from 'node:fs/promises'
import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

declare const ctx: Context

ctx.tools.register(defineTool({
  name: 'read_file',
  description: 'Read a file from disk.',
  parameters: {
    path: { type: 'string', required: true, description: 'Absolute file path' },
    offset: { type: 'number' },
    limit: { type: 'number' },
  },
  output: {
    schema: { type: 'string' },
    render: (_args, value) => [{ type: 'text', text: value }],
  },
  async execute(args, exec) {
    // args is typed: { path: string; offset?: number; limit?: number }
    return readFile(args.path, { encoding: 'utf8', signal: exec.signal })
  },
}))
```

（未验证：本环境未构建运行仓库，此例照录官方 README；它无需 API key，只需构建好的 `@deepseek-ai/dsh-tools` 与已启动的 Context。）

`defineTool`（`packages/core/tools/src/schema.ts:545-617`）替你做的四件事：

1. **编译 schema**：`parameterSchemaSpecToJsonSchema` 与 `valueSchemaSpecToJsonSchema`（`packages/core/tools/src/schema.ts:566-567`）把 DSL 变成注册表强制执行的 JSON Schema 子集；
2. **执行前校验参数**：违规抛 `ToolArgsError`（`INVALID_ARGS`，`:585-588`），走普通错误路径由模型自己重试（`packages/core/tools/README.zh.md:95`）；
3. **软验证呈现器**：`presentCall` / `presentResult` / `isConcurrencySafe` 都对参数做"软验证"，不合法时回退 `undefined`（呈现器）或 `false`（并发分类器），绝不抛错（`:594-615`）——UI **回放**旧日志时调用呈现器，旧参数可能来自更早 schema；
4. **校验 `timeoutMs`**：必须正数且有限（`:563-564`）。

真实工具复杂得多，看第一方参考实现 `read`（`packages/fs/tool-fs/src/read.ts`）：注册时给出 `output.schema`（结构化行窗口，`:84-105`）、`render`（把窗口渲染成带行号文本，`:106-119`）、`presentationMeta`（把窗口投影进持久化 `meta`，供 UI 回放时重建"读文件卡片"，`:123-132`）、`isConcurrencySafe: () => true`（`:135`：读操作的观察性竞态失败即关闭）、`execute`（`ctx.fs.streamText` 大文件流式读取，`:136-164`）。execute **观**察 `exec.signal`（`:145-146`），执行完还 `ctx.emit('fs/observed', …)`（`:162`）——这是第 12 章"先读后写"策略的入口；本章只需记：执行函数拥有 `ctx`，可发事件。

`output` 三件套分工贯穿全书，记住这句：**`value` 是规范值（执行局部）、`content` 是模型文本、`meta` 是给 UI 的投影（随 `tool/result` 持久化）**（`packages/core/tools/README.zh.md:114`）。11.7 看注册表如何分装三者。

### 11.2.2 工具如何被看见：模型视角与注册表视角

定义立刻交给 `ctx.tools.register`（`packages/core/tools/src/index.ts:1037-1062`）。注册时验证：

- `output` 必须存在且 `render` 是函数（`packages/core/tools/src/index.ts:1039-1044`，缺失即 `TypeError`）；
- `output.schema` 必须是受支持的 JSON Schema 子集（`:1045`，`assertSupportedJsonSchema`）；
- `timeoutMs` 正有限（`:1046-1050`）；
- 名字不能是保留的 `run_code`（`:1054-1056`，见 11.5 的折叠讨论）；
- 成功则返回"随调用方 fiber 一起 dispose"的注销函数（`:1057-1061`，`layers.effect`：注册本身是 effect，见第 3 章）。

模型看到的只是 `schemaOf` 白名单过滤出的三分：`name`、`description`、`parameters`（`packages/core/tools/src/index.ts:1256-1267`）。`timeoutMs`、`isConcurrencySafe`、`execute`、`present*`、`finalizeContent` 全部留在注册表内部——**工具对自己执行方式的声明，模型一个字看不到**。`ctx.tools.schemas(scope)`（`:1234-1236`）把这份投影交给第 10 章提示词组装；`ctx.tools.get(name, scope)`（`:1204-1206`）按作用域解析"这名字现在对谁可见"。

"对谁可见"——下节主角。

## 11.3 注册与作用域化：工具属于谁

### 11.3.1 三步认识作用域（scope）

**第一步，类比。** 全局注册像公司公共工具间——每个 agent 都看得见、拿得到；通过 `agent.ctx` 注册像发给某个工位的专属工具箱——只有该工位看得见，且**同名工具以工具箱里的为准**（近者遮蔽）；"代理预设（preset）"像车间级挂墙工具——挂着的一律继承。

**第二步，精确定义。** 作用域（scope）= 一个不透明对象键（`ScopeKey`，`packages/core/scope/src/index.ts:15`）。`createScope(ctx, key)`（`:137-147`）在一个 fiber 下铸造打标签的 Cordis 上下文：从此**通过它进行的每项注册，既按这个键可见，也随这个 fiber 的所有权一起回收**。两个函数撑起两个方向：

- `scopeOf(ctx)`（`packages/core/scope/src/index.ts:154-156`）读"这个上下文带哪个键"；
- `scopeTarget(base, key)`（`:170-185`）构造一个**路由载体**，它只放行"无标签监听器"或"标签为 key 或其祖先"的监听器——即**事件沿父链向上放行**。

两条方向合起来读（`packages/core/scope/README.zh.md:5`）：**注册视图沿链向下继承**（子作用域见祖先各层，近者遮蔽远者），**事件放行沿链向上扩展**（标签为祖先的监听器收得到子孙键事件，反向永不成立）。注册上下文同时决定**可见性与所有权**（`packages/core/scope/README.zh.md:11`），防止"在 A 可见、却随 B 被卸掉"的悬空。

**第三步，实证。** 每个存活的 agent 就是这样一个作用域（`packages/core/agent-loop/src/agent.ts:94-95`）：

```ts
this.scope = createScope(loopCtx, this)
this.ctx = this.scope.ctx.extend({ agent: this })
```

`ReactLoopAgent` 构造时把自己（`this`）当键（`packages/core/agent-loop/src/agent.ts:64`），`agent.ctx` 即带标签上下文；此后 agent 级能力集合（工具、守卫、限制、提示词段）全由 `agent.ctx` 上的注册决定。

### 11.3.2 注册表的"层"：`ToolLayer` 与 `view()`

`ToolRuntime` 内部用 `ScopedLayers`（`packages/core/scope/src/store.ts:159-266`）持有两类层：一个立即构造的**全局层**（`:169`）与按需创建的**作用域层**（`peek` 只读不建、链盲，`:180-183`；`chainLayers` 按"最远祖先在前、本层最后"返回，`:192-199`；`effect` 依 `scopeOf(ctx)` 落层，层全空即回收，`:226-266`）。每个 `ToolLayer`（`packages/core/tools/src/index.ts:714-754`）装四样：具名工具表 `tools`、匿名限制表 `restrictions`、匿名守卫表 `guards`、呈现模式 `mode`；同层重名注册直接抛错（`:725-729`）。

关键是 `view(scope)` 的合并规则（`packages/core/tools/src/index.ts:1152-1193`）：

```ts
const inherited = new Map<string, ToolDefinition>(this.layers.global.tools.entries())
for (const layer of layers) {
  if (layer === own) continue
  for (const [name, definition] of layer.tools.entries()) inherited.set(name, definition)
}
```

**规则一：继承面 = 全局层 + 链上各层，近者遮蔽。** `packages/core/tools/src/index.ts:1161-1165`。同名时，最近的祖先层说了算（`set` 覆盖）。**规则二：限制是整条链的交集。** `:1169-1174` 里 `layers.every(layer => layer.admits(name))` 才把该工具放进 `visible`；`admits`（`:738-744`）对 allow / deny 两表做判定——任何一层说不，就看不见。**规则三：本层自己的注册最后并入，且不受过滤。** `:1178-1183`。`:1137-1143` 解释为何豁免：子代理的"汇报、结构输出"工具注册在**自己层**里，父代滤器滤不掉它们——否则子代理连汇报通道都没了。**规则四：Code Mode 的 `run_code` 传输最后插入、在能力过滤之外。** `:1189-1191`：任何限制都无法移除它——它不属于"可过滤的能力"，而是呈现基础设施。

`view` 另产出 `knownNames`（限制前能力名，供提示词顺序校验）与 `restrictableNames`（**当前**全局名，供 restrict 校验未知名，`packages/core/tools/src/index.ts:1167-1168`、`:1166-1175`）。

### 11.3.3 遮挡与过滤：`tools.restrict`

除注册之外，另一个改变"agent 看见什么"的 API 是 `tools.restrict(filter)`（`packages/core/tools/src/index.ts:1071-1098`）。它把一份 `ToolRestriction`（`:680-685`：`allow` 只留 / `deny` 移除）挂到**调用方所在的层**，限制是整条链上所有层的交集（`packages/core/tools/README.zh.md:22`）。四个硬校验值得记住：

- **必须作用域上下文**：从普通上下文调用直接抛错（`packages/core/tools/src/index.ts:1072-1075`）——全局屏蔽一刀切所有 agent，注释直言："要拒绝就给目标 agent 拒绝"；
- **空过滤报错**：`restrict({})` 是 no-op，几乎必然是"空配置物化"的 bug（`:1078-1080`）；
- **`run_code` 保留名不可命名**（`:1085-1087`）；
- **未知名字直接拒绝**：`restrictableNames` 不含的名字会被列出并抛错（`:1088-1092`）——错字当场拦下，而不是让模型看到"少了个工具"却不知道为什么。

`restrict` 的语义边界要划清：**它是可见性的实时组合，不是权限边界**（`packages/core/tools/README.zh.md:22`；`packages/core/scope/README.zh.md:27` 明确作用域"不是沙箱或权限边界"）。要让调用**必然失败**，用 11.5 的守卫或第 12 章的事件型策略。真实用例：子代理的 `toolFilter`（`packages/subagent/subagent/src/types.ts:133-140`：命名工具"从提示词消失**且**拒绝执行"）在进程内驱动里落成 `childCtx.tools.restrict(composition.toolFilter)`（`packages/subagent/subagent/src/child-agent.ts:174`）——组织机制留第 13 章；这里只需记：**父代一次 restrict，子代工具视野就变了**，名字校验在启动时完成。

## 11.4 三段流水线总览：prepare / dispatch / finalize

`ToolRuntime`（`packages/core/tools/src/index.ts:787-837`）是注册表，也是流水线的调度方。构造时注入 `systemPrompt`（`:788`）并接线"工具 schema → 提示词组装"（`:832`）；`ctx.tools` 键由 `super(ctx, 'tools')` 注册（`:827`）。

流水线对外唯一出口是 `execute`（`packages/core/tools/src/index.ts:1342-1344`），但被"并行调度器"调用的是挂在 symbol 上的分阶段方法（`:796-801`、`:466`）：

```ts
export interface ToolRuntimeScheduler {
  prepare(exec: ToolExecutionInput): Promise<ScheduledToolPreparation>
  dispatch(exec: ToolRunContext): Promise<ScheduledToolDispatch>
  finalize(exec: ToolRunContext, result: ToolExecutionResult): Promise<ToolExecutionResult>
  finish(exec: ToolRunContext, result: ToolExecutionResult): ToolExecutionResult
}
```

（`packages/core/tools/src/index.ts:451-460`；注释声明它"不是插件扩展点"，插件请走 `ctx.tools.execute`。）三阶段的职责与衔接由两个判别类型刻写：

| 阶段 | 调用 | 做什么 | 返回 |
|---|---|---|---|
| prepare | `prepareScheduledExecution`（`packages/core/tools/src/index.ts:1459-1461`） | 物化参数 → pre-execute 瀑布 → 守卫 →（ask 审批） | `dispatch` / `post-result` / `final-result`（`:431-434`） |
| dispatch | `dispatchScheduledExecution`（`packages/core/tools/src/index.ts:1569-1599`） | around 包装瀑布 → 工具主体 → 规范化 | `post-result` / `final-result`（`:441-443`） |
| finalize | `finalizeScheduledExecution`（`packages/core/tools/src/index.ts:1609-1621`） | post-execute 瀑布 → `finalizeContent` → 物化 → 通知 | 最终结果 |
| finish | `finishScheduledExecution`（`packages/core/tools/src/index.ts:1631-1646`） | 同上但**跳过** post-execute | 最终结果 |

判别类型注释（`packages/core/tools/src/index.ts:427-430`、`:437-440`）给出全章最要紧的分界：**`post-result` 仍要经过 post-execute；`final-result` 绕过它**。`prepare` 被否决（deny / 守卫拦截 / 取消）走 `post-result`——策略失效也要有"后置策略"改判的机会；而管道本身的故障（包装抛异常、参数不可序列化）已是"最终结果"，不必绕回 post-execute。`completeScheduledExecution`（`:1346-1362`）的 switch 是路由三种判别类型的接线员。

为什么这样拆？第 9 章调度器给出节拍（`packages/core/agent-loop/src/tool-calls.ts:1-6`："Dispatch may overlap, while policy, results, and result context remain model-ordered"）：`prepare` 与 `finalize` 必须**按模型顺序**逐对执行（结果回填、上下文注入都要有先后），只有 `dispatch` 允许重叠。"前段后段有序、中段重叠"正是 11.8 主角。

## 11.5 第一站：prepare——物化、把关与守卫

### 11.5.1 `createExecution`：为这次调用铸一个身份

`createExecution`（`packages/core/tools/src/index.ts:1364-1451`）做四件事。

**第一，铸造 token。** `createExecutionToken`（`packages/core/tools/src/index.ts:1866-1868`）生成一个带品牌的 `Symbol`（`ToolExecutionToken`，`:307`）：只支持相等性比较、用于关联，绝不跨模型/日志/worker 边界（`packages/core/tools/README.zh.md:45`）；`rootCallId` 在此解析（`:1368`），嵌套执行只拿外层 token 作不透明 `parent`（`:335` 注释）。

**第二，参数快照并冻结。** `snapshotJsonValue(exec.arguments)`（`packages/core/tools/src/index.ts:1412`）把参数无损序列化（`undefined`/函数/循环引用都会失败，见第 8 章），随后 `deepFreeze`（`:1416`）——跨过"无损 JSON 边界"后**模型借出去的东西再也改不动**，策略、包装、主体看到同一份冻结快照（`ToolExecution` 的注释 `:372-378`）。

**第三，提前快照 `finalizeContent`。** `packages/core/tools/src/index.ts:1408-1410`。注释（`:1398-1407`）讲清次序问题：必须在参数物化**之前**捕获回调，因为"参数 getter 可能在 `snapshotJsonValue` 期间替换或清空已注册的回调"。`finalizerFor()`（`:1409-1410`）再决定回调在折叠/中止路径上的存留——能执行的调用才保留，注定失败的（被折叠的、参数非法且未中止的）丢弃。

**第四，折叠检查。** 这是本章最"安全敏感"的判定，先讲清楚。

**Code Mode 折叠（collapse）三步讲。** ① 类比：商场改造后只剩一个"服务台"窗口——模型只能直接叫 `run_code`（服务台），其他货架上的工具都要**经由程序**（服务台派单）去取；模型若直接点名货架上的东西，得到的是"该工具不可直接调用"的拒绝，而非"查无此物"。② 定义：`mode: 'code'` 时注册表只向模型暴露 `run_code` 与生成的 SDK 声明（`packages/core/tools/README.zh.md:120`），模型直呼其他任何可见工具名，`collapses` 谓词（`:1324-1326`：`!nested && modeFor(scope) === 'code' && name !== RUN_CODE_NAME`）判定为"塌缩"，在**任何策略之前**就解析为 `UNKNOWN_TOOL`——"没有人会观察、更不会批准一个注定失败的调用"（`:1373-1379` 注释）。③ 代码：`createExecution` 先查可见性再查折叠（`:1380-1381`），折叠时若已中止给出 `ABORTED_BEFORE_DISPATCH`（`:1429-1431`），否则构造带**路由提示**的 `ToolNotFoundError`（`:1436-1443`），文案（`:1441`）正是"`only \`run_code\` is callable directly — call \`<name>\` from inside a \`run_code\` program instead`"——同一份提示词刚声明过那个工具，只说 "unknown tool" 会被读成"部署坏了"而非"我点错了"（注释 `:1432-1435`）。

折叠与"真未注册"两条路：前者确定失败、抢先一步；后者保留历史路径——策略监听器仍能看到每个到达注册表的陌生名字（`packages/core/tools/src/index.ts:1376-1379`）。`ToolNotFoundError` 继承 `HarnessError`、错误码 `UNKNOWN_TOOL`（`:494-510`），让重试/沙箱/回放代码区分"模型点错工具"与"工具主体抛错"。

### 11.5.2 `prepareExecution`：两道闸门与一条岔路

`prepareExecution`（`packages/core/tools/src/index.ts:1463-1507`）是"守卫室"。逐段走：

```ts
if (this.callerCancelled(exec)) {
  return next({ kind: 'final-result', exec, result: toolAbortedBeforeDispatchResult() })
}
```

**取消最先查**（`packages/core/tools/src/index.ts:1470-1472`）：进入时已中止 → 直接 `ABORTED_BEFORE_DISPATCH`（`:1933-1944`）。注意它发生在参数物化**之后**——入口处已中止的调用先物化冻结参数，才跳过一切策略（`packages/core/tools/README.zh.md:35`）。

```ts
const gate = await this.ctx.waterfall(
  carrier, 'tools/pre-execute', exec,
  () => Promise.resolve<PreToolDecision>({ kind: 'allow' }),
)
```

**第一道闸门：`tools/pre-execute` 瀑布**（`packages/core/tools/src/index.ts:1474-1478`）。waterfall 语义见第 4 章：监听器串成链，最后不调 `next()` 即否决。默认分支是 `allow`，所以"没人管 = 放行"。决策类型 `PreToolDecision`（`:588-591`）只有三态：`allow` / `deny{reason}` / `ask{reason?}`。这是刻意的**缺省**：类型注释（`:582-587`）写得很清楚："输入改写被排除（input rewriting is excluded），因为参数已经记录并展示了"。即 **pre-execute 里不能改参数**：参数登录在 `tool/call` 事件里（第 8 章"模型可见即已记录"），静默改写使日志与执行脱节。

`ask` 态走 `serviceAsk`（`packages/core/tools/src/index.ts:1479-1481`，`:1689-1729`）：注册表用 `ctx.get('approval')` **机会式**取审批服务——没装即退化为拒绝（`:1693-1698`）；无 agent 也拒绝（`:1700-1705`：无可审计会话、无可路由 UI）；`allowed-once` 放行，`rejected`/`cancelled`/`unavailable` 各自给拒绝理由（`:1706-1727`）。审批机制（ApprovalService、`approval/request` 瀑布等）第 12 章讲，这里只记注册表这端合同：**ask 永远以"放行一次或拒绝"收尾，绝不悬置**。

```ts
const denialReason = decision.kind === 'allow'
  ? this.guardReason(exec)
  : decision.reason
if (denialReason !== undefined) {
  return await next({ kind: 'post-result', exec, result: this.materializeFinalResult({ … }) })
}
```

**第二道闸门：单调守卫**（`packages/core/tools/src/index.ts:1486-1498`）。

**单调守卫（monotonic guard）三步讲。** ① 类比：登机口的检票员（pre-execute 瀑布）之后还有一道"黑名单闸机"——闸机只负责**拦**，从不负责放；多台闸机只要有一台响，人就不能上飞机；闸机装在哪台前面都不影响结论。② 定义：守卫是一个同步函数 `ToolGuard = (execution) => string | undefined`（`packages/core/tools/src/index.ts:711`）——返回理由字符串即拒绝，`undefined` 即不表态。因为**守卫没有 allow 结果**，"监听器顺序不可能把一次拒绝变回允许"（`:703-707` 注释）——这是它与瀑布的本质区别：waterfall 是"最后一个说话的人赢"，守卫是"任何一个人说不就不行"。注册方式是 `ctx.tools.guard(guard)`（`:1110-1116`），注意它 `notify: false`——守卫变化不触发 `tools/change`（全局能力集没变）；求值顺序为"全局层先，然后作用域链最远祖先先"（`guardReason`，`:1119-1128`；每层内部按注册序，`:747-753`）。③ 实证：子代理"结构输出"驱动（`packages/subagent/subagent-in-process-driver/src/structured.ts:105-111`）在捕获结构化结果后注册守卫：

```ts
childCtx.tools.guard(exec => captured === undefined && pending === undefined
  ? undefined
  : `structured output already recorded: the run is complete, so \`${exec.name}\` is not executed`)
```

注释（`packages/subagent/subagent-in-process-driver/src/structured.ts:106-108`）给出选守卫而非瀑布监听器的理由：**守卫在整条 pre-execute 瀑布之后求值**，因此即使某个监听器把前面的调用"复活"，守卫照样拒绝——子代理一旦产出结构化结果，同回合内后续工具调用必然被拦下。

守卫/瀑布否决之后，结果不是"直接终局"而是 `post-result`（`packages/core/tools/src/index.ts:1489-1499`）：一个 `isError: true`、内容是 `Error: <reason>` 的规范化结果，**仍要送去 post-execute**（11.7 将看到这给"策略改判"留了门）。最后还有取消复查（`:1500-1502`）与异常兜底（`:1504-1506`，瀑布监听器抛异常 → `final-result`）。

prepare 段收尾：`dispatch`/`post-result`/`final-result` 三选一。

## 11.6 第二站：dispatch——把工具主体包进洋葱

### 11.6.1 around 包装三步讲

**① 类比。** 货物（工具主体）不变，可套一层"快递盒"（超时包装）、再套"保价单"（检查点包装）。每层盒子只能在**交接处**动手脚：换交接单（signal）、读时间戳；货物身份（callId、name、token）封死在面单上，谁都改不了。

**② 精确定义。** around 包装 = 在 `tools/execute` 事件（`packages/core/tools/src/index.ts:163`，waterfall）上注册的监听器：`next()` 返回"规范化结果"，包装可在 `next()` 前后计时、记录、加元数据，并可**替换**其返回。两道硬约束铸在类型里：

- `ToolDispatchExecution`（`packages/core/tools/src/index.ts:391-394`）是 `tools/execute` 专属视图：`signal` 可写（包装**唯一**交接点），其余字段全部只读——**包装只能换信号，不能换身份**；
- 注册表在进入工具主体前，把调用方原始 signal 与包装替换后的 signal **重新融合**（`:1536-1537`，`fuseToolSignals` 见 `:1889-1916`：同引用直接返回；否则建一个 `AbortController`，两个来源各挂一次性监听，任一触发即中止并卸载），所以"换信号"永远**不会**把你和调用方的取消切断；包装还须"还原信号并达到静默"（`:156-158` 注释）——`finally` 里换回 `exec.signal` 是约定（`:1556-1559`）。

**③ 真实代码走读。** 仓库自带超时政策（`packages/guard/timeout-policy/src/index.ts:55-80`）：

```ts
ctx.on('tools/execute', async (exec, next): Promise<ToolExecutionResult> => {
  const timeoutMs = ctx.tools.get(exec.name, exec.agent)?.timeoutMs
  if (timeoutMs === undefined) return next()          // 没声明预算：透明放行

  using d = deadline(exec.signal, timeoutMs, TOOL_TIMEOUT)
  const upstream = exec.signal
  exec.signal = d.signal                               // 换信号
  try {
    const result = await next()                        // 剥到工具主体
    if (timeoutOf(d.signal, TOOL_TIMEOUT) !== undefined) {
      return toolTimeoutResult(timeoutMs)              // 我的计时器赢了才替换
    }
    return result
  } finally {
    exec.signal = upstream                             // 还原信号
  }
})
```

`deadline`（`@deepseek-ai/dsh-timeout`）在到期时中止 `d.signal`——工具主体看到中止信号，须合作地停下（`ToolDefinition` 的契约 `packages/core/tools/src/index.ts:226-234`：注册表不能硬杀同进程代码）。`timeoutOf(d.signal, TOOL_TIMEOUT)` 做"谁的火"分类（`packages/guard/timeout-policy/src/index.ts:23-24`：嵌套的外层超时读出来是 `undefined`，不会被误认）；只有自己的计时器触发才替换结果为 `TOOL_TIMEOUT`（`:26`：常量本身，以及 `:41-48` 的替换函数，模型看到 `tool call timed out after Nms`）。

同站另一位乘客是**会话检查点包装**（`packages/session/session-checkpoint-policy/src/index.ts:70-75`）：顶层工具调用在进入主体前 `await ctx.sessions.flush(exec.agent.session)`——把已记录的调用落盘；**检查点失败即关闭**（函数头注释 `:58-59`："fail-closed at the model and tool side-effect boundaries"），持久化机制第 15 章讲。

诚实说明：`packages/core/tools/README.zh.md:58` 说 `tools/execute` 供"超时、重试或指标"插件使用，这是**扩展点能力**的表述；本仓库实际挂载的包装是上面两个（`packages/bundle/base/cordis.patch.yml:343-344`、`:355-356`）。工具级"重试"包装并不存在——模型调用的重试（llm-retry）属第 10 章 LLM 适配器。**平台给你放盒子的位置，不等于每个盒子都已出厂。**

### 11.6.2 `dispatchScheduledExecution`：瀑布、规范化与延迟上下文

`dispatchScheduledExecution`（`packages/core/tools/src/index.ts:1569-1599`）是"try 里瀑布、catch 里兜底"：

```ts
const result = await this.ctx.waterfall(
  carrier, 'tools/execute', mutableExec,
  () => this.dispatchToolBody(mutableExec),      // 最内层 next() = 工具主体
)
const normalized = this.normalizeDispatchResult(exec, result)
```

- **瀑布最内层就是主体**（`packages/core/tools/src/index.ts:1573-1576`）：包装们按注册/效应顺序叠盒，最后一个 `next()` 真正执行工具——这一行把"洋葱"织成了代码。
- **规范化**（`:1577`，`normalizeDispatchResult` 见 `:1826-1844`）：所有经过 waterfall 的结果都要回到"本执行的输出契约"上来。注册表给自产结果打 token 标记（`markCanonical`，`:1787-1790`）；包装拿来的外部结果若带**别的** token（比如另一个调用的缓存），成功值**重新**过 `createSuccessResult` 校验（`:1837-1839`），错误结果只补标签（`:1831-1835`）。**外面盒子塞进来的结果，必须过一遍本工具的输出声明**。
- **延迟上下文合并**（`:1578-1589`）：工具主体调用过 `exec.deferContext(ctx)`（`ToolRunContext`，`:404-421`）的，在此并入 `additionalContexts`，供循环在 `tool/result` 之后按 FIFO 注入下一轮（`docs/tool-execution-pipeline.zh.md:27`）。
- **取消胜出**（`:1586-1594`）：主体调用**后**到达的取消，只能把**成功**结果换掉（`cancellationResult`，`:1517-1525`：按 `bodyInvoked` 选 `ABORTED` 或 `ABORTED_BEFORE_DISPATCH`）；已是错误则保留原状。
- **管道失败即终局**（`:1596-1598`）：包装或瀑布抛异常 → `final-result`，**不再经过 post-execute**（注释 `:1563-1564`）。与 11.4 分界一致：工具失败仍被审视，管道失败已是最终裁决。

### 11.6.3 `dispatchToolBody`：真正执行的那一刻

`dispatchToolBody`（`packages/core/tools/src/index.ts:1532-1560`）只有 29 行，却是整条旅程的心脏：

```ts
const fused = fuseToolSignals(state.callerSignal, wrapperSignal)
const signal = fused.signal
if (isAborted(signal)) { fused.dispose(); return toolAbortedBeforeDispatchResult() }
exec.signal = signal
try {
  const tool = this.resolveExecution(exec.name, exec.agent, exec.parent !== undefined)
  if (!tool) throw new ToolNotFoundError(exec.name)
  state.bodyInvoked = true
  const returned = await tool.execute(exec.arguments, exec)
  const result = this.createSuccessResult(exec, tool, returned)
  return isAborted(signal) ? toolAbortedResult(result) : result
} catch (error: unknown) {
  return toolErrorResult(error)
} finally {
  fused.dispose()
  exec.signal = wrapperSignal
}
```

- **融合信号**（`packages/core/tools/src/index.ts:1536-1538`）：`fuseToolSignals`（`:1889-1916`）的要点是**不嵌套 `AbortSignal.any`**——手动搭桥、一次性监听、工作结算即卸载（`:1885-1888` 注释：防止监听器随信号滞留）。进入时已中止则直接 `ABORTED_BEFORE_DISPATCH`（`:1540-1543`）。
- **再次解析**（`:1546-1547`）：`resolveExecution`（`:1221-1226`）执行与 11.5 折叠**同一套**谓词——模型直呼被塌缩的名字在此同样被拒成 `UNKNOWN_TOOL`；而携带 `parent` token 的子分发（Code Mode 程序内部调用）可以调用任意可见工具（注释 `:1208-1215`）。
- **`bodyInvoked = true`（`:1548`）是取消语义的分界线**：此**后**取消只能把成功结果换成 `ABORTED`（`:1551-1553`，`toolAbortedResult` `:1919-1930`——保留先前的 `additionalContexts`，`:1920-1928`）；此**前**一切取消都是 `ABORTED_BEFORE_DISPATCH`。为何回放关心这条线？因为两种结果在日志里**编码不同**（`ABORTED` / `ABORTED_BEFORE_DISPATCH` 两个错误码，`:469`、`:472`），模型据此知道"活儿干到一半被叫停"还是"根本没开工"。

`createSuccessResult`（`packages/core/tools/src/index.ts:1793-1823`）履行 11.2 的"三件套分装"：`snapshotToolValue` 无损快照返回值（`:1794`）→ `validateJsonSchemaValue` 按 `output.schema` 校验（`:1795-1796`，违规即 `ToolOutputError`/`INVALID_TOOL_OUTPUT`，`:513-522`）→ `deepFreeze`（`:1797`）→ `output.render`（`:1799-1804`，投影异常也是 `ToolOutputError`）→ **仅顶层调用**运行 `presentationMeta`（`:1806-1814`；嵌套子分发不计算 meta，因为它们不回放）→ 记入 `concludesTurn`（`:1815`，`exec.concludeTurn()` 在此落地）。

## 11.7 第三站：finalize——收尾、定格与通知

### 11.7.1 `tools/post-execute`：最后一道可改写的瀑布

`postExecute`（`packages/core/tools/src/index.ts:1742-1781`）先跑 `tools/post-execute` 瀑布（`:1743-1746`），决策类型 `PostToolDecision`（`:597-600`）四选一：

- **`accept{content?}`**：接受，或仅替换内容（`packages/core/tools/src/index.ts:1776-1780`）——规范值与 meta 原样保留；
- **`accept{value}`**：替换规范值——**重走**整个输出契约（重新快照、校验、渲染、投影，`:1764-1775`），失败的替换直接抛错；
- **`block{feedback}`**：把反馈文本变成 `isError` 结果（`:1748-1756`，`failureMessageFromContent` `:624-630`）。**block 丢弃 defer 的上下文**——被拦截的结果不该再携带它自己申请的上下文（`:1736-1740` 注释）；
- **加 `additionalContexts`**：任意决策都可携带；接受时它们追加在工具延迟上下文之后（`:1760-1763`）。

还有互斥校验：同时替换 `content` 与 `value` 会报错（`packages/core/tools/src/index.ts:1757-1759`）。`packages/core/tools/README.zh.md:59` 的提醒正合适：**内容替换不是保密边界**——值不该被编程消费方拿到时，用 block 或替换值，而非只改文字。

### 11.7.2 `finalizeContent`：只换内容，且对失败也执行

`finalizeScheduledExecution`（`packages/core/tools/src/index.ts:1609-1621`）拿到 post-execute 结果后，若取消胜出再换一次（`:1612-1616`），交给 `finishScheduledExecution`（`:1631-1646`）：

```ts
materializedResult = this.materializeFinalResult(result)
…
finalResult = this.materializeFinalResult(this.applyFinalContent(exec, materializedResult))
this.notifyResult(exec, finalResult)
```

`applyFinalContent`（`packages/core/tools/src/index.ts:1649-1654`）只有四行：取 11.5 快照的 `finalizeContent` 调用，返回 `undefined` 则保留原内容，否则**只替换 `content` 字段**——`{ ...result, content }`，其他一律不可动（`:1653`）。它的三条合同（`:236-247` 注释 + `packages/core/tools/README.zh.md:43`）：

1. **调用开始时已快照**（`packages/core/tools/src/index.ts:1408-1410`），执行期间回调被换也不影响本次；
2. **对每个规范化结果恰好执行一次**，含绕过 post-execute 的管道失败（`final-result` 路径同样经 `finishScheduledExecution`→`applyFinalContent`）；回调必须是**同步、全定义**的，抛错由 `:1641-1642` 兜底捕获回 `toolErrorResult`；
3. **只能换内容**。它常用于截断/给位置一类（如 spill 策略），所以不能接触 `value`、`isError`、`meta`。

物化（`materializeFinalResult`，`packages/core/tools/src/index.ts:1847-1862`）：`content` / `meta` / `additionalContexts` 三者被无损快照并深度冻结（`materializePresentation` `:633-639`，非无损 JSON 直接 `TypeError`）；成功结果额外带上 `value`（`:1861`）——`value` 至此最后一次现身：**只活在执行局部**，不进日志、不给 UI（`ToolExecutionSuccess` 注释 `:558`）。

### 11.7.3 `tools/result`：冻结的观察事件

`notifyResult`（`packages/core/tools/src/index.ts:1657-1676`）先 `Object.freeze(exec)`（`:1660`）——观察者拿到的是注册表活对象的只读视图；再以 `scopeTarget(this, exec.agent)` 为载体做 `emit` 分发（`:1665-1667`）：**按调用 agent 键控**，哪个 agent 的调用通知哪个作用域的监听器（事件声明 `:197`）。观察者异常被**包含**：同步抛错与 Promise 拒绝都进 `logger.warn`（`:1662-1675`），绝不让一个观察者毁掉结果。

这里必须分清两个名字相近的事件（`packages/core/tools/README.zh.md:39`）：

| 事件 | 谁发 | 何时 | 生命周期 |
|---|---|---|---|
| `tools/result` | 注册表（本处） | 流水线终局、结果冻结后 | **实时**观察事件，不进会话日志 |
| `tool/result` | agent loop（`packages/core/agent-loop/src/tool-calls.ts:282-288`） | 提交结果时 | **持久**会话事件（见 8.3），`surfaceOp: 'append'`、`sourceEventSeqs: [callSeq]` 关联到本调用的 `tool/call`；`meta` 一并持久化（`:287`） |

两个工具型观察者常驻此站：`tools/result` 的"提交判定"（如 `packages/subagent/subagent-in-process-driver/src/structured.ts:116-131`：确认结构输出工具结果，成功才写 `captured`）与 `tool/result` 的"回放素材"（`meta` 留给 UI 重建卡片）。注册与限制的变化则发出**不筛选**的 `tools/change`（`:207`）——全局能力集变了，每个 agent 的下一次组装都受影响（注释 `:198-206`）。`tools/result` 之后，旅程回到 11.8 的循环。

## 11.8 回到循环：谁在驱动这趟旅程

### 11.8.1 `executeToolCalls`：分组与滚动池

回看第 9 章"轮次"里的 `executeToolCalls`（`packages/core/agent-loop/src/tool-calls.ts:59-101`）。先取发起 agent（`:67`），把每个 tool-call 块变成 `ToolExecutionInput`（`:71-80`：`callId`、`name`、`parseArguments` 解析的参数、`agent`、`signal`；`agent` 由循环设置，`packages/core/tools/src/index.ts:324`）。`parseArguments`（`:103-110`）把模型 JSON 文本解析为对象，**无效 JSON 原样保留为字符串**（回放需忠实），空串映射 `{}`。

然后是分组主循环（`packages/core/agent-loop/src/tool-calls.ts:82-100`）：

```ts
const mode = ctx.tools.executionMode(first.exec).kind
const group = mode === 'parallel' ? planned.slice(next) : [first]
const outcome = await runGroup(ctx, turn, step, group, mode, signal, acceptContext)
```

每次取排在最前的调用，问 `executionMode`（`packages/core/tools/src/index.ts:1276-1285`）：`parallel` 把**剩余全部**编为一组（滚动池），`exclusive` 则**单独成组**形成排序屏障。这就是"模型想并行、注册表说了算"——**executionMode 的 fail-closed 规则**（学习目标 5）：只有可见定义的 `isConcurrencySafe(exec.arguments)` **恰好**返回 `true`（严格相等）才并行；未知、被限制、被塌缩、未声明、参数无效、分类器抛异常——一律 `exclusive`（`:1276-1285`；`packages/core/tools/README.zh.md:27`）。模型消息里说"并行"在 dsh 里只是**建议**，错误声明安全落回串行。相应的契约是：选择并行的工具**不得修改父级拥有的状态**（`packages/core/tools/src/index.ts:261-265`）。

`runGroup`（`packages/core/agent-loop/src/tool-calls.ts:121-246`）实现滚动池，四点：

1. **槽位按模型顺序**：`slots` / `callSeqs`（`packages/core/agent-loop/src/tool-calls.ts:132-134`）给每个调用留位；
2. **先记录后执行**：`startCall` 第一步是 `appendToolCall`（`:167`，`:261-265`）——`tool/call` 日志在**执行前**落笔（`docs/tool-execution-pipeline.zh.md:13` 同此），是第 8 章"模型可见即已记录"的又一体现；
3. **`prepare` 先行、`dispatch` 后行、`finalize` 按序提交**：`startCall` 只调 `prepare`（`:169`）并按判别类型落槽（`:171-195`）；仅 `dispatch` 启动 Promise 进 `inFlight`（`:173-183`）；`commitReady`（`:146-160`）按模型顺序提交——仅**连续**槽位就绪才 `finalize`/`finish` 并 `appendToolResult`（`:152-155`），结果的上下文经 `acceptContext` 进入下一轮 inbox（`:156`）。11.4 的三段式在此**分开调用**：前段后段保序、中段重叠；
4. **滚动池与重分类**：`fillPool`（`:198-213`）在池容量 `maxParallelToolCalls`（`:131`）内连续启动；每次启动新调用前**重读** `executionMode`（`:203-204`）——注册表可能在提交间隙变了（工具被卸载/被限制），出现"滚动到一半遇屏障、剩余改走独占"。主循环（`:218-235`）用 `Promise.race` 等最早结算的调用，结算后立即提交，再补池。

**取消语义**（`packages/core/agent-loop/src/tool-calls.ts:237-241`）：中止后，已启动的调用**排干并提交**（上下文也被接受），未启动的调用合成一条 `ABORTED_BEFORE_DISPATCH` 结果（`appendSkippedToolCall`，`:248-259`）——合成结果保证**回放有效**（模块注释 `:8-10`：每条 `tool/call` 都有配对的 `tool/result`，日志不悬空）。调度器内部失败则相反：**不伪造**任何结果（`:118-119` 注释），只拒绝。

### 11.8.2 闭环

把九站串回一条线：循环启动 → `tool/call` 落笔 → prepare（物化、瀑布、守卫）→ dispatch（洋葱、主体、规范化）→ finalize（post-execute、finalizeContent、冻结通知）→ `tool/result` 落笔 + `additionalContexts` 入 inbox → 模型拿到结果消息，开始下一轮装配（第 9、10 章）。一次 `tool/call` 旅程至此闭环。

## 本章小结

- 工具是"模型可见契约 + 同进程执行 + 规范输出声明"的复合体（`packages/core/tools/src/index.ts:222-288`）；`defineTool` 负责参数校验与软验证，注册表只把 `name/description/parameters` 交给模型（`packages/core/tools/src/schema.ts:545-617`、`packages/core/tools/src/index.ts:1256-1267`）。
- 注册带作用域：注册视图向下继承、近者遮蔽，事件放行向上；`view()` 的合并规则是"继承面 × 限制交集 + 自身层豁免 + 传输插入"（`packages/core/tools/src/index.ts:1152-1193`）。
- 流水线三段式：prepare（物化/瀑布/守卫）→ dispatch（around/主体/规范化）→ finalize（post/finalizeContent/通知）；`post-result` 过 post-execute，`final-result` 绕过（`:427-440`）。
- 两道把关本质分工：pre-execute 瀑布"最后说话的人赢"，单调守卫"任何一人说不就不行"（`:703-711`）；审批 `ask` 以"放行一次或拒绝"收尾（`:1689-1729`）。
- around 包装只能替换 `signal`、不能改身份；注册表把调用方与包装的信号融合后交主体（`:391-394`、`:1889-1916`）；超时与检查点是实际挂载的包装（`packages/bundle/base/cordis.patch.yml:343-344`、`:355-356`）。
- `finalizeContent` 开始即快照、失败也执行、只换内容；`tools/result` 是冻结的实时观察事件，`tool/result` 才是持久会话事件（`packages/core/tools/src/index.ts:1657-1676`、`packages/core/agent-loop/src/tool-calls.ts:282-288`）。
- executionMode fail-closed：仅精确 `true` 并行，其余一律独占（`packages/core/tools/src/index.ts:1276-1285`）；循环按此分组、滚动池启动前重分类（`packages/core/agent-loop/src/tool-calls.ts:82-100`、`:198-213`）。
