# 第 1 章　从一条命令到一棵插件树：dsh 全景

> **本讲法**：这是一章"数据流预览"。我们不像读说明书那样逐条罗列功能，而是跟着一个用户问题，看一条 `dsh` 命令如何一步步变成一棵正在运行的插件树，再反过来看如何把这棵树"拍成快照"。全章出现的多数术语（patch、bundle、entry、fiber 等）先"露面"、后"带走"：本章只给出足以继续往下读的直觉和出处，精确定义与机制剖析留给后续各章（我会在首次出现处标出第几章详解）。心里有全局之后再进第 2 章，你会知道"为什么要学 Context 与 Service"。
>
> **前置**：TypeScript 与 Node.js 基础、LLM Agent 的基本概念（消息、工具调用、流式输出）。若尚未接触，请先回到本书首页的"先修知识"清单。

**学习目标**。学完本章，你将能够：

1. 说出 `dsh` 的三种启动模式与各自的使用场景；
2. 在纸上画出"命令 → 配置组装 → 插件树 → 轮次流程"的完整链路，并指出每一步对应的源码文件；

5. 掌握本书的引用格式、术语约定与诚实性标注规则，为后续 16 章建立统一的阅读习惯。

## 1.1 一个用户问题开场

假设你刚从 GitHub 克隆了 DeepSeek Harness（下文简称 `dsh`）仓库，装好依赖、跑完 `pnpm run build`，然后你有一个真实需求：**修复这个仓库里一个失败的测试**。

动手之前，总得先把产品跑起来。README 给了两种方式。第一种，浏览器界面：

```sh
pnpm dsh web
```

文档说这会启动 Web UI，默认地址 `http://127.0.0.1:3080`（`examples/headless-agent/README.zh.md:19-23`）。第二种，把任务直接交给命令行，让它干完就退出：

```sh
pnpm dsh --profile headless "fix the failing test in this workspace"
```

`examples/headless-agent/README.zh.md:13` 正是这样示例的。输出的不是聊天流，而是"最终 assistant 文本"——修完即退出。第三种，你可能想要一个自己的界面组合：安装一个第三方插件包，把它叠进某个 profile，再启动。官方参考手册（`apps/cli/reference/README.md:45-49`）给出了这种形态：

```sh
dsh plugin --profile tui add github:deepseek-harness/turtle-ui
dsh plugin --profile tui remove turtle-ui
dsh --profile tui
```

现在请你停下片刻，观察一个乍看不起眼的事实：**这三种行为的差异完全来自命令行参数，命令本身没有任何 agent 逻辑**。`dsh` 只是一个"分发器"加一套"组装器"——它自己不认识模型、不会调用工具、不存储会话。那么，`dsh` 到底把活交给了谁？答案在下一节。

（顺带一提：从仓库源码运行时，`package.json:136` 的脚本 `"dsh": "node --import tsx/esm apps/cli/src/bin.ts"` 说明 `pnpm dsh` 其实就是用 tsx 直接执行 `apps/cli/src/bin.ts`——本章源头。）

## 1.2 产品三形态：三种启动方式

### 1.2.1 入口只有一处：`apps/cli/src/bin.ts` 的三路 switch

`apps/cli/src/bin.ts` 是唯一入口。它先解析参数（`apps/cli/src/bin.ts:27`），然后按解析出的 mode 走一个三路 switch（`apps/cli/src/bin.ts:29-52`）：

```ts
switch (invocation.mode) {
  case 'profile': {
    const { runProfile } = await import('./profile-boot.ts')
    await runProfile({ environment: loadLayeredEnv('dsh'), profile: invocation.profile,
      patchFiles: invocation.patches, args: invocation.args })
    break
  }
  case 'plugin': {
    const { runPlugin } = await import('./plugin.ts')
    process.exit(runPlugin(invocation.profile, invocation.args))
    break
  }
  case 'dump-config': {
    const { runDumpConfig } = await import('./dump-config.ts')
    runDumpConfig(invocation.profile, invocation.defaultOnly, invocation.patches)
    break
  }
  ...
}
```

三个分支对应三种模式，而文件头注释（`apps/cli/src/bin.ts:2-5`）说明了设计意图：**按模式动态 import**——你只跑 `dump-config` 时，`profile-boot.ts` 与 `plugin.ts` 的代码根本不会加载。模式分派表如下：

| 模式 | 入口 | 干什么 | 你什么时候用 |
|---|---|---|---|
| `profile` | `apps/cli/src/bin.ts:30-39` | 组装一棵插件树并启动 | 一切真实使用：`web`、`headless`、自定义 profile |
| `plugin` | `apps/cli/src/bin.ts:40-44` | 把参数原样转发给 pnpm，管理 profile 的插件依赖 | 安装/移除第三方 bundle |
| `dump-config` | `apps/cli/src/bin.ts:45-48` | 打印组装结果后退出，**不启动** | 排查"我的配置为什么长这样" |

### 1.2.2 启动器只解析自己的旗标

注意 `apps/cli/src/bin.ts:36` 的 `args: invocation.args`：profile 模式把参数包里"剩下的参数"原样交给了组装器。这是 `dsh` 命令行设计的分界原则，`apps/cli/src/args.ts:4-11` 的注释写得非常清楚：

> 启动器只解析自己拥有的东西——用哪个 profile 启动、要加哪些 patch overlay、是否打印配置——**并把它自己旗标之后的一切原样交给启动起来的插件树**，由注入树中的应用插件解析自己的旗标族并打印自己的 `--help`。

这条原则解释了 `dsh web -h` 打印的是 web 应用自己的帮助（`apps/cli/src/args.ts:10-11`、`apps/cli/src/args.ts:66-70` 的示例文本），也解释了为什么 `dsh --profile web --port 8080` 里的 `--port` 会到达 web 应用的参数解析器而不是报"未知参数"（`apps/cli/reference/README.md:17`）。相应地，"应用参数"必须排在启动器旗标之后：`apps/cli/src/args.ts:123-129` 用 `passThroughOptions()` 等方法让解析在第一个不认识的位置参数处停止。

### 1.2.3 三形态的官方定义

`apps/cli/reference/README.md` 是 CLI 行为的权威文档，它对三种形态各有一句话定性：

- **web**：`dsh web` 是 `--profile web` 的硬编码别名（`apps/cli/src/args.ts:13`，`apps/cli/src/args.ts:156-168` 注册了 `web` 子命令并复用 `resolveBoot`）。首次使用自动初始化：`web: base + web-app`，`headless: base + headless`（参考手册 `apps/cli/reference/README.md:13`，模板表见 `packages/boot/app-boot/src/profile.ts:113-117`）；web 提供 `--host`、`--port`、可重复的 `--trusted-host`（`apps/cli/reference/README.md:25-28`），默认监听 `http://127.0.0.1:3080`，且当前**故意不支持** `--host 0.0.0.0`（`apps/cli/reference/README.md:64`）。
- **headless**：一次性任务运行器。"创建一个新的持久化 Agent，提交任务，等待静默，打印最后一条非空 assistant 文本；`completed` 退出码 0，否则 1"（`apps/cli/reference/README.md:30`）。这个 profile 不挂载 ApiProxy、Host、HTTP 服务器、Web 运行时或浏览器客户端——成功运行**不会写 stderr、不开任何监听端口**（`apps/cli/reference/README.md:30`；`packages/bundle/headless/README.zh.md:5`）。
- **自定义 profile**：`dsh plugin --profile <name> add <pkg>` 初始化（其他名字没有内置模板时只用 `@deepseek-ai/dsh-base`，`packages/boot/app-boot/src/profile.ts:125`），然后把命令转发给 pnpm；成功安装后，凡 package.json 里声明了 `"dsh": {"bundle": {"patch": "./cordis.patch.yml"}}` 的依赖都会进入该 profile 的层栈（`apps/cli/reference/README.md:43`）。

`plugin` 模式还有两个值得知道的边界：其一，它要求 `pnpm` 在 PATH 上，转发的参数原样交给 pnpm，所以 `add`、`remove`、`why`、`update` 等所有 pnpm 动词都能用（`apps/cli/reference/README.md:43`）；其二，Git 托管的插件若在安装时跑自己的 `prepare` 脚本，pnpm ≥10 会先拒绝，要求你在 profile 的 `pnpm-workspace.yaml` 里显式放行（`apps/cli/reference/README.md:51`）——这是供应链安全设计，不是 bug。

三种形态共享同一套配置档案（profile）机制——这正是 1.3 节要展开的全局图。

## 1.3 全局图：从一条命令到一棵插件树

本节把 1.1 节那个"谁来干活"的问题彻底回答。整条链路分四段：**解析 → 组装 → 启动 → 运行**。

### 1.3.1 解析：`parseDshArgs`

参数进入 `parseDshArgs`（`apps/cli/src/args.ts:112-190`）后归一成一个 `DshInvocation`（`apps/cli/src/args.ts:20-48`：`mode`、`profile`、`patches`、`args` 四要素）。注意 `patches` 是**可重复**的 `--patch` 路径列表（`apps/cli/src/args.ts:61` 的 `collect` 是"重复单值收集器"而非变参——注释说变参会把应用参数吞掉）。到此为止，`bin.ts` 还不知道任何关于插件的事；它只持有"要启动谁、要叠什么补丁"的意图。

### 1.3.2 组装：把一层层补丁叠成一颗"配置洋葱"

以 `dsh --profile web` 为例。`runProfile` 内部调用 `prepareProfile(name)` 与 `composeProfile(name, patches)`（`apps/cli/src/profile-boot.ts:142-171`）。这一段是"组装"的中枢，必须读注释，因为里面藏着整个产品最重要的不变量，总结为四条：

**第一，每棵 profile 树都从"空根"开始叠补丁。** 空根是一个只含 `[]` 的 `cordis.yml`（`apps/cli/src/profile-boot.ts:59-64` 的 `PROFILE_ROOT_CONFIG`，文件名常量在 `:66-67`）。它的注释说：profile 树是作为补丁组合出来的——先按 `package.json` 的 `dsh.profile.bundles` 依次应用每个 bundle 的补丁，再应用 `cordis.patch.yml`，最后是 `--patch` overlay；请你编辑 `cordis.patch.yml` 而不是这个文件。`prepareProfile` 在每次启动前都**重写**这个空根（`apps/cli/src/profile-boot.ts:98-103`）：因为 vendored Loader 的树回写（某个插件自我卸载时把当前树持久化）可能把组装好的行烘焙进文件里，下次启动就会重复插入每个 bundle（`:85-97` 的注释推理）。这个文件在磁盘上存在，只是因为 Loader 需要一个真实 include 根来锚定 `baseUrl`——配置转储也锚定同一个文件，所以"转储"与"启动"在完全相同的基座上组装（`:92-93`）。

**第二，层序是硬编码的。** `allPatches`（`apps/cli/src/profile-boot.ts:121-129`）的顺序是：bundle 层（`composed.bundlePatches`）→ profile 自己的 `cordis.patch.yml`（`profile.patches`）→ home 级 `$DSH_HOME/cordis.patch.yml`（`homePatches`）→ overlay（`--patch` 与遥测开关，`overlays`）。参考手册归纳为一句："后面的层按行胜出；一条 patch 替换目标行的**整个 config**，而不是深合并键，也可以插入新行"（`apps/cli/reference/README.md:9`）。home 级文件之所以排在 profile 自己之上，是因为它是"机器本地偏好，对每个 profile 生效"（`apps/cli/src/profile-boot.ts:131-137`）。

**第三，行序与语义无关——激活顺序由"服务可用性"驱动。** 请看 `packages/bundle/base/cordis.patch.yml:12-13` 的头注释："行序不携带加载语义（激活由服务可用性驱动），分组只是为了方便读者。"这句话是本教程的枢纽之一：一个 entry 会在它声明的依赖服务全部就绪后才运行（第 2、3 章逐一解释），所以你在树文件里看到的顺序**不能**当作执行顺序。理解这一点，你就不会在排查"为什么 `llm` 行排在 `session` 行前面却不先启动"上浪费时间。

**第四，组装还会"加料"。** `composeProfile` 收尾时做两件事（`apps/cli/src/profile-boot.ts:159-169`）：若树里存在 `agent-presets` 行，给它增补一个"出厂预置根"（`SHIPPED_PRESET_ROOT`，`trust: 'system'`）；若设置了非空 `DSH_TELEMETRY_DISABLED`，追加一个禁用 session 遥测行的补丁——注意它选择"宁可误关不可误开"（`:69-79` 的注释）。这两处都是"组装器站在使用者角度替树做决定"的例子：`dsh` 是组装器，同时也是产品规则的执行者。

### 1.3.3 启动：`boot()` 把空根交给 Loader

组装出的层列表最终交给 `packages/boot/app-boot/src/index.ts` 的 `boot()`（`packages/boot/app-boot/src/index.ts:757-785`）。它的前五步是：

1. `new Context()`——创建根上下文（第 2 章的主角）；
2. 设置 `ctx.baseUrl` 指向配置文件所在目录（`packages/boot/app-boot/src/index.ts:769`），避免相对路径解析漂移；
3. `await ctx.plugin(Loader)`——装上 cordis 的插件加载器（`:771`）；
4. 可选的 `prepare`（宿主准备工作，`:772`）；
5. `mountRootInclude(ctx, absoluteConfigPath, patches, bareModuleBaseUrl)`（`:774`）——把那个空根 `cordis.yml` 作为 include 根挂载进去。

`mountRootInclude`（`packages/boot/app-boot/src/index.ts:486-524`）把 include 插件注册为内置（`:492-503`，还处理了 bare 包名的宿主解析），然后通过 `ctx.loader.create(rootInclude)` 创建 id 固定为 `'include'` 的根条目（`:514-523`）。从这一刻起，Cordis 的 include 插件开始工作：它读取 `cordis.yml`，把 bundle 补丁、profile 补丁、home 补丁与 overlay 作为**一个扁平列表**喂给 `applyEntryPatches`，然后每个 entry 变成一个插件实例（fiber）——"一棵插件树"就此成形。补丁算法的细节（`applyEntryPatches`、`!!js` 表达式、insert 的 id 索引）是第 5 章的内容，这里只记住一个结论：**树是补丁叠出来的，且"转储"与"启动"共用同一个补丁算法调用**——这个结论的出处是 `renderConfigDump` 的注释："compose the effective entry list exactly as `boot()` would mount it … the same single call `boot()` makes"（`packages/boot/app-boot/src/index.ts:348-356`）。

`boot()` 还做收尾检查：等 Loader 服务就绪后 `assertEntriesActivated(ctx, binName)`（`packages/boot/app-boot/src/index.ts:784`）——确认每个条目都激活了，否则报带标签的错误并清理部分启动的树（`:786-794`）。启动失败时你会看到 `host preparation failed` 或 `plugin tree failed to load` 前缀。

### 1.3.4 运行：插件树在轮次中真正干活

树启动之后，"干活的"是一系列事件。`docs/architecture.zh.md:66-88` 给出了官方流程（节选关键行）：

```text
turn/start
  claim next-step input plus one queued message
  assemble prompt sections + tool schemas
  -> agent/pre-step                   reject | enter(messages)
     step/start
     append entered messages as user/message
     derive model history from the log
     agent/request -> llm/stream -> assistant/chunk* -> assistant/message
     tool/call* -> tools/pre-execute -> tools/execute -> tools/post-execute -> tool/result*
     step/end
  -> agent/turn-stopping
turn/end
```

这里先建立两个词（第 8、9 章再展开）：**步骤（step）**= 一次模型请求加上它调用的工具；**轮次（turn）**= 零个或多个步骤，从领取首条输入开始、到不再欠任何工作时关闭（`docs/architecture.zh.md:69`）。你在这个流程中能看到树的三个特征：其一，`llm/stream`、`tools/*` 这类事件是**扩展点**——任何插件都可以注册监听器在流式输出或工具执行路径上插入自己的行为；其二，`agent/pre-step` 是"瀑布式事件（waterfall）"，监听器必须调用 `next()` 才能委托下去（`docs/architecture.zh.md:88`）；其三，`turn/start` 这类事件会**持久化**进会话日志，而 `deriveMessages()` 从日志投影出模型历史——"模型可见即已记录"（`docs/architecture.zh.md:96-100`）。

另外请注意两点"先说破、后详解"的关系：插件之间**按服务名**互相发现（`ctx.tools`、`ctx.llm`、`ctx.agents` 都是服务，`docs/cordis-tutorial/03-services.zh.md:5`）——这是第 2 章的主题；事件有五种分派模式（`emit`、`parallel`、`waterfall`、`serial`、`bail`）——这是第 4 章的主题。你现在只需要知道：**树启动后的一切协作，要么通过服务，要么通过事件**。

浏览器里的 Web UI 并不是这棵树的另一份实现，而是通过 API 网关消费树的另一个客户端（`docs/architecture.zh.md:125` 给出了"添加 UI 或编辑器集成：驱动 `ctx.agents` 并从 `session/event` 渲染"的归属行）。树与客户端之间的协议层是第 16 章的内容。

至此，1.1 节的问题有了完整回答：

```
dsh --profile web
  │  parseDshArgs (args.ts:112-190)          —— 只认启动器旗标
  ▼
composeProfile (profile-boot.ts:142-171)      —— 空根 + 层序叠补丁
  │  boot() (app-boot/src/index.ts:757)       —— new Context + Loader
  ▼
mountRootInclude (index.ts:486)               —— 空根 cordis.yml 作为 include 根
  │  applyEntryPatches (第5章)               —— 扁平补丁列表 → entry 列表
  ▼
插件树：每个 entry 一个 fiber                —— 树启动完毕
  │  turn/start … turn/end (architecture.zh.md:66-88)
  ▼
一次轮次的一次完整执行
```

## 1.4 `--dump-config`：把组合过程拍成快照

### 1.4.1 它解决什么问题

假设你在 `$DSH_HOME/profiles/web/cordis.patch.yml` 里写了一条补丁，想把 `agent-loop` 的 `agents` 换成自己的，结果行为不符合预期。你想弄明白："现在这棵树到底是什么样？"——这正是 `dump-config` 模式存在的理由：**不启动、不评估，把组装结果直接打印出来**。官方文档甚至建议把这一步当作日常操作："要查看你的机器实际启动的配置树"（`docs/architecture.zh.md:29-33`）。

### 1.4.2 它是"boot-free"的：关键在共享同一个补丁算法

`apps/cli/src/dump-config.ts:1-6` 的模块注释说：通过 include 插件的补丁算法组装 profile 的补丁层，**但不启动、不求值 `!!js`**。实现上，`runDumpConfig`（`apps/cli/src/dump-config.ts:30-52`）先 `prepareProfile(profile, !defaultOnly)`（`:31`，第二个参数控制是否解析用户层），再为每一层构建一个 `ConfigDumpLayer`（bundle 层按包名标注，`:32-35`；用户层、home 层、overlay 依次追加，`:36-49`），最后 `renderConfigDump`（`:51`）。

为什么"不启动也能打印出与启动一致的树"？因为 `renderConfigDump` 没有重写补丁算法——它在**逐层快照**上调用同一个 `applyEntryPatches`：`snapshot(count)` 把前 count 层的补丁拍平后调用一次（`packages/boot/app-boot/src/index.ts:411-419`），注释明确说明这是 "the exact arguments boot passes for that prefix"（`:406-407`）。同一版本算法意味着连"补丁可见性角例"都一致：`boot()` 里后一层补丁看不到前置 config 替换新引入的行，转储里也一样（`:352-356`）。

顺带一提快照法还产生了一个副作用：文件与补丁标签是通过"单次调用前缀快照的位置 diff"推出来的（`packages/boot/app-boot/src/index.ts:360-365`），所以输出里的 `patched by` 列表严格按应用顺序排列——转储测试正是因此断言 `patched by <profilePatch>, <overlay>`（`apps/cli/tests/built-bin.e2e.ts:759`）。

### 1.4.3 输出解读：`# ==` 分组与 `patched by`

转储输出由 `groupedDump` 渲染（`packages/boot/app-boot/src/index.ts:445-473`）：每一段连续的、来源相同的行，前面加一条 `# == <label>` 注释（`:454`）；若某行被后续层改过，则标签变为 `<origin>, patched by <layers>`（`:462-464`）。于是输出既是**合法的 YAML 文档**（可以直接喂回 include），又是**带出处的清单**。下面是一段真实结构的示意输出——请注意它**不是**本机运行的实录，而是依据源码中的真实行与真实测试断言整理出来的（各行的出处我都附在括号里；你机器上的实际输出以 `dsh web --dump-config` 为准，标注"输出样式以实际版本为准"）：

```yaml
# == @deepseek-ai/dsh-base
- id: timer
  name: '@deepseek-ai/cordis-plugin-timer'          # packages/bundle/base/cordis.patch.yml:15-17
- id: hmr
  name: '@deepseek-ai/cordis-plugin-hmr'            # packages/bundle/base/cordis.patch.yml:19-22
  config:
    root: ['.']
- id: llm
  name: '@deepseek-ai/dsh-llm'                      # packages/bundle/base/cordis.patch.yml:24-25
- id: session
  name: '@deepseek-ai/dsh-session'                  # packages/bundle/base/cordis.patch.yml:27-28
# …（中间略去大量 base 行）…
- id: agent-loop
  name: '@deepseek-ai/dsh-agent-loop'               # packages/bundle/base/cordis.patch.yml:436-439
  config:
    agents: []

# == @deepseek-ai/dsh-base, patched by @deepseek-ai/dsh-web-app
- id: system-prompt
  name: '@deepseek-ai/dsh-system-prompt'
  config:
    persona: >-
      You are a coding agent powered by the {{model}} model. Your working directory is {{cwd}}.
                                                        # packages/bundle/web-app/cordis.patch.yml:16-20 覆盖
- id: hmr
  disabled: true                                     # packages/bundle/web-app/cordis.patch.yml:22-23 覆盖（同一行第二次出现）

# == @deepseek-ai/dsh-web-app
- id: webserver
  name: '@deepseek-ai/dsh-host-webserver'            # packages/bundle/web-app/cordis.patch.yml:115-120
  inject: [webStartup]
  config:
    host: !!js ctx.webStartup.host ?? '127.0.0.1'
    port: !!js ctx.webStartup.port ?? 3080
# …（modules 等浏览器侧行）…
- id: modules
  name: '@deepseek-ai/dsh-client-modules'            # packages/bundle/web-app/cordis.patch.yml:151-152
```

逐段对照你能验证四条规律（每条都有源码出处）：

1. **分组注释出自"来源文件"**：`# == @deepseek-ai/dsh-base` 正是端到端测试断言的真实注释文本（`apps/cli/tests/built-bin.e2e.ts:707`）。
2. **改过的行会累积 `patched by`**：`system-prompt`、`hmr` 由 base 插入、被 web-app 覆盖，所以它们出现在"base, patched by web-app"段——`hmr` 行里 `disabled: true` 正是 web-app 覆盖后的样子（`packages/bundle/web-app/cordis.patch.yml:22-23`），而 base 里的原行（`packages/bundle/base/cordis.patch.yml:19-22`）不再单独出现，因为"整行替换"。
3. **`!!js` 表达式原样打印、不求值**：`host` 的默认值写成 `ctx.webStartup.host ?? '127.0.0.1'`（`packages/bundle/web-app/cordis.patch.yml:119`）——因为 `--help` 之类不提供 `webStartup` 服务的调用不应绑定任何地址（`packages/bundle/web-app/cordis.patch.yml:8-12` 注释）。转储与启动共享同一 YAML 方言，所以它打印的就是**表达式文本**。
4. **"树从哪个入口进过，输出就有哪些行"**：headless 的转储断言不含 `dsh-host-`、`dsh-web-app`、`dsh-client-`（`apps/cli/tests/built-bin.e2e.ts:719-721`），与"不挂 Host/HTTP/Web"的定性（`apps/cli/reference/README.md:30`）一一对应。

### 1.4.4 两个旗标与一个错误渠道

- `--dump-config`：打印 bundle 层 + 用户层 + home 层 + `--patch` overlay（`apps/cli/src/args.ts:89-102`、`apps/cli/src/dump-config.ts:36-49`）；
- `--dump-default-config`：**只**打印 bundle 层，省略用户层与 overlay——文档说它是"`cordis.patch.yml` 损坏时的恢复诊断"（`apps/cli/src/dump-config.ts:24-27`；互斥与不接受 `--patch` 的检查在 `apps/cli/src/args.ts:89-101`）。

还有一个"被拒绝"的边界：**转储不接受应用参数**。若你同时给了应用参数与 `--dump-config`，直接报错（`apps/cli/src/args.ts:95-97`）。原因在注释里写得很直白：转储不运行应用命令行提供方，因此无法知道那些旗标会决定什么；打印一棵与同一调用的真实启动树不同的树会误导人（`apps/cli/src/args.ts:92-94`）。这条边界反过来印证了 1.2.2 的分界原则——"转储"与"启动"的差异必须被谨慎控制，凡是启动时才会发生的影响，转储宁可拒绝也不猜测。

还有一处需要留意的行为：**未命中任何行的补丁会报到 stderr**。`renderConfigDump` 的 `warn` 参数默认写往 stderr（`packages/boot/app-boot/src/index.ts:383`），且逐层快照的警告列表是"递延拼接"的——后一层的新警告才显示（`packages/boot/app-boot/src/index.ts:429-432`）。测试里用户补丁写了一条针对 `absent-row` 的配置，转储的 stderr 里便出现 `patch: entry "absent-row" not found`（`apps/cli/tests/built-bin.e2e.ts:760`）。当你想"为什么我的补丁没生效"时，先看 stderr 的这一行。

## 1.5 "产品的每一部分都是插件"

### 1.5.1 一句话的出处

`docs/architecture.zh.md:11` 的原文是：

> 产品的每一部分都是插件，包括模型适配器、工具注册表、会话日志，以及 agent loop（智能体循环）本身，因此每一部分都可以从配置替换。

第 1.3 节你已经看到这句话的"硬件基础"：树由补丁层叠出，行按 id 定位、整体替换 config。于是"替换某一部分"在操作层面等于"在靠后的层里写一条针对该 id 的补丁"。`docs/architecture.zh.md:13` 还补了另一半："不存在需要打补丁的特权内核：扩展 dsh 的方式是把插件挂载到其他插件旁边"。

仓库布局印证了这句话的规模。`packages/` 下是一个个可独立发布的插件包，按能力族分组（`packages/README.md:11-59` 的层级表）：`core/` 是产品 API 主干（会话、提示词、工具、agent 服务与具体循环，`:13`），`llm/` 是 LLM 能力族（抽象服务 + 提供方适配器，`:20`），`fs/`、`shell/`、`subprocess/`、`sandbox/`、`lsp/`、`code-runtime/` 各管一类能力（`:22-28`），`session/` 管持久化数据面（`:45`），`host/` 与 `client/` 是 Web GUI 的宿主半与浏览器半（`:55-56`）……每个分组都是"同一类插件的集合"，而不是"一整个产品的零件库"。

组合包（bundle）是这一切的**分发格式**：一个可安装的包，通过声明 `"dsh": {"bundle": {"patch": "./cordis.patch.yml"}}` 贡献一层补丁（`docs/architecture.zh.md:21-23`）。内置三个——`dsh-base` 是每个 profile 的第一层（模型适配器、工具、持久化、沙箱与审批策略、设置、凭据、遥测），`dsh-web-app` 增加浏览器应用，`dsh-headless` 增加一次性运行器且完全不带服务器（`docs/architecture.zh.md:25`）。

### 1.5.2 最小可读示例：`examples/headless-agent/cordis.yml`

「一切皆插件」在配置层面是什么样子？看 `examples/headless-agent/cordis.yml` 的开头（`:9-16`）：

```yaml
- id: settings
  name: '@deepseek-ai/dsh-settings-file'

- id: credentials
  name: '@deepseek-ai/dsh-credentials-local'

# The DeepSeek adapter. Swap to '@deepseek-ai/dsh-llm-pi-ai' for the pi-ai-backed
```

每一行都是一个 entry（条目）：`id` 是补丁寻址的名字，`name` 是实际的插件包。注意 `credentials` 行的注释（`examples/headless-agent/cordis.yml:12-14`）：密钥不在文件里内联，而是在每次请求时经凭据存储解析 `DEEPSEEK_API_KEY`——"配置里没有密钥"是产品级的边界设计，第 15 章展开。下方还有一行指示了"替换"的写法：把 `name` 换成别的提供方即可（`:18` 注释）。这正是"配置可以选择提供方，无需修改消费方"（`docs/cordis-tutorial/03-services.zh.md:5`——这个原则将在第 2 章从机制上真正讲透）。

"每一部分都可以从配置替换"不是口号，`docs/architecture.zh.md:112-131` 的"新行为归属表"把它落成了一张可执行的清单：添加模型提供方→在 `ctx.llm` 上注册其适配器；添加文件系统访问或策略→注册 `ctx.fs` 提供方或监听 `fs/*` 事件；添加 shell 执行→注册 `ctx.shell` 后端；添加面向模型的能力→在 `ctx.tools` 上注册，其 schema 自动加入提示词组装（`:114-116`）。每一行都是一条"从配置/注册表替换"的路径——而 `ctx` 正是第 2 章的对象。读到这里，你应当建立这样的心理模型：**在 dsh 里，"加功能"= 挂插件，"换实现"= 换提供方，"观察行为"= 监听事件**，三者都是树上的操作，不存在需要打开源码修改的核心。

## 本章小结

- `dsh` 是分发器加组装器，自身不含 agent 逻辑；三种模式（profile / plugin / dump-config）由 `apps/cli/src/bin.ts:29-52` 一个 switch 分派，按模式动态加载。
- 启动器只解析自己的旗标，其余参数原样移交树中的应用插件（`apps/cli/src/args.ts:4-11`）。
- 每棵 profile 树从空根 `cordis.yml` 起，按"bundle 层 → profile 层 → home 层 → overlay"叠补丁（`apps/cli/src/profile-boot.ts:121-129`）；每条补丁按 id 定位、整行替换 config。
- `boot()`（`packages/boot/app-boot/src/index.ts:757`）挂 Loader，`mountRootInclude`（`:486`）把空根交给 include；此后每个 entry 一个 fiber，插件树成形，轮次事件流驱动真实工作（`docs/architecture.zh.md:66-88`）。
- `--dump-config` 与启动共享同一个 `applyEntryPatches` 快照序列，因此能"不启动、不求值 `!!js`"地打印出真实组装树；`# ==` 注释标出来源，`patched by` 按应用顺序列出改写者，未命中的补丁进 stderr。
- "产品的每一部分都是插件"（`docs/architecture.zh.md:11`）：`packages/` 即插件群，bundle 是其分发格式，配置即插件树。
