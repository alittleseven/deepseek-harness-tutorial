# 第 4 章　事件即扩展点：五种分发模式与 dsh 的真实事件

> **本章学习目标**（读完本章，你应该能够）：
> 1. 给出事件（event）、监听器（listener）、分发（dispatch）、`next`、否决（veto）、声明合并（declaration merging）的规范定义，并说出 `EventOptions` 两个字段的语义；
> 2. 在"是否等待、顺序、返回值、如何短路"四个维度上默写五种分发模式的差异，并各举一个典型用途；

> 4. 推导 waterfall 的洋葱模型：最后一个参数为什么是最内层 `next`，为什么"不调用 `next()` 即否决"，为什么观察型监听器必须调用 `next()`；
> 5. 指出 dsh 中 `agent/pre-step`、`agent/turn-stopping`、`llm/stream`、`tools/pre-execute` 各自使用哪种模式，并说明子系统包如何通过声明合并把自己的事件类型注入 `ctx.events`。
>
> **本章讲法**：对比型——先用"同一条消息、五种广播"建立直观差异（4.1），再进引擎逐行解析（4.3）、用语义表归纳（4.4）、对 waterfall 做深潜（4.5），最后落到 dsh 的真实事件（4.10），看同一套引擎在三种典型场景中如何使用。第 3 章讲的是"注册什么事、怎么撤销"；本章讲"注册之后，一次调用如何被投递给所有监听器"。

## 4.1 一条消息，五种广播

先看现象，不谈原理。假设我们已经建好上下文 `ctx`，并向同一个事件 `'seal'`（盖封条，纯属演示取名；其类型声明方式见 4.2 节 ③）注册了三个监听器（listener，观察者）：

```ts
ctx.on('seal', (word: string) => { console.log('L1 第一道封条:', word) })
ctx.on('seal', (word: string) => { console.log('L2 第二道封条:', word) })
ctx.on('seal', (word: string) => { console.log('L3 第三道封条:', word) })
```

同一个事件名，Cordis 提供五种分发方式——`ctx.emit`、`ctx.parallel`、`ctx.serial`、`ctx.bail`、`ctx.waterfall`（`vendor/cordis/src/events.ts:32`）。对 `'seal'` 各发一次，行为差异如下（**以下输出均按 `events.ts` 源码推演，未在本仓库实际运行**）：

```ts
// ① emit：同步调用全部监听器，返回值与返回的 Promise 一律忽略
ctx.emit('seal', '甲')
// 输出：L1 第一道封条: 甲 → L2 第二道封条: 甲 → L3 第三道封条: 甲

// ② parallel：所有监听器并发启动，等全部结束才算完成
await ctx.parallel('seal', '乙')
// 输出顺序不定；三个监听器都执行

// ③ serial：按注册顺序逐个执行并等待；谁返回"非 null/false/undefined"谁胜出，后面的人不再出场
const r = await ctx.serial('seal', '丙')
// 若 L1 返回 '封住了'：输出只有 L1，且 r === '封住了'

// ④ bail：serial 的同步版，不等待 Promise
const r2 = ctx.bail('seal', '丁')

// ⑤ waterfall：最后一个参数必须是 next；监听器必须调用 next() 才能轮到大后方"默认行为"
ctx.waterfall('seal', '戊', () => '默认行为')
```

第 ⑤ 行与前面四种有本质不同：它的监听器签名里多了一个 `next` 参数。`waterfall` 的事件"默认行为"以最后一个参数的身份被传入，监听器把自己包在默认行为外面——这与第 3 章看到的 `ctx.effect` 双栈登记完全不同，是一种"洋葱"式的协作。四种普通模式下所有监听器是平行的观察者；waterfall 下监听器链则是"从前向后包裹、从后向前返回"。

本节只负责"看到差异"，不解释原理：`dispatch` 引擎如何找到监听器、五种模式各自的循环策略、`next` 的确切语义，依次从 4.2 节起讲。

为什么五种方式必须并存？因为"收到事件"在不同场景里有四种完全不同的需求：看一眼就走（emit）、互不干扰地干活但在最后汇总错误（parallel）、按优先级排队处理、谁拍板谁终止（serial/bail）、以及先到先服务、层层加工（waterfall）。下面按"是什么 → 怎么实现 → 怎么用"的顺序把它们讲透。

## 4.2 事件是什么：三步讲解

### ① 类比：广播站与服务台

第 2 章的服务（service）像一个"服务台"：一个名字（如 `ctx.llm`）在任一时刻对应一个提供方。事件（event）则是"广播站"：一个频道名（`'llm/stream'`）可以有任意多个订户（监听器），播出时每个订户都会收到；不同的是，有些频道只是"通知"，有些频道允许订户"对节目内容动手脚"。服务回答"这个能力现在归谁"，事件回答"这件事发生了，谁想知道、谁想参与"。

### ② 精确定义

> **事件（event）**：一个命名的、可以被多个监听器同时观察或协作的调用点。事件名即频道名，参数列表与返回类型由类型层面的 `Events` 接口契约约定（`vendor/cordis/src/events.ts:329-352`，4.9 节展开）。
>
> **监听器（listener）**：通过 `ctx.on(name, fn)` 注册到某个事件的观察函数；同一个事件名可注册多个监听器。
>
> **分发（dispatch）**：把一次调用投递给某个事件的全部匹配监听器的过程，由事件服务 `EventsService` 负责（`vendor/cordis/src/events.ts:131`）。

事件服务挂在 `ctx.events` 上，在构造根上下文时创建（`vendor/cordis/src/context.ts:26`、`vendor/cordis/src/context.ts:80`）：`this.events = new EventsService(self)`。它把自己的七个方法混入上下文代理，于是我们前面写的 `ctx.on`、`ctx.emit`、`ctx.waterfall` 都是真实存在的（`vendor/cordis/src/reflect.ts:219-222`，其中第 222 行 `this.mixin('events', ['on', 'once', 'parallel', 'emit', 'serial', 'bail', 'waterfall'])`）。第 3 章讲 `ctx.on` 走的是 fiber 的 effect 栈；本章讲这些方法如何把调用投递给监听器。

### ③ 最小示例：声明、注册、分发

一个事件要成立，需要三件事：**声明**（告诉 TypeScript 这个事件名、参数、返回值是什么）、**注册**（谁监听）、**分发**（谁广播）。声明用 TypeScript 接口合并（declaration merging，声明合并）完成——这是本章第一个新概念，先讲清楚：

> **声明合并**：TypeScript 允许多个同名的 `interface` 声明自动合并为一个接口（字段取并集）。借助这一点，第三方包可以给别的包声明的接口"补丁式"添加成员，而不改动原文件。可以类比：考试大纲是官方印的，教师可以在大纲外贴一页补充说明，两份加在一起才是完整大纲。Cordis 在 `vendor/cordis/src/events.ts:34-109` 用 `declare module './context.ts'` 给 `Context` 接口补充事件方法，正是同一机制；dsh 的子系统反过来给 cordis 的 `Events` 接口补充自己的事件（4.10 节）。

```ts
// ① 声明：给自己的"项目专用事件"补进 Events 接口
// （放在任意一个 import 了 @deepseek-ai/cordis 的模块里）
declare module '@deepseek-ai/cordis' {
  interface Events {
    'project/ready'(name: string): void
  }
}

// ② 注册：插件启动时挂上监听器；返回的 dispose 可手动移除
const dispose = ctx.on('project/ready', (name: string) => {
  console.log(`项目 ${name} 就绪`)
})

// ③ 分发：广播这个消息，上面这个监听器被同步调用
ctx.emit('project/ready', 'harness')   // 输出：项目 harness 就绪
```

声明合并不仅是类型糖：`ctx.on('project/ready', ...)` 能过类型检查、`ctx.emit` 的参数能被校验，全部依赖它。一旦声明与分发的参数不匹配，编译期就会报错——这是"事件即契约"的落点：**每个分发点用哪种模式，也是契约的一部分**（`@mode` 标签，见 4.10 节）。

## 4.3 dispatch 引擎：一次分发如何找到监听器

五种分发方式的差异不在"找监听器"（找的过程完全一样），而在"找到之后怎么调用"。先看公共的找法——`dispatch()`（`vendor/cordis/src/events.ts:165-175`）：

```ts
dispatch(type: string, args: any[]) {
  const thisArg = typeof args[0] === 'object' || typeof args[0] === 'function' ? args.shift() : null
  const name: string = args.shift()
  if (!name.startsWith('internal/')) {
    this.emit('internal/dispatch', type, name, args, thisArg)
  }
  const filter = thisArg?.[Context.filter]
  return (this._hooks[name] || [])
    .filter(hook => hook.global || !filter || filter.call(thisArg, hook.ctx))
    .map(hook => hook.callback.bind(thisArg))
}
```

逐句看：

1. **提取 `this`（166 行）**：`args[0]` 若是对象或函数，就把它当作分发时的 `this` 并从参数里移走。于是 `ctx.waterfall(carrier, 'tools/execute', exec, next)` 的第一个参数 `carrier` 被识别为 `thisArg`——它是"作用域载体"（scope carrier，4.10 节讲），不算事件参数。这个约定解释了为什么 dsh 的事件声明里总是写着 `(this: Scoped<Agent>, payload, ...)`：`this` 类型就是载体，插件监听器里的 `this` 指向它。
2. **取出事件名（167 行）**：`args.shift()` 后剩下的才是真正的负载参数。
3. **`internal/` 前缀特判（168-170 行）**：只有"公开事件"（不以 `internal/` 开头）才会先广播一个 `internal/dispatch` 诊断事件（4.9 节）。框架内部事件的分发不会自触发诊断，避免无限递归与噪音。
4. **作用域过滤（171-173 行）**：`Context.filter` 是挂在 `thisArg` 上的过滤器（`vendor/cordis/src/context.ts:46`）。`hook.global` 为真则无条件通过；没有过滤器则全通过；否则调用 `filter.call(thisArg, hook.ctx)`，用**注册监听器的上下文** `hook.ctx` 做判定——这一步正是 dsh 的"事件只发给该管的人"的实现基础。
5. **绑定（174 行）**：`hook.callback.bind(thisArg)` 让监听器执行时 `this` 就是分发时的 `thisArg`。

这五步对所有模式共用。回到 4.1 的五个方法，它们只是"对 `dispatch()` 返回的回调数组"执行不同的循环策略（`vendor/cordis/src/events.ts:183-243`）：

| 方法 | 实现核心（行号） | 循环策略 |
|---|---|---|
| `emit` | `vendor/cordis/src/events.ts:194-196` | `this.dispatch('emit', args).map(cb => cb(...args))`——同步逐个调用，**不 await** 返回值；某个监听器同步抛错会直接抛出并把 `map` 中断，后面的监听器不再执行 |
| `parallel` | `vendor/cordis/src/events.ts:183-187` | `Promise.allSettled` 并发调用全部回调，全部结束后若存在被拒者则抛 `AggregateError`（聚合错误） |
| `serial` | `vendor/cordis/src/events.ts:204-209` | `for...of` 顺序 `await` 每个回调，第一个 `isBailed(result)` 为真的直接 `return` |
| `bail` | `vendor/cordis/src/events.ts:217-222` | 同样的顺序短路循环，但**不 `await`**：同步调用，返回的 Promise 本身也会被 `isBailed` 判为胜出（4.6 节） |
| `waterfall` | `vendor/cordis/src/events.ts:234-243` | 见 4.5 节，唯一一个"监听器互相调用"而非"引擎逐个调用"的模式 |

细心的读者已经发现：`emit` 在引擎层是"裸奔"的——一个监听器抛错会饿死后续监听器，返回的 Promise 直接被丢弃。这个缺口正是 dsh 在 `agent` 事件上重写 `emit` 的原因（`packages/core/agent/src/dispatch.ts:120-137`），4.10 节再展开。

## 4.4 五模式语义表

现在把五种模式放到一张表里对比。前四列的答案是"引擎行为"，最后一列是"设计意图"（`vendor/cordis/src/events.ts:24-31` 的注释与 dsh 各事件的 `@mode` 标签共同佐证）：

| 模式 | 是否等待 | 调用顺序 | 返回值 | 短路/否决方式 | 典型用途 |
|---|---|---|---|---|---|
| `emit` | 否（同步调用） | 注册顺序 | 无（`void`，`vendor/cordis/src/events.ts:53`） | 不可否决，只通报；同步抛错即中断 | 日志、指标、纯观察 |
| `parallel` | 是（`Promise<void>`，`vendor/cordis/src/events.ts:44`） | 并发无序 | 无；有错则统一抛 `AggregateError` | 不可否决；失败聚合成一个错误 | 配置检查、并行清理 |
| `serial` | 是（逐个 `await`） | 注册顺序 | 第一个 bail 值（`vendor/cordis/src/events.ts:63`、`204-209`） | 返回非 `null`/`false`/`undefined` 即终止后续 | 按优先级决策的拦截链 |
| `bail` | 否（同步） | 注册顺序 | 第一个 bail 值（`vendor/cordis/src/events.ts:73`、`217-222`） | 同上，同步判定 | 需要同步短路的钩子（如注册拦截） |
| `waterfall` | 由监听器决定（`await next()` 则等待） | 注册顺序（洋葱包裹） | 最外层监听器的返回值（`vendor/cordis/src/events.ts:86`） | **不调用 `next()` 即否决整条链** | 请求/配置的环绕加工（中间件） |

记忆口诀：**看**用 `emit`，**干**用 `parallel`，**拦**用 `serial`/`bail`，**改**用 `waterfall`。"看"是通知，"干"是并行干活，"拦"是按顺序谁拍板谁收工，"改"是把默认行为包进一层层包装里。

一个容易被忽略的点：`serial` 的返回值类型是 `Promisify<ReturnType<Events[K]>>`（`vendor/cordis/src/events.ts:63`），即"事件声明里监听器返回什么类型，`serial` 就返回什么——但总是包在 Promise 里"；`bail` 则原样返回（`vendor/cordis/src/events.ts:73`）。也就是说，**同一个事件既可以 `serial` 分发又可以 `bail` 分发，不必为两种模式分别声明事件**——模式是分发时的选择，不是事件本身的属性。这也是为什么 dsh 要把模式写进每个事件的 `@mode` 标签：它约束的是"本项目约定用哪种分发"，防止消费方误用。

## 4.5 waterfall 深潜：洋葱、next 与否决

### ① 类比：收银台的"传话结账"

想象一条收银队伍：每位顾客买了东西，结账时却要由**最后进店的导购**完成。要拿到结账结果，你得把"请下一号处理"的话头传给下一位，全场只有最后默认的那个人真正扫了商品码。waterfall 的事件分发性与之同构：每个监听器都收到一个 `next`——"叫下一位"的函数；谁不叫，后面的全体（包括默认行为）就都不发生。

### ② 精确定义

> **`next`**：waterfall 分发时注入每个监听器的最后一个参数的函数。调用 `next()` 会执行链中下一个监听器（链尾的 `next` 是调用方传入的默认行为），并把内层结果作为 `next()` 的返回值交给当前监听器。
>
> **否决（veto）**：监听器不调用 `next()` 直接返回自己的结果，链条就此中断，默认行为与更内层的监听器都不执行。

### ③ 最小示例与逐行走读

`waterfall` 的全部逻辑只有十行（`vendor/cordis/src/events.ts:234-243`）：

```ts
waterfall(...args: any[]) {
  const cbs = this.dispatch('waterfall', args)   // ① 取出匹配的监听器回调数组
  const inner = args.pop()                        // ② 弹出最后一个参数：最内层 next（默认行为）
  const next = () => {                            // ③ 唯一的共享 next
    const cb = cbs.shift() ?? inner               // ④ 叫下一位；没人了就叫默认行为
    return cb(...args)                            // ⑤ 把同样的参数传给它
  }
  args.push(next)                                 // ⑥ 把 next 挂到参数末尾
  return next()                                   // ⑦ 从第一个监听器开始
}
```

这个实现极其精巧，值得逐行体会：

- **② 为什么"最后一个参数即最内层 `next`"**：调用方 `ctx.waterfall('seal', '戊', () => '默认行为')` 的第三个参数是默认行为。`args.pop()` 把它单独保存为 `inner`，剩下的 `['seal', '戊']` 才是监听器真正收到的业务参数。
- **③-④ 一个闭包、一个计数器**：所有监听器收到的 `next` 是**同一个闭包**。每次调用 `next()`，`cbs.shift()` 消费一个监听器；当 `cbs` 为空时，`?? inner` 使最后一次 `next()` 落到默认行为上。所以"调用一次 `next()` 推进一格"；链上的监听器可以**多次调用** `next()`（把链推进多格，一般不这么做），也可以完全不调（否决）。
- **⑤ 参数传递**：`cb(...args)` 展开的 `args` 在 ⑥ 之后已带上 `next`，所以每个监听器收到的签名都是 `(…业务参数, next)`——与 dsh 事件声明里 `next: () => Promise<Xxx>` 的最后一个参数一一对应（`packages/core/agent/src/runtime-types.ts:231`）。
- **⑦ 返回值**：`next()` 的返回值是内层监听器的返回值，因此监听器内 `const x = await next()` 拿到的是**整条内层链的结果**；监听器 `return x`（透传）或 `return 加工后的 x`（替换）都可以。最终整个 `waterfall` 返回**最外层监听器**的返回值（`vendor/cordis/src/events.ts:86`）。

一个三个监听器的完整例子放在 4.8 节；这里先明确一条端到端的纪律：

> **waterfall 纪律**：观察型监听器必须调用 `next()` 并（通常）返回其结果，否则会否决掉默认行为；只有决策型监听器——明确拥有这个事件的"决定权"的——才可以在不调用 `next()` 的情况下直接返回自己的结论。官方教程称之为"不调用 `next()` 直接返回则短路，拥有决策权时的短路是设计意图"（`docs/cordis-primer.zh.md:34-48`）。

例如 `agent/pre-step`：默认行为是"进入这个 step 并把系统提示拼接进消息"（`packages/core/agent-loop/src/agent.ts:236-239`）。一个只想记录日志的插件若忘了 `await next()`，整个 agent 的步骤推进就会停摆——这比"少打一行日志"严重得多，所以纪律必须先行。

最后一点：`prepend` 与 `global` 这两个选项只在 `EventOptions` 里出现（`vendor/cordis/src/events.ts:112-117`）——`prepend: true` 让监听器排到同事件其他监听器**前面**（`register` 里 `unshift` 代替 `push`，`vendor/cordis/src/events.ts:255`），`global: true` 让它**跳过作用域过滤器**（`vendor/cordis/src/events.ts:173`）。恰当地说：waterfall 链的"包裹顺序"就是注册顺序（`prepend` 可反转这一顺序），这与洋葱模型的直觉一致。

## 4.6 serial 与 bail 的短路边界：isBailed 的精确判定

`serial` 与 `bail` 的"谁胜出"由一个两行函数决定（`vendor/cordis/src/events.ts:13-15`）：

```ts
export function isBailed(value: any) {
  return value !== null && value !== false && value !== undefined
}
```

**注意它不是 truthy 判断**。`isBailed` 的边界语义可以精确陈述为："只要不等于 `null`、`false`、`undefined` 三者中的任何一个，就算 bail。"于是下表成立：

| 监听器返回值 | `isBailed` | 是否短路 |
|---|---|---|
| `null` / `false` / `undefined` | 恒为假 | 否，继续叫下一位 |
| `0` / `''` / `NaN` | 真 | **是**（与直觉相反：`0`、空字符串都算"拍板"） |
| `true` / 任意对象 / 任意字符串 | 真 | 是 |
| `Promise`（未 await） | 真 | **bail 模式下直接判为胜出**（同步无等待） |

由此得到两个必须记住的坑：

1. **`bail` 模式永远不要在监听器里返回 Promise**。`bail` 是同步循环（`vendor/cordis/src/events.ts:217-222`），它拿到一个 Promise 对象——该对象既非 `null` 也非 `false` 也非 `undefined`——立刻判定胜出并把 Promise 还给你。如果你当时是想"异步确认后再决定"，这个 Promise 就是 bug 的种子。异步短路请用 `serial`（它会 `await cb(...)` 再判定，`vendor/cordis/src/events.ts:206`）。
2. **`serial` 模式"不反对"的正确写法是 `return undefined`（或直接不写 `return`）**。dsh 的 `agent/turn-stopping` 就是这样设计：事件声明为 `Promise<void> | void`（`packages/core/agent/src/runtime-types.ts:278`），监听器如果反对当前 turn 结束，就通过 `agent.steer(...)` 引导并返回自身的结果；如果不反对，什么都不返回——`undefined` 不会短路（`vendor/cordis/src/events.ts:207`），机器继续走完它的收尾逻辑（`packages/core/agent-loop/src/agent.ts:296`）。

理解了这个边界，再看一眼 4.4 的表：`serial`/`bail` 的"短路"不是"返回 false 就停"，而是"返回一个'非空'值就停"。把 `isBailed` 设计成显式三值排除而非 truthy 判断，意图是让 `false` 参与"继续"而不必引入哨兵常量——这是一个值得在代码评审中留意的设计取舍。

## 4.7 监听器的生命周期：注册即 effect

第 3 章的核心命题是"每个注册都必须是 effect，撤销与注册成对出现"。事件监听器正是这一命题最典型的应用：`on()` 的全部工作，就是"把监听器登记进 fiber 的 effect 栈"。

先看 `on()` 的完整实现（`vendor/cordis/src/events.ts:288-302`）：

```ts
on(name: string | symbol, listener: (...args: any) => any, options?: boolean | EventOptions) {
  if (typeof options !== 'object') {
    options = { prepend: options }              // ① 布尔参数简写：true ≡ { prepend: true }
  }
  this.ctx.fiber.assertActive()                 // ② 当前 fiber 必须还活着（第 3 章 3.4 的状态机）
  listener = this.ctx.reflect.bind(listener)    // ③ 包一层追踪代理
  const result = this.bail(this.ctx, 'internal/listener', name, listener, options)  // ④ 允许框架接管注册
  if (result) return result
  const hooks = this._hooks[name] ||= []        // ⑤ 惰性建槽
  const label = `ctx.on(${typeof name === 'string' ? JSON.stringify(name) : name.toString()})`
  return this.register(label, hooks, listener, options)  // ⑥ 登记为当前 fiber 的 effect
}
```

- **① options 归一化**：`ctx.on(name, fn, true)` 等价于 `{ prepend: true }`。
- **③ `reflect.bind`**：`vendor/cordis/src/reflect.ts:408-417` 用 `Proxy` 包住监听器，每次调用都把 `this` 与参数标记（trace）到注册方上下文，服务于诊断堆栈——不影响函数语义，但让"这个监听器是谁注册的"在排查时可见。
- **④ `internal/listener` 是 bail 模式**：事件总线自己用 `ctx.on('internal/listener', ...)` 注册了这个钩子的处理器（`vendor/cordis/src/events.ts:140-146`）。任何对普通事件的 `on()` 都会先走一遍 `bail` 分发（第 ④ 步），如果一个框架钩子返回了非空值，注册流程就被它接管。`EventsService` 构造器正是借此为 `internal/update` 实现了"每个 fiber 本地一份更新回调表"的特例（`vendor/cordis/src/events.ts:141-145`：`internal/update` 的监听器不放进全局 `_hooks`，而是放进 `this.fiber._hooks['internal/update']`，按 `prepend` 决定 `unshift`/`push`）——你注册的 `ctx.on('internal/update', ...)` 会停在**当前 fiber 自己的表**里，随 fiber 卸载一起消失。
- **⑥ register**：`register()`（`vendor/cordis/src/events.ts:254-260`）就一句话核心——`this.ctx.fiber.effect(() => { hooks[method]({ ctx: this.ctx, callback, ...options }); return () => this.unregister(hooks, callback) }, label)`：把"注册"动作与"注销"动作打包成一个 effect 交给当前 fiber（第 3 章 3.5）。分发的开销也交代清楚：`Hook` 记录（`vendor/cordis/src/events.ts:120-123`）存了注册时的 `ctx`（过滤用）与回调。

`unregister`（`vendor/cordis/src/events.ts:269-275`）是 `findIndex` + `splice`：按**回调引用**删除。注意这与 `once` 的关系——`once`（`vendor/cordis/src/events.ts:312-318`）注册的是个包装函数：第一次被调用时先 `dispose()` 自己再转发给原监听器。因此 **4.1 到 4.8 所有示例里的监听器都是"纤维自带生命周期的"**：插件卸载（fiber 卸载，第 3 章 3.6 的连带卸载机制）时，effect 栈里的注销动作自动执行，监听器从 `_hooks` 中被移除——事件系统不存在"插件卸载后监听器仍存活"的幽灵。这正是热重载（第 3 章 3.1）能安全成立的关键一环。

## 4.8 最小示例：三个 waterfall 监听器的输出顺序

把 4.5 的十行逻辑用三个监听器跑一遍（演示代码，**输出为按 `vendor/cordis/src/events.ts:234-243` 推演，未在本仓库运行**）：

```ts
const order: string[] = []

ctx.on('seal', (word: string, next: () => string) => {
  order.push('L1-前')
  const r = next()            // 叫下一位；r 是整条内层链的返回值
  order.push('L1-后')
  return `[${r}]`             // 向外包装
})
ctx.on('seal', (word: string, next: () => string) => {
  order.push('L2')
  const r = next()
  return `${r} +L2`
})
ctx.on('seal', (word: string, next: () => string) => {
  order.push('L3')
  const r = next()
  return `${r} +L3`
})

const result = ctx.waterfall('seal', '戊', () => '默认行为')
console.log(order)    // 推演输出：['L1-前', 'L2', 'L3', 'L1-后']
console.log(result)   // 推演输出：'[默认行为 +L3 +L2]'
```

推演过程：⑦ 步 `next()` 进入 L1，L1 打印 `L1-前` 后调 `next()`（④ 步 `shift` 到 L2）→ L2 打印后调 `next()` → L3 打印后调 `next()` → `cbs` 已空，`?? inner` 调用默认行为，得 `'默认行为'` → 逐层返回：L3 得 `'默认行为 +L3'`，L2 得 `'默认行为 +L3 +L2'`，L1 套上自己的方括号得 `'[默认行为 +L3 +L2]'` 并打印 `L1-后`。

两个值得留意的推论：

- **最外层监听器先挂、最后返回**：`order` 显示 L1 的"前"在 L2、L3 之前，"后"却在最后——洋葱的壳比芯早进晚出。所以包裹顺序 = 注册顺序（`prepend: true` 可反转），返回值则从内向外传播。
- **不听 `next()` 的后果**：若把 L1 改成 `return 'L1 决定'` 且不调用 `next()`，则 `order` 为 `['L1-前']`，`result` 为 `'L1 决定'`；L2、L3、默认行为全部未执行——这就是否决。任何一个"我在 L1 里改个参数再放行"的监听器，都必须写成 `const r = await next(); return {...r, 改动}` 的形式。

## 4.9 内置事件逐行走读：interface Events

全部九个内置事件声明在 `vendor/cordis/src/events.ts:329-352`，逐个分类如下：

| 事件 | 模式 | 触发时机 | 监听器职责 |
|---|---|---|---|
| `internal/plugin` | `emit` | 插件 fiber 创建或其 uid 被清空时（`vendor/cordis/src/events.ts:331`） | 观察插件装配 |
| `internal/status` | `emit` | fiber 生命周期状态迁移时，参数带上旧状态（`vendor/cordis/src/events.ts:333`） | 观察 PENDING→…→DISPOSED 的迁移（第 3 章 3.4） |
| `internal/config` | `waterfall` | 注入激活后解析插件原始配置（`vendor/cordis/src/events.ts:339`） | 改写配置；`next` 为默认解析 |
| `internal/service` | `emit` | 服务绑定被拦截时，无默认生产者（`vendor/cordis/src/events.ts:341`） | 观察依赖注册 |
| `internal/update` | `waterfall` | 插件配置更新被应用时（`vendor/cordis/src/events.ts:343`） | 拦截更新；不调 `next()` 即否决；4.7 节 ④ 的特殊装载 |
| `internal/get` | `waterfall` | 通过上下文代理读取服务时（`vendor/cordis/src/events.ts:345`） | 拦截读取（按名取服务） |

| `internal/dispatch` | `emit` | 每次公开事件分发前（`vendor/cordis/src/events.ts:351`，仅非 `internal/` 事件，见 168-170 行） | 诊断、监控 |

这张表的触发方同样值得盘点：`internal/listener` 与 `internal/update` 的处理逻辑由 `EventsService` 构造器自己挂载（`vendor/cordis/src/events.ts:140-155`）；其余分别由 fiber（`internal/plugin`，`vendor/cordis/src/fiber.ts:302`；`internal/status`，`vendor/cordis/src/fiber.ts:586`；`internal/config`，`vendor/cordis/src/fiber.ts:642`）、反射层（`internal/get`，`vendor/cordis/src/reflect.ts:153`；`internal/set`，`vendor/cordis/src/reflect.ts:191`；`internal/service`，`vendor/cordis/src/reflect.ts:333`）与事件总线自身（`internal/dispatch`，`vendor/cordis/src/events.ts:169`）触发。至此可以补全第 3 章遗留的一个疑问：状态的迁移与插件的装配本身也在事件系统里——`internal/status` 是 fiber 状态机对外发布的"观测口"，`internal/plugin` 是插件装配的观测口。整个框架内建在事件系统之上，插件系统与事件系统互为表里。

**一处教材式的审校观察**：`internal/listener` 的声明（`vendor/cordis/src/events.ts:349`）把第 4 个参数标注为 `prepend: boolean`，但实现侧传入的是 `options` 对象（`vendor/cordis/src/events.ts:296`），构造器内置处理器也按 `EventOptions` 结构读取 `global`/`prepend`（`vendor/cordis/src/events.ts:140-146`）。（推断：接口注释滞后于实现，实现已把参数泛化为选项对象。）读者在扩展 `internal/listener` 时应以 `options` 对象为准。

## 4.10 dsh 的真实事件：声明合并、作用域与三类用法

### 声明合并：子系统事件从哪来

dsh 的事件全部声明在各自子系统包里，统一通过一次接口合并进入 cordis 的 `Events`（4.2 节 ③ 的机制）：`packages/core/agent/src/runtime-types.ts:146`、`packages/core/tools/src/index.ts:137`、`packages/llm/llm/src/index.ts:46` 各自写着 `declare module '@deepseek-ai/cordis' { interface Events { ... } }`。例如 `llm/stream`：

```ts
declare module '@deepseek-ai/cordis' {
  interface Events {
    'llm/stream'(this: LlmRuntime, options: GenerateOptions, next: () => AsyncIterable<StreamChunk>): AsyncIterable<StreamChunk>
  }
}
```

（`packages/llm/llm/src/index.ts:46-64`）：声明合并从 46 行开始，`llm/stream` 事件体在 62-64 行落下 `@mode waterfall` 标签。**为什么事件声明放在子系统包而不是 cordis**？因为事件是子系统的公开契约，随包发布、随包版本化；声明里的 `@mode waterfall` 标签（`packages/llm/llm/src/index.ts:62`）把"本项目约定用哪种分发"写在了类型旁边——4.4 节说过模式本是分发时选择，这里用标签把它钉死为约定。

### 作用域：只有该收到的人收到

4.3 节 第 4 步的 `Context.filter` 在 dsh 里的实现位于 `packages/core/scope/src/index.ts:170-183` 的 `scopeTarget`：它构造一个"载体"对象（carrier），载体上带着 `Context.filter` 函数，逻辑是——先沿用基座对象（agent 或服务）自带的过滤器；再取监听器注册上下文的 scope 标签（`scopeOf`，`packages/core/scope/src/index.ts:154`）；**没标签的监听器视为全局**（谁都收）；**有标签的，只有当标签是分发键本身或它的祖先时放行**（`packages/core/scope/src/index.ts:177-179` 沿 `scopeParents` 的祖先链回溯）。注释点明了方向性："事件沿链条向上流动，绝不向下"（`packages/core/scope/src/index.ts:159-164`）——一个顶层组合（如编排多个 agent 的调度器）能收到它名下每个 agent 的事件，而 agent 内部插件收不到兄弟 agent 的事件。载体就是 `ctx.waterfall(carrier, ...)` 里那个被 `dispatch` 认作 `thisArg` 的第一个参数。

### 三类用法：环绕、按序、通报

**① waterfall 的"环绕"——`agent/pre-step` 与 `agent/request`**

`agent/pre-step` 声明为 waterfall（`packages/core/agent/src/runtime-types.ts:231`），分发点在每开始一个 step 前（`packages/core/agent-loop/src/agent.ts:234-240`）：

```ts
const decision = await this.dispatch.waterfall(
  'agent/pre-step', { messages: claimed, ...position, signal },
  (): Promise<PreStepDecision> => Promise.resolve<PreStepDecision>({
    kind: 'enter',
    messages: context === undefined ? claimed : [...claimed, context],
  }),
)
```

默认行为（最后的箭头函数）是"进入 step，把组装好的上下文拼进消息"（`packages/core/agent-loop/src/agent.ts:236-239`）。一个插件想"拒绝这个 step"或"替换进入 step 的消息"，就注册监听器：不调 `next()` 直接返回 `{ kind: 'reject' }`，或者 `const d = await next(); return { ...d, messages: 改写后的 }`。同样的套路还出现在 `agent/request`（换掉模型调用配置，`packages/core/agent-loop/src/agent.ts:438-441`）与 `agent/request-error`（接管失败重试，`packages/core/agent-loop/src/agent.ts:355`）——三个决策点全是 waterfall，因为决策语义天然是"层层环绕，最内层才是默认"。

`llm/stream` 是同一套路的模型侧版本：`stream()` 委托给 `streamWithRegistration`，后者就是一句 `this.ctx.waterfall(this, 'llm/stream', options, () => this.adapterStream(options, prepared))`（`packages/llm/llm/src/index.ts:917-926`）——**默认行为是"调用已解析的适配器取流"**。重试、重放、路由等插件各自 `await next()` 包装 chunk 流，或整段替换成自己的流（`packages/llm/llm/src/index.ts:62-64` 注解说"yield your own chunks to short-circuit"）。注意到它的 `this` 是 `LlmRuntime` 本身（`llm/stream` 声明里的 `this: LlmRuntime`，`packages/llm/llm/src/index.ts:64`），这与 agent 事件用"载体"做 `this` 略有取舍：服务对象自身即载体，订阅方拿到的是运行时实例。

**② serial 的"按序观察"——`agent/turn-stopping`**

turn 即将关闭时，机器按顺序 `await` 所有监听器（`packages/core/agent-loop/src/agent.ts:296`）：`await this.dispatch.serial('agent/turn-stopping', { turn, signal })`。事件声明为 `Promise<void> | void`（`packages/core/agent/src/runtime-types.ts:278`）——监听器用返回值表达"我反对/我接管"（4.6 节 坑 2：非 `undefined` 即为反对），否则什么都不返回。这里用 `serial` 而非 `waterfall` 的理由很微妙：**它不是为了"改造"什么，而是按顺序让每个观察者表态**；数据决定胜负（谁来动手改状态），而 listener 顺序不应能改变结果——这正是 `@mode serial` 注释里"listener order cannot change the outcome"（`packages/core/agent/src/runtime-types.ts:266-278`）的含义。

**③ waterfall 的四连——tools 的全链路**

工具执行链路上挂的四件事（`packages/core/tools/src/index.ts:150-197`）是全链路示范：`tools/pre-execute` 门禁（默认 `allow`，可 deny/ask，`packages/core/tools/src/index.ts:150-152`；分发在 `1475-1478`），`tools/execute` 环绕真正的工具体（默认就是 `dispatchToolBody`，`packages/core/tools/src/index.ts:161-163`；分发 `1573-1576`），`tools/post-execute` 改写/阻止归一化结果（`packages/core/tools/src/index.ts:173-175`；分发 `1743-1746`），`tools/result` 则回归 `emit`——只是**观察**被冻结的最终结果（`packages/core/tools/src/index.ts:195-197`；分发 `1665-1667`）。注意 `tools/result` 的分发点没有直接调用 `ctx.emit`，而是 `this.ctx.events.dispatch('emit', [...])` 拿到回调数组后**逐个 `try/catch`**（`packages/core/tools/src/index.ts:1668-1675`）——因为 `emit` 的一个同步抛错会饿死后续观察者（4.3 节），而"结果观察者"恰恰最不该互相干扰。

**融合分发器的容错重写——agent 的 `emit`**

dsh 在 agent 侧把这种容错升级成了正式 API：`agentEvents`（`packages/core/agent/src/dispatch.ts:107-149`）返回的融合分发器（fused dispatcher）中，`emit` 被完整重写——注释直言：Cordis 的 `emit` 通过 `Array.map` 调用回调，一个同步抛错会饿死后面的监听器，返回的 Promise 被丢弃；既然 agent 通知（notification）是**非否决**的，那就自己解析同一份过滤后的回调集合，分别孤立这两种失败模式（`packages/core/agent/src/dispatch.ts:120-137`：`try/catch` 包同步抛错、`Promise.resolve(returned).catch` 收 Promise 拒绝，都交给 `ctx.logger.warn`）。而 `serial`/`waterfall` 只是把（载体, 事件名, 已注入 `agent` 的负载）转发给 `ctx.serial` / `ctx.waterfall`（`packages/core/agent/src/dispatch.ts:138-147`）。这样设计的意义还在类型上：`agentEvents` 在构造时就把"载体"与"事件负载里的 `agent` 字段"绑定（`packages/core/agent/src/dispatch.ts:113-118`），调用方只传负载其余部分，杜绝了"载体与负载中的 agent 不一致"的可能。

## 4.11 事件总线的归属：Cordis 自研，与 cosmokit 无关

一个常见猜测是"事件总线来自 cosmokit 的工具库"。事实并非如此：`@deepseek-ai/cosmokit` 只导出 `array`/`string`/`time`/`misc`/`types` 等工具模块，**没有 Emitter**（`vendor/cosmokit/src/index.ts`）。`EventsService` 对 cosmokit 唯一的借用发生在 `vendor/cordis/src/events.ts:1` 的 `defineProperty`（用于给服务打 `symbols.tracker` 标记，`vendor/cordis/src/events.ts:135-138`；`defineProperty` 本身定义在 `vendor/cosmokit/src/misc.ts:72`）。事件总线是 Cordis 的核心自研组件：**fiber 负责注册与撤销，事件系统负责投递与协作**，二者皆非外借。

## 小结

本章的核心是一条主线与一张表：

- **主线**：事件是"命名 + 多监听器"的扩展点；`dispatch()`（`vendor/cordis/src/events.ts:165-175`）以相同的方式获取回调数组（thisArg 提取、`internal/` 特判、`Context.filter` 作用域过滤、绑定），五种模式只改变"对回调数组的调用策略"（`vendor/cordis/src/events.ts:183-243`）：`emit` 同步不等待、`parallel` 并发聚合、`serial` 逐个等待遇 bail 即停、`bail` 同步遇 bail 即停、`waterfall` 用共享 `next` 闭包把监听器串成洋葱。
- **两张保障**：`isBailed`（`vendor/cordis/src/events.ts:13-15`）把"短路"定义为"非 `null`/`false`/`undefined`"，制造了 4.6 节两个必须记住的坑；`register` 经 `ctx.fiber.effect` 使监听器随 fiber 卸载自动注销（`vendor/cordis/src/events.ts:254-260`、第 3 章 3.5），消灭了"幽灵监听器"。
- **落到 dsh**：子系统通过声明合并注册事件（`packages/core/agent/src/runtime-types.ts:146` 等），用 `@mode` 标签固定分发模式；作用域经 `scopeTarget` 的载体过滤器实现"事件只向上流"（`packages/core/scope/src/index.ts:170-183`）；agent 的融合分发器重写了 `emit` 的容错（`packages/core/agent/src/dispatch.ts:120-137`），并把四个工具事件与三个 agent 决策点分别做成了门禁/环绕/观察三种形态。

## 分层练习

**基础**：1. 用 `isBailed` 的定义（`vendor/cordis/src/events.ts:13-15`）判断以下返回值是否短路：`0`、`''`、`NaN`、`null`、`false`、`undefined`、`Promise.resolve()`、`{}`。2. 写出 `dispatch()` 的五步流程，并说明 `hook.global`、`Context.filter`、`hook.ctx` 三个量各自在过滤中扮演什么角色。3. `once` 注册的监听器在第一次调用时发生了什么（`vendor/cordis/src/events.ts:312-318`）？为什么它不需要调用方手动 `dispose`？

**进阶**：4. 假设 `ctx.on('seal', ...)` 三个监听器分别同步抛错、返回被拒的 Promise、正常返回——分别描述 `emit`、`parallel`、`serial` 三种分发下会发生什么（对照 `vendor/cordis/src/events.ts:184-186`、`vendor/cordis/src/events.ts:195`、`vendor/cordis/src/events.ts:205-207`）。5. 画出 4.8 节示例中 `next` 每次调用后 `cbs` 的内容与 `order` 的变化；如果把 L2 改成不调 `next()` 直接返回 `'L2 拦截'`，`order` 与 `result` 各是什么？6. 阅读 `packages/core/agent-loop/src/agent.ts:438-441` 与 `packages/core/agent/src/runtime-types.ts:244`：解释为什么 `agent/request` 必须用 waterfall 而不能用 serial。（提示：考虑"改写配置"与"短路"两种语义。）

**挑战**：7. `internal/update` 的监听器为什么存放在 `fiber._hooks` 而不是全局 `_hooks`（`vendor/cordis/src/events.ts:140-155`）？试用第 3 章的 fiber 生命周期解释"fiber 卸载后它的更新监听器随之消失"对热重载的意义。8. `tools/result` 的分发点（`packages/core/tools/src/index.ts:1665-1675`）与 `packages/core/agent/src/dispatch.ts:120-137` 的 agent `emit` 都在手动容错——如果把这两处都换成 `ctx.emit`，分别会出现什么可观察的行为回归？9. 为你的插件设计一个"登录前校验"事件：声明它并用 `serial` 分发，要求"第一个校验失败的监听器使登录中断"，并验证 `isBailed` 的边界（如返回错误码 `0` 是否会导致误判）。
