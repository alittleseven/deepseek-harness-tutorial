# 第 8 章　会话日志：仅追加事件流与"模型可见即已记录"

> **本章学习目标**（读完本章，你应该能够）：
> 1. 说出 `SessionEventMap` 的全部事件类型，并把任意一条事件正确归类为"边界 / 模型可见 / 日志专用"三类之一；
> 2. 用三条理由论证 `deriveMessages` 为什么必须从日志投影，而不是维护一份缓存的消息数组；
> 3. 推导"新增模型可见输入必须新增会话事件"扩展规则的由来，并判断一个提案该做成表面事件还是日志专用事件；
> 4. 解释 surface 节点、`ignorable`、`sourceEventSeqs`、`surfaceOp` 各自解决的问题，以及它们如何让 compaction 不必重写日志；
> 5. 说明"回放 / 恢复 / fork"为什么只是同一事件流的不同走法，并指出每条路径共同经过的一致性闸门。
>
> **本章讲法**：数据流逆推型。我们不按"类型定义 → 方法"的说明书顺序讲，而是从一次流式输出中最小的一个产物——一条 `assistant/chunk` 事件是怎么出生、怎么被消费的——往回追：谁写它（8.3），谁读它（8.4），凭什么它们说的是一回事（8.6），这套结构又让回放、恢复与 fork 成为可能（8.7）。8.2 先补词汇表，8.5 讲表面机制。**前置**：第 4 章（事件分发的五种模式）；第 9 章（Agent Loop 如何消费这些事件）可后置阅读。

## 8.1 现场：一次流式输出留下了什么

设想一个最普通的场景：你给 dsh 发了一句"帮我把这个文件夹里的测试跑一遍"。模型流式输出，屏幕上的 token 一个接一个冒出来；输出里出现一个工具调用，工具执行、结果写回；模型接着输出，若干轮后任务完成。

把镜头放慢，问一个看起来很简单的问题：**模型第二轮开始时"看到"的历史消息，是谁、在哪里、以什么形式维护的？**

最直觉的答案是"内存里有个消息数组，每轮往里 push"——大多数玩具 demo 正是如此。它有两个毛病：第一，第一轮的**流式中间过程**（逐 token 的 chunk）丢了，一旦要重放（把会话恢复出来接着聊），只能重建一个"近似"历史；第二，数组是"活"的，拿到引用的代码都能改，而它又是模型请求的唯一输入——改一处，模型看到的就跟当初不一样。

dsh 的答案是把问题倒过来：**不维护"消息数组"，只维护一条只增不改的事件日志（append-only event log），模型每次请求要用的消息历史，都是当下从日志里推导（derive）出来的**。这是数据库教科书级的思路（日志即真相、视图由日志推导），但 dsh 有三个实现细节值得细看：怎么保证**坏数据进不了账**（8.6）、怎么让推导**从日志而不是缓存里来**（8.4）、以及怎么让"删除历史"（compaction）**不改一行旧日志**（8.5）。

日志里最小的一类记录是流式 chunk（`packages/core/session/src/types.ts:266`：`'assistant/chunk': { turn; step; chunk: StreamChunk }`），注释写着 **token-level replay fidelity**（token 级重放保真度）：chunk 不是"中间过程"，它本身就是要被持久化的真相——若日志只存"组装好的 assistant/message"，重放时永远无法还原"模型当时逐字吐了什么"。这条注释的"上游"是 `packages/core/session/src/types.ts:231-234` 对日志本身的定位：

> The merge-extensible, append-only source of truth for an agent interaction. Message history is derived from this log. Every event is lossless JSON and sequence numbers stay contiguous, including raw chunks, so persistence can store the canonical log verbatim.

关键词是 **source of truth**（唯一真源）：日志里存的是"发生的事实"，而非"某个阶段的结果"。理解了这一点，8.2 词汇表就顺理成章——先看事实有哪几类。

## 8.2 词汇表：一条会话事件的全身检查

### 8.2.1 从流水说起：event、session、turn、step、message

先建立直觉（① 类比）。打开一家银行的账户：**流水（statement）** 是只追加、永不修改的记录列表；每一条流水（transaction）记着"什么时候、发生了什么、金额多少"。账户的"当前余额"没有人维护——柜台只维护流水，余额是"把流水按规则合计出来"的**投影**。日志与消息历史的关系，就是流水与余额的关系。

再精确定义（②）。dsh 里：

> **session（会话）**：一次 agent 交互的全量事件日志及其生命周期（`packages/core/session/src/types.ts:231-234`）。有唯一 id（`packages/core/session/src/types.ts:96-100`，`SessionId` 品牌类型）与首条实况序号 `firstLiveSeq`。
>
> **event（事件）**：日志里的一条记录，键是类型（如 `'turn/start'`），值是类型专属的数据。定义 `SessionEvent`，见 `packages/core/session/src/types.ts:404-436`。
>
> **turn（轮次）**：一次"领取输入 → 执行一轮循环 → 关闭"的完整单位，由 `turn/start` 与 `turn/end` 一对事件括起来；一轮里可以有**零个或多个** step（`packages/core/session/src/types.ts:238-252`）。
>
> **step（步骤）**：一轮里的一次"模型请求 + 它引发的工具执行"，由 `step/start` 与 `step/end` 括起来（`packages/core/session/src/types.ts:253-256`）。一次模型流式输出 + 若干工具调用 = 一个 step。
>
> **message（消息）**：模型可见历史中的一条：`user`、`assistant` 或带工具结果块的 `user` 角色消息（`packages/llm/llm/src/message.ts:129-156`）。message 是**推导产物**而非日志成员——日志里只有产生它的"事实"。

最后给最小示例（③）。一条真实的 `turn/start` 事件在 JSON 里长这样（字段含义见 8.2.2）：

```json
{ "type": "turn/start", "seq": 12, "time": 1766409600123, "data": { "turn": 3 } }
```

### 8.2.2 统一信封：`SessionEvent` 的形状

`SessionEvent` 不是一把"类型 + 泛型数据"的散装对象，而是一个**按 `type` 判别的联合类型（discriminated union）**（`packages/core/session/src/types.ts:391-403` 注释：`switch (event.type)` 会自动收窄 `event.data`，无需断言）。它每个成员都有四个公共字段（`packages/core/session/src/types.ts:404-411`）：

- `type`：事件类型键；
- `seq`：会话内单调递增的序号。**连续性契约**：`seq === log.length`（写端 `packages/core/session/src/index.ts:629`；读端 `Session.seq` getter 见 `packages/core/session/src/index.ts:564-567`）——没有空洞、没有乱序；
- `time`：Unix 毫秒时间戳；
- `data`：类型专属载荷。

另有三个条件字段（`packages/core/session/src/types.ts:412-435`）：

- `ignorable?: true`：见 8.2.4；
- `surfaceOp` 与 `sourceEventSeqs`：只出现在三类模型可见事件上，见 8.5。

### 8.2.3 词汇表：`SessionEventMap` 的十三种事件

`SessionEventMap`（`packages/core/session/src/types.ts:236-333`）是全部事件类型的花名册。把 13 种事件按"对模型可见性/重放的意义"分为三类——这个三分类是本章骨架：

| 类别 | 事件 | 作用 | 谁会读它 |
|---|---|---|---|
| **边界**（生命周期） | `turn/start`（packages/core/session/src/types.ts:243）、`turn/end`（:252）、`step/start`（:254）、`step/end`（:256）、`session/end-seed`（:332） | 括出轮次/步骤/种子边界；`turn/end` 携带结束原因 `reason`（见下） | replay、恢复、fork、UI 时间线 |
| **模型可见**（surface 事件） | `user/message`（packages/core/session/src/types.ts:264）、`assistant/message`（:273）、`tool/result`（:291-297） | 恰好是 `SurfaceEventType`（`packages/core/session/src/types.ts:343-346`）——三种**进入投影历史**的事件 | `deriveMessages`、UI、重放 |
| **日志专用**（log-only，痕迹数据） | `assistant/chunk`（packages/core/session/src/types.ts:266）、`tool/call`（:279）、`todo/write`（:299）、`request/header`（:304）、`request/context`（:309） | 只进日志、不进模型历史；保证回放保真或支撑"最新快照"重建 | 回放、标题生成、UI、第 9 章请求构建 |

几个字段的分量，挑关键的看：

- `user/message`（`packages/core/session/src/types.ts:257-263`）：模型可见的用户消息有三类来源——人类直接提问（本轮认领的排队消息）、`agent.inject()` 合成的上下文（文件变更、子目录 AGENTS.md、技能内容、cron 通知……）、目标延续轮；三者 content 逐字投影，靠 `source` 区分。
- `tool/call`（`packages/core/session/src/types.ts:274-279`）：`arguments` 是**模型产出的原始 JSON 字符串，未解析**——解析是"读端"的事，日志只存事实（第 9 章 `parseArguments` 失败时保留原文，`packages/core/agent-loop/src/tool-calls.ts:103-110`）。
- `tool/result`（`packages/core/session/src/types.ts:280-297`）的三个可选字段是设计重点：`error?: { name, code }` 是**内部错误标识**（失败是事实）；`meta?: JsonValue` 是**工具私有的展示载荷**，对核心不透明（如 `dsh-tool-fs` 携带的结果时上下文 diff），但必须 JSON 可序列化——`Session.append` 运行时校验，不合格直接拒绝入账（8.6.1）。
- `todo/write`（`packages/core/session/src/types.ts:298-299`）：整表快照、last-write-wins，**纯日志 UI 状态**；`TodoItem` 是 `content + status(pending|in_progress|completed)`（`packages/core/session/src/types.ts:189-194`）。
- `request/header`（`packages/core/session/src/types.ts:300-304`）：下一个请求的**完整**请求头快照，写在自己的 step 内、dispatch 之前；最新快照重建请求头，`reason` 为 `'initial' | 'resume' | 'change'`（`packages/core/session/src/types.ts:228`）。`request/context`（:305-309）则只在路由变化时记，**不参与请求重建、不参与 header 相等比较**——它回答"这次请求走了哪个提供方"。
- `session/end-seed`（`packages/core/session/src/types.ts:310-332`）：种子结束标记，载荷为空，**只有 `Session` 构造器能写**；深层语义见 8.7.2。

`turn/end` 携带的 `reason: TurnEndReason` 是第 9 章状态机的"结算单"，这里先认识值域（`packages/core/session/src/types.ts:155-174`）：`completed`（正常完成）、`aborted`（取消）、`blocked`（输入被 pre-step 拒绝）、`error`（LLM 失败拍平为 `LlmFailure` 或 `UNKNOWN`）、`max-tokens`（撞顶）、`interrupted`——最后这个**只有持久化后端在恢复时合成**（后端发现"孤儿轮次"：文件里轮次开着但生产它的 loop 已死，`packages/core/session/src/types.ts:155-156`），Agent Loop 从不发它。

### 8.2.4 扩展与兼容：`ignorable` 与版本号

日志是**可合并扩展**的（merge-extensible）：`SessionEventType = keyof SessionEventMap`（`packages/core/session/src/types.ts:335-336`），插件可以向 `SessionEventMap` 合并新类型，`Session.append(type, data)` 的类型参数是开放的。开放意味着一个风险：**旧版本读者遇到新类型事件怎么办？**

答案为 `ignorable?: true`（`packages/core/session/src/types.ts:412-422`）：

> Marks an event a reader may safely skip when it does not recognize `type`. Absent means required: a reader meeting an unrecognized type without this marker MUST refuse to reconstruct the session instead of silently dropping the event.

默认是"必须认识"（over-refuse，宁可拒绝也不带病重建）。**这是刻意的默认值**：忘了打标记会让旧版本读者过度拒绝（不便）；反过来"默认可忽略"会让旧版本读者悄悄重建残缺会话（错误）。两害相权，"不方便"优于"伤数据"。

有了 `ignorable` 兜底，版本号保持简单：`SESSION_FORMAT_VERSION = 0`（`packages/core/session/src/types.ts:56`），单整数、不分主次。决策规则（`packages/core/session/src/types.ts:33-55`）：**只新增普通事件类型不 bump**（交给 `ignorable`），**只有结构变化才 bump**。

## 8.3 写入端：`Session.append` 的七步走读

现在回答 8.1 的第一个问题：谁写日志？答案是唯一的公开写入口 `Session.append`（`packages/core/session/src/index.ts:604-655`）——Agent Loop、工具链、inbox、compaction 等所有写入方最终都调它。签名先看（`packages/core/session/src/index.ts:604-608`）：

```ts
append<T extends SessionEventType>(
  type: T,
  data: SessionEventMap[T],
  ...opts: T extends SurfaceEventType ? [opts: SurfaceIntent] : []
): SessionEvent<T>
```

注意这个类型技巧：**只有当 `type` 是三类 surface 事件之一时，第三个参数 `SurfaceIntent` 才存在**——非表面事件强制不携带 `surfaceOp`，编译期就拦住了"给 `turn/start` 传 surface 元数据"这类错误（`packages/core/session/src/types.ts:397-402` 注释）。`SurfaceIntent` 的形状见 8.5.2。

逐段走读实现，**七步，顺序都是有意为之的**：

**第一步：组装 surface 元数据（packages/core/session/src/index.ts:610-613）。** 把 `surfaceOpts` 里的 `sourceEventSeqs`/`surfaceOp` 摊平成 `surfaceMetadata`——注意它和 `data` 分开处理，因为 `data` 是业务载荷，`surfaceMetadata` 是编排元数据，两者都要进 JSON 校验。

**第二步：无损 JSON 校验 + 拷贝（packages/core/session/src/index.ts:614-617）。** `const dataSnapshot = snapshotJsonValue(data)`，返回 `undefined` 即抛错"carries non-JSON-serializable data"。这里不是"验证一下再存原引用"，而是**读一遍、验一遍、拷一份**——`snapshotJsonValue` 的语义在 8.6 展开，此处只需记住：带 getter 的属性只被调用一次，注释原文说 "a stateful getter cannot supply one value to validation and another to storage"（有状态的 getter 不可能一边给校验一边给存储，因为校验与拷贝是同一次遍历的同一份数据）。坏数据**在 append 现场就失败**，而不是等后端 flush（`packages/core/session/src/index.ts:599-600`）。

**第三步：兼容性拒绝（packages/core/session/src/index.ts:618）。** `assertSupportedRequestHeader`（定义 `packages/core/session/src/index.ts:363-372`）拒绝历史遗留的 `request/header-delta` 格式与 `reason: 'fallback'`——写入方必须在写入时就证明自己用的是新协议。

**第四步：surface 元数据校验（packages/core/session/src/index.ts:619-622）。** `surfaceMetadata` 同样要过 `snapshotJsonValue`——校验做到元数据层面。

**第五步：重入检查 + 事件冻结（packages/core/session/src/index.ts:623-633）。** `attachments` 是挂在 Session 实例上的 `WeakMap`（`packages/core/session/src/index.ts:415`），`entry?.appending` 为真即抛"cannot reenter"——**一次只能有一个 append 在发布中**（为何需要它，见 8.6 闸门四）。然后构造事件本体：`seq: this.log.length`（连续性契约）、`time: Date.now()`、`data: dataSnapshot`，并 `deepFreeze`。还有先行验证：`this.surfaceManager.validateNext(event)`（:634）在 `log.push` **之前**调用——候选事件先"计划"（plan），不合法就整体失败，日志一行不动。

**第六步：入账（packages/core/session/src/index.ts:636-647）。** 顺序是：`entry.appending = true`（:636）→ 收集监听器快照 `collectSessionCallbacks`（:641，解析时刻的 `ctx.events.dispatch('emit', ...)`，`packages/core/session/src/index.ts:377-379`）→ **`this.log.push(event)`（:643）** → 使 `eventsSnapshot` 失效（:644）→ 通知 `session/event` 观察者（:646）。关键顺序：**先入账、后通知**——观察者收到的每条事件必然已在日志中，不存在"通知了但日志里没有"的窗口（若先通知后入账，持久化插件可能把未入账的事件写进后端）。

**第七步：收尾（packages/core/session/src/index.ts:649-654）。** `finally` 里复位 `appending`，并在"此 entry 的 detach 被推迟"（`detachRequested` 且非 announcing）时执行 detach——"卸载与发布互不打断"纪律在日志层的复现（`packages/core/session/src/index.ts:650-654`）。

一句话总结本节"写入总纲"：**先规划（surface 校验）→ 再冻结 → 再入账 → 最后通知**；每步失败都发生在 `log.push` 之前，日志要么完全不变、要么已包含这条事件——后者又须在崩溃恢复时成立，即 8.6 的活。

## 8.4 读取端：为什么必须从日志投影

### 8.4.1 投影：把"事实"折叠成"视图"

（① 类比）回到银行流水：柜台从不记账"当前余额"，你要查余额就把流水从头到尾累加一遍。若柜台在每次取钱时**同时**维护一个余额缓存字段，就会出现两类事故：某个柜台忘了更新，或者两条流水同时到达——缓存与流水不一致。数据库界的标准答案是**视图（view）**：不物化，查询时现算。

（② 定义）dsh 的"视图"就是 `Session.deriveMessages()`（`packages/core/session/src/index.ts:726-747`）：遍历"表面节点"序列，把每个节点折叠成一条消息，返回**新数组**。它对应的纯函数形式是 `foldSurface`（`packages/core/session/src/surface.ts:387-395`）——给定事件数组，离线重建表面节点与替换历史，全程无副作用。

（③ 最小示例）三个事件的日志，投影一次：

```ts
session.deriveMessages()
// 事件流： turn/start → user/message(seq=1) → assistant/chunk×3 → assistant/message(seq=4)
// 投影结果： [user 消息, assistant 消息]   ← chunk 不产生任何消息
```

### 8.4.2 走读 `deriveMessages`

```ts
deriveMessages(): Message[] {
  const surface = this.surface
  const nodes = surface.nodes
  const generation = surface.replaceGeneration
  if (generation !== this.derivedGeneration) {
    this.derived = []
    this.derivedNodes = 0
    this.derivedGeneration = generation
  }
  for (const seq of nodes.slice(this.derivedNodes)) {
    const msg = this.deriveEventMessage(this.log[seq]!)
    if (msg) this.derived.push(msg)
  }
  this.derivedNodes = nodes.length
  return [...this.derived]
}
```

（`packages/core/session/src/index.ts:726-747`，省略了一行 oxlint 注释）

四个要点，与直觉不同之处都在注释里：

1. **它确实有缓存，但缓存的是投影结果、不是消息数组的"另一份维护者"。** `derived`/`derivedNodes`（`packages/core/session/src/index.ts:701-706`）做增量投影：每个 surface 节点只投影一次，之后每次调用只处理新节点，成本 O(新节点数)（`packages/core/session/src/index.ts:717-719`）。与"维护一个消息数组"的本质区别：**它自己从不被写入方更新**——唯一让它失效的是 `replaceGeneration` 变化（某次 `replace`，`packages/core/session/src/index.ts:730-734` 整表作废重建）。
2. **返回的是新数组、共享的冻结消息。** `return [...this.derived]`：调用方拿到的数组是快照，之后日志再追加也不会让已持有的数组变长（`packages/core/session/src/index.ts:719-721`）；数组里的 `Message` 对象**共享且深冻结**，内容复用事件里已冻结的 `data`，无需二次深拷贝（`packages/core/session/src/index.ts:721-723`）——消费方仍无法篡改日志。
3. **逐节点投影规则是 `deriveEventMessage`**（实例面 `packages/core/session/src/index.ts:755-757`，纯函数 `packages/core/session/src/surface.ts:83-114`）：`user/message` → 返回 `event.data` 本体（逐字透传，注释强调**不得重新加框架**——`<context>` 这类包装由生产者自己烘进 `content`，`packages/core/session/src/surface.ts:88-95`）；`assistant/message` → 返回 `message`，但**空 content 返回 `null`**（`:100-104`：只为承载 usage 的消息不得把无内容 assistant 塞进 transcript——第 9 章 max-tokens 的关键）；`tool/result` → 返回 `event.data.message`；**其余全部 `null`**——边界、chunk、usage、错误都是 trace/replay 数据（`packages/core/session/src/surface.ts:83-86`："Intentionally non-exhaustive"）。
4. **"表面节点"是由 `surfaceOp` 标注的序列，不是"所有事件"**：这就是 8.5 的主题。

### 8.4.3 为什么不能维护一份缓存消息数组——三个反例

把"投影"换成"缓存数组"会怎样？设想写入方每轮把新消息 push 进 `messages` 数组，读侧直接用它。三个反例逐一击破（每个都能在源码里找到对应的"如果……"）：

**反例一：追加点不止一个。** `user/message` 的写入方有 loop（认领输入）、inbox（注入上下文）、目标系统（延续轮）……（`packages/core/session/src/types.ts:257-263` 三类来源）；`assistant/message` 由 loop 写；`tool/result` 由工具链写。让每个写入方在写日志之外**再**更新缓存，等于把"一致性"交给"所有写入方的共同纪律"——一次遗漏，历史与日志从此分叉，且无检查能发现。

**反例二：删除。** 缓存数组只能追加，而 compaction（第 14 章）会**替换中间的一组节点**——数组中间删除是 O(n)，持旧引用的读者还会看到"半新半旧"的历史。投影方案里，`replace` 只让 `replaceGeneration` +1、缓存整表作废重建（`packages/core/session/src/index.ts:730-734`），持旧引用的读者拿到"重构前的完整快照"——干净。

**反例三：重建路径只有一条。** 恢复、fork、replay（8.7）拿到的只是一串事件，也必须得到与 live session **完全一致**的消息历史——它们能用的唯一资料来源就是事件。因此"事件 → 消息"的折叠必须是**纯函数、离线可算、且唯一**：live 用 `deriveMessages`，重建用 `foldSurface` + `deriveEventMessage`（`packages/core/session/src/surface.ts:387-395`、`packages/core/session/src/request-header.ts:65-71`）。若 live 侧另有"缓存数组"这份真源，重建侧永远不可能与它一致。

### 8.4.4 扩展规则：模型可见即已记录

把 8.4.2 与 8.4.3 合成一条**运行时不变量**（这是本章的题眼）：

> **凡是模型在当前或未来请求中能看到的消息，必然对应日志里的一条表面事件；反过来，任何想进模型历史的输入，都必须先通过 `Session.append` 写进日志。**

它的两个方向的推论都值得背下来：

- **正向**（"已记录 ⇒ 可见"）：`deriveMessages` 的输入只有日志，所以"日志里没有的，模型绝不能看到"——这解释了为什么 `agent/pre-step` 的改写（第 9 章）最终也要落成 `user/message` 事件，而不是直接改内存数组。
- **反向**（"可见 ⇒ 已记录"）：要给模型提供**任何**新的可见输入，必须**新增一种会话事件类型**（在 `SessionEventMap` 上合并扩展），并在 `deriveEventMessage` 里给出投影规则——**不允许**"绕过日志直接塞进 messages 数组"。它把"新输入"从"写一个函数"变成"定义事件 + 定义投影"两件事；代价是工作量稍大，收益是**可回放、可恢复、可审计**全部免费获得。

（一个反向"反例"钉牢边界：`request/header` 里的 system prompt 与 tools 也是模型可见输入，但**不是事件**——载体是请求头，重建走 `foldRequestHeader` 而非 `deriveMessages`。可见输入有两条通道：消息通道（surface 事件）与请求头通道（`request/header` 快照）；第 9 章 `buildRequest` 两者都会用到。）

### 8.4.5 两个折叠：`requestHeader` 与 `requestContext`

消息历史之外，会话日志还支撑两类"最新快照"查询，都是同样的折叠思想（增量、只读）：

- `Session.requestHeader()`（`packages/core/session/src/index.ts:670-680`）：把 `request/header` 事件折叠成**当前生效的请求头**，是纯函数 `foldRequestHeader`（`packages/core/session/src/request-header.ts:65-71`）的增量形式："each header event is folded once, when first seen, so a per-step read costs O(new events)"。折叠结果 `deepFreeze`（`:672-675`：折叠是按引用暴露的会话状态——原地改它而非构建替换，后续比较都会失步，所以**突变直接抛错**）。`canonicalHeader`（`packages/core/session/src/request-header.ts:21-31`）把空 system/tools 归一为缺省，`headerEquals`（`packages/core/session/src/request-header.ts:44-54`）逐字段比较（config 用 `callConfigEquals`、tools 按序 JSON 对比）。
- `Session.requestContext()`（`packages/core/session/src/index.ts:691-699`）：只折叠 `request/context`，返回最近一次路由元数据。

对第 9 章一句话预告：loop 每次请求前调用 `requestHeader()`，与"这次想用的头"比较，**不等才写 `request/header`（reason: 'change'）**——"压缩日志"与"可重建"在此握手。

## 8.5 表面：让"模型可见"可以回答的三件事

### 8.5.1 为什么需要表面：投影数据与痕迹数据的分界

日志里大部分事件**不该**变成模型历史：chunk 是 token 级重放数据、`tool/call` 是调用记录、`todo/write` 是 UI 状态、`turn/start` 是边界。若投影规则是"每种事件都投影"，模型历史就会被边界、chunk 与待办污染。dsh 引入第三个结构——**surface（表面）**：

> **Surface**：按模型可见顺序排列的**消息产生型事件序列**，由写入时携带的 `surfaceOp` 标注维护（`packages/core/session/src/surface.ts:136-142`）。它不是日志的子表，而是日志的一种**折叠索引**：`SessionSurface.nodes` 是当前表面事件序号的有序数组，`replaceGeneration` 是已提交的位置替换次数。

`deriveEventMessage` 的 `default → null`（`packages/core/session/src/surface.ts:109-113`）保证了"不是三类就不投影"，这是**投影层**的过滤；`SurfaceManager` 在**写入层**（`validateNext`）就拒绝"非表面事件携带 surface 元数据"（`packages/core/session/src/surface.ts:185-194`）——两层各守一道，痕迹数据永远进不了历史，表面事件永远带标记。

### 8.5.2 `surfaceOp`：三态与"如何进入表面"

`SurfaceOp`（`packages/core/session/src/types.ts:359-374`）是**一个 append 对表面的声明**：

```ts
export type SurfaceOp =
  | 'append'
  | { op: 'replace'; start: number; end: number }
```

- `'append'`：追加到尾部——`user/message`、`assistant/message`、`tool/result` 的常规路径；
- `{ op: 'replace', start, end }`：用本条事件**替换**从 `start`（含）到 `end`（含）的表面节点（`start === end` 即单节点替换）；**用得最多的是 compaction**（`packages/core/session/src/types.ts:365-370`：任何做位置替换的生产者都可用）。replace 事件的 `sourceEventSeqs` 必须包含**全部被遮蔽节点**（`packages/core/session/src/types.ts:367-370`、`packages/core/session/src/surface.ts:239-242` 的 `assertProvenance`——少列一个即拒绝）。

配套的 `SurfaceIntent`（`packages/core/session/src/types.ts:376-389`）：表面事件**必须**带 `surfaceOp`；`sourceEventSeqs` 可选，但 `assistant/message` 可为空数组（已知空 provider 流），其他表面事件若带则必须非空。

### 8.5.3 `sourceEventSeqs`：溯源的两副用途

`sourceEventSeqs` 是"这条消息由哪些更早事件产生"的声明（`packages/core/session/src/types.ts:424-431`）。三处典型使用：

- **`assistant/message` → chunkSeqs**：一条组装消息由哪些 chunk 拼成——重放时把 chunk 与消息关联起来（第 9 章 `step()`：`sourceEventSeqs=chunkSeqs`，`packages/core/agent-loop/src/agent.ts:381-390`）；
- **`tool/result` → [callSeq]**：结果对应哪次调用——`packages/core/agent-loop/src/tool-calls.ts:288` 写结果时带 `sourceEventSeqs:[callSeq]`（第 9 章）；
- **compaction replace → 全部被遮蔽节点**：声明"我遮蔽了谁"——`assertProvenance`（`packages/core/session/src/surface.ts:211-243`）强制校验：引用必须是**更早**事件（`packages/core/session/src/surface.ts:230-237`）、不得重复（`:232-234`）、replace 必须覆盖全部遮蔽节点（`:239-242`）。

### 8.5.4 compaction 的 replace 为什么不需要重写日志

传统方案里"压缩长历史"意味着**重写**存储——旧文件不可变，只能新开文件、复制前半段、拼接摘要。dsh 的 surface 方案让 compaction 的行为变成：**追加一条表面事件，带 `surfaceOp: { op: 'replace', start, end }`，`sourceEventSeqs` 列出被遮蔽的全部节点**。旧日志一行没改。

走一遍机制（`packages/core/session/src/surface.ts:350-379`）：`planSurfaceEvent`（:321-347）"先计划后提交"——校验 `seq` 连续、`surfaceOpOf`、`replacementRange`（:246-266，start/end 必须对应真实存在的表面节点）、`assertProvenance`、`assertToolResultRewrite`（:287-318：tool/result 的 replace 只允许改 content，且必须是唯一当前节点）；然后 `applySurfacePlan`（:362-379）真正变形：`append` 是 `push`，`replace` 是 `splice` 后 `replaceGeneration += 1`。提交后，`deriveMessages`（8.4.2 第 1 点）的 `generation` 不匹配即整表重建。

给一个具体走读：表面节点 `[1, 4, 8]`（三条消息），compaction 用 seq=20 的事件替换 `start=1, end=8`：

1. `validateNext(20号事件)`（`packages/core/session/src/surface.ts:421-429`）：先 `_processDelta()` 补折叠到当前，再对候选做 `planSurfaceEvent`——`replacementRange` 算出被遮蔽节点 `[1, 4, 8]`；
2. `assertProvenance` 要求 `sourceEventSeqs ⊇ [1, 4, 8]`，缺一即抛；
3. 提交后 `nodes = [20]`，`replaceGeneration = 1`；
4. 下次 `deriveMessages()` 发现 generation 变了，从 seq=20 重新投影——模型历史从此只有摘要一条消息，而日志里 1、4、8 的原记录**原封不动**。

这个设计的深意：**可回放性（1、4、8 都还在日志里）与可重建性（投影出来只有摘要）同时成立**——这正是"日志唯一真源"的红利：观点（view）可以换，事实（facts）不必动。

## 8.6 一致性：四道闸门，全部在入账之前

日志作为唯一真源，最怕的不是"写得太慢"，而是"写进了坏数据"——坏数据一旦入账，回放、恢复、fork 全部分叉。dsh 在 `append` 路径上设了四道闸门，**全部在 `log.push` 之前**（8.3 已见其中三道，这里系统化）。

**闸门一：`snapshotJsonValue`——无损 JSON 契约（`json.ts`）。** `JsonValue`（`packages/core/session/src/json.ts:13`）是"可无失真写入 JSON"的类型域。`walkJsonValue`（`packages/core/session/src/json.ts:70-163`）迭代式单遍执行"读 + 校验 + 复制"：拒绝稀疏数组、循环引用、原型污染类异形对象（`hasIntrinsicConstructor` 等原型检查，`packages/core/session/src/json.ts:16-49`）、`-0`、非有限数、Map/Set/Date/类实例；getter 抛错会传播。为何必须"复制"而非"校验后存引用"？调用方的对象之后可能被改——日志存的是**快照**。`snapshotJsonValue`（`packages/core/session/src/json.ts:177-179`）返回 `undefined` 表示不合格。

**闸门二：封套校验 `assertSessionEventEnvelope`（`packages/core/session/src/index.ts:213-250`）。** 种子/恢复路径（构造器，8.7.1）逐条校验：封套键白名单、`seq` 从 0 连续（`packages/core/session/src/index.ts:525-527`）、拒绝遗留 `request/header-delta`（`packages/core/session/src/index.ts:215-217`）——外部来的事件与本地 append 的形状上不可区分。

**闸门三：surface 预校验 `validateNext`（`packages/core/session/src/surface.ts:421-429`）。** "先计划后提交"：候选事件过 `planSurfaceEvent` 的全部校验（8.5.4 列出），计划暂存于 `_pendingPlan`（`packages/core/session/src/surface.ts:404`），`log.push` 后由 `_processDelta`（`packages/core/session/src/surface.ts:444-459`）提交——**校验失败时日志零变更**。

**闸门四：seq 连续与重入。** `seq = log.length`（`packages/core/session/src/index.ts:629`）使"空洞"在类型上不可能出现：第 n 条事件 seq 必为 n-1；配合第五步的重入检查（`packages/core/session/src/index.ts:623-626`），杜绝"两个 append 并发发布导致乱序"——**日志追加是严格串行的**。另有 `packages/core/session/src/invariant.ts` 提供**关系型**不变量伴侣（跨事件的 `openTurn/openStep` 配对、`pendingCalls` 与 `tool/call`/`tool/result` 配对、`nextTurn/nextStep` 单调），作为可选诊断插件装载（`packages/core/session/src/invariant.ts:1-6`），把校验粒度从"单条事件"提到"事件之间"。

最后，**持久化是插件关注点**。`packages/core/session/src/index.ts:1-7` 的模块注释开门见山：

> Persistence is a plugin concern (subscribe to `session/event`, drain on `session/flush`).

`SessionStore` 的类注释同样直白："Persistence is intentionally not implemented here"（`packages/core/session/src/index.ts:789-792`）。会话核心只提供四条钩子：`session/created`（mode emit，`packages/core/session/src/index.ts:54`）、`session/disposed`（mode emit，:64）、`session/event`（mode emit，:76——监听者拿到**已入账**的冻结事件）、`session/flush`（mode parallel，:85——等待式持久化检查点；唯一 flush 入口 `packages/core/session/src/index.ts:1022-1039`，`Promise.allSettled` 等所有参与者、首个失败抛出）。存到哪里、如何检查点，是 `session-persistence` 插件的选择（8.11 延伸阅读）。**核心与持久化解耦**，是"日志唯一真源"成立的组织保证：核心只负责"日志必须是什么"，不关心"日志存在哪里"。

## 8.7 回放、恢复与 fork：同一事件流的三种走法

### 8.7.1 构造器：所有路径的公共咽喉

`Session` 没有公开构造器，只有两个静态入口：`Session.create(id, seed?, header?)`（`packages/core/session/src/index.ts:482-484`）与 `Session.fromRestore(id, seed, header)`（`packages/core/session/src/index.ts:495-497`）。两者都进入私有构造器（`packages/core/session/src/index.ts:499-548`），而私有构造器对种子事件做的工作，几乎就是 8.3 的七步走读的"完整重演"：

1. 逐条：`mode === 'restore' ? source : snapshotJsonValue(source)`（packages/core/session/src/index.ts:519）——恢复路径的事件来自持久化后端，已是快照；新建路径的种子重过一遍无损校验；
2. `assertSessionEventEnvelope`（:523）+ `seq !== index` 即抛"seed must be contiguous from 0"（:525-527）；
3. `assertSupportedRequestHeader`（:524）；
4. `surfaceManager.validateNext`（:532）——**种子逐条递增进入同一个表面折叠**，注释（:528-530）说得很清楚："a seed is accepted incrementally through the same transition as a live append and a full-log fold"——同一函数走种子、活体追加与整日志折叠，不存在"恢复有另一套规则"；
5. `log.push`（:536；restore 用 `freezeRestoredObject`，`packages/core/session/src/index.ts:197-210`——迭代式深冻结，不消耗 JS 调用栈，避免深层次结构栈溢出）；
6. 收尾：`firstLiveSeq = log.length`（:539）——**实况从种子之后开始**；若种子末条不是 `session/end-seed`，补一条（:545-547；"Re-marking is skipped because a cold session is resumed on first touch, so repeatedly opening one must not grow its log per open"，:542-544）。

注意：构造器里的追加**不会广播 `session/event`**（`packages/core/session/src/index.ts:454` 注释："constructor seeds do not emit"）——种子事件不是"本生命周期发生的"，不通知观察者；这也是 `session/end-seed` 要在构造器里补（而非外部 append）的原因：它就是"本生命周期未发生任何种子事件"的标记。

### 8.7.2 `session/end-seed`：一眼认出"哪段是别人的"

`session/end-seed` 的载荷是空的（`Record<string, never>`，`packages/core/session/src/types.ts:332`），意义全在位置与 `time`（`packages/core/session/src/types.ts:310-331` 注释）。它解决的是恢复时的一个微妙问题：

> 一个拥有独立开/闭括号的生命周期（`compaction/start` … `compaction/end`）的读者会读它，因为种子与实况部分**字节相同**：在这个事件之前出现的不配对起始标记，属于一个**已结束**的生命周期，不管它是怎么结束的。（`packages/core/session/src/types.ts:325-328` 大意）

也就是说：日志的"种子部分 + 实况部分"字节上无法区分（都是合法事件串），加上 `session/end-seed` 后，任何人**定位最后一条**即可切分。设计上有两条纪律：**只有 `Session` 构造器能写**（`packages/core/session/src/types.ts:321-323`——其他插件 append 一条会把一切实况静默归类为种子历史；不变量伴侣对此"deliberately constrains nothing"（`:322-324`），纯靠代码评审守住）；已有种子以 `session/end-seed` 结尾就不再补（`:317-319`）。

### 8.7.3 三种走法

- **回放（replay）**：一串事件 → `foldSurface`（`packages/core/session/src/surface.ts:387-395`）→ `deriveEventMessage` → 历史；`foldRequestHeader` → 请求头。全部是纯函数，不依赖任何 live 对象。
- **恢复（resume）**：`SessionStore.prepare` 里 `seedSource === 'persistence'` 走 `fromRestore`（`packages/core/session/src/index.ts:863-889`，persistence 提供 `persistence.prepare(id)` 取种子，`packages/core/session/src/index.ts:872-874`），然后照常 `enter` → `announce`（`packages/core/session/src/index.ts:913-947`；`session/created` 监听器同步抛出可击退整个挂载——veto 可回滚，见 `packages/core/session/src/index.ts:968-996`）。
- **fork（分支）**：`SessionStore.fork(sourceId, childId, boundary)`（`packages/core/session/src/index.ts:1081-1095`）→ `_forkSeed`（`packages/core/session/src/index.ts:1097-1138`）取源会话 `[0, boundary)` 的种子造新会话。失败码（`SessionForkError`，`packages/core/session/src/index.ts:779-784`）语义明确：`SESSION_NOT_FOUND`（源 id 未知）、`SESSION_NOT_LIVE`（不是 store 的活实例）、`SESSION_ALREADY_EXISTS`（子 id 已被占）、`INVALID_BOUNDARY`（边界不是连续存在的 seq）、**`OPEN_TURN`（前缀末端是未关闭的 turn——种子必须是完整的逻辑段，`packages/core/session/src/index.ts:1128-1135`）**。

三条走法收拢成一句：**live、恢复、fork 全部从"一串事件"出发，经过同一套校验，得到同一个投影函数的结果**。8.4.3 反例三在此闭环——投影唯一，故 fork 出的新会话与父会话在"同一段历史"上的视图**必然一致**，无论 fork 何时发生。

## 8.8 最小示例：离线构造一条事件流并投影

下面的示例不调用任何模型、无需 API key，只需仓库已构建（或 `node --import tsx` 运行）。它演示本章回路：**构造 → 追加 → 派生**。

```ts
import { Session, SessionId } from '@deepseek-ai/dsh-session'

// 1. 构造空会话（第二个参数 seed 省略：无种子）
const session = Session.create(SessionId('demo-1'))

// 2. 追加：边界事件不需要 surface 参数
session.append('turn/start', { turn: 1 })
// 3. 追加：模型可见事件必须带 SurfaceIntent
session.append('user/message', {
  id: 'msg-1', role: 'user',
  content: [{ type: 'text', text: '跑一下测试' }],
  source: { kind: 'user' },
}, { surfaceOp: 'append' })
// 4. 追加：流式 chunk（日志专用）
for (const delta of ['我来', '看看']) {
  session.append('assistant/chunk', {
    turn: 1, step: 1,
    chunk: { type: 'text', delta }, // 形状取自 StreamChunk 的文本增量
  })
}
// 5. 追加：组装后的消息，并声明溯源
session.append('assistant/message', {
  turn: 1, step: 1,
  message: {
    id: 'msg-2', role: 'assistant',
    content: [{ type: 'text', text: '我来看看' }],
    source: { kind: 'model', provider: 'example', model: 'demo' }, // 字段以 MessageSource 为准
  },
}, { surfaceOp: 'append', sourceEventSeqs: [2, 3] })
session.append('turn/end', { turn: 1, reason: 'completed' })

// 6. 派生：只有两条消息，chunk 与边界不出现
console.log(session.deriveMessages().map(m => m.id)) // ['msg-1', 'msg-2']
console.log(session.seq)                             // 6 —— 连续契约
```

对照语义推演预期输出（**未在本写作环境运行**：执笔约定不执行 node；在仓库内直跑应得到与注释一致的输出）：

1. `deriveMessages()` 得到 `['msg-1', 'msg-2']`：chunk（序号 2、3）与 `turn/start`/`turn/end` 不投影（`packages/core/session/src/surface.ts:109-113`）；`assistant/message` 的 `content` 非空所以投影（`packages/core/session/src/surface.ts:99-105`）；
2. `session.seq === 6`：追加了 6 条事件，seq 从 0 起连续到 5；
3. 追加时不保留 `chunk` 对象引用，之后 `deriveMessages()` 结果不变——**投影只看日志**；
4. 若给第 3 步去掉 `surfaceOp`，TS 编译直接报错（条件参数类型，`packages/core/session/src/index.ts:604-608`）；若运行时强行给 `turn/start` 塞 `surfaceOp`，`surfaceOpOf` 抛"not surface-eligible"（`packages/core/session/src/surface.ts:187-190`）。

## 8.9 本章小结

1. **日志是唯一真源，消息历史是投影**：`SessionEventMap` 的 13 种事件按"边界 / 模型可见 / 日志专用"三分类；`SessionEvent` 是判别联合，`seq` 连续即 `log.length`（`packages/core/session/src/types.ts:236-333`、`packages/core/session/src/index.ts:629`）。
2. **扩展规则**：模型可见输入必须先是会话事件——新输入 = 新事件类型 + 新投影规则；`ignorable` 缺省"必须认识"，版本号因此保持单整数（`packages/core/session/src/types.ts:33-55`、`412-422`）。
3. **写路径七步**：组装元数据 → 无损校验拷贝 → 兼容性拒绝 → 元数据校验 → 重入检查与冻结 → 先入账后通知 → 收尾；失败全部发生在 `log.push` 之前（`packages/core/session/src/index.ts:604-655`）。
4. **读路径是增量折叠**：`deriveMessages` 逐表面节点投影一次、`replaceGeneration` 驱动缓存作废、返回新数组共享冻结消息；空 content 的 assistant/message 不进 transcript（`packages/core/session/src/index.ts:726-747`、`packages/core/session/src/surface.ts:83-114`）。
5. **surface 让"删除"成为追加**：compaction 用一条 replace 事件遮蔽旧节点，旧日志原封不动；`sourceEventSeqs` 完整性由 `assertProvenance` 强制（`packages/core/session/src/surface.ts:211-243`、`362-379`）。
6. **恢复/fork/replay 与 live 同源同规**：种子逐条过同一套校验、`session/end-seed` 切分种子与实况、`OPEN_TURN` 拒绝断在轮次中间的 fork——投影唯一 ⇒ 各路径视图一致（`packages/core/session/src/index.ts:499-548`、`1097-1138`）。
7. **持久化是插件关注点**：核心只发 `session/created`/`session/disposed`/`session/event`/`session/flush` 四条钩子，不实现任何存储（`packages/core/session/src/index.ts:1-7`、`76-85`、`789-792`）。

## 8.10 分层练习

**理解层**
1. 不看源码，把 13 种事件写进三分类表，再为每一类各举一条"为什么必须存在"的理由。
2. 用两句话解释：什么叫"over-refuse"？为什么 `ignorable` 缺省即"必认"？

**应用层**
3. 给定事件流：`turn/start → user/message(0) → assistant/message(1, 空 content) → assistant/message(2) → tool/call(3) → tool/result(4)`，写出 `deriveMessages()` 的结果（逐条说明 `deriveEventMessage` 的分支）。
4. 若第 3 题里 `tool/result` 的 `sourceEventSeqs` 写成 `[5]`，`append` 会怎样？写成 `[3, 3]` 呢？（对照 `packages/core/session/src/surface.ts:211-243`）

**综合层**
5. 论证"只记 `assistant/message`、不记 `assistant/chunk`"会破坏哪些能力；再论证"只记 chunk、不记 message"又会怎样。（提示：从重放保真与投影成本两侧想。）
6. 你的项目要求"模型必须看到文件变更通知"，但通知内容可能含不可序列化对象（如 Error 实例）。梳理从消息源到日志的路径，指出 dsh 在哪里以什么错误拒绝它，并给出两类修复方案（生产者侧/协议侧）。

**挑战层**
7. 设计自定义会话事件 `weather/current`（天气快照）：该做 surface 事件还是日志专用？如何写 `deriveEventMessage`？UI 展示历史天气曲线应订阅什么？画出"事件 → 日志 → 投影 → UI"链路，并说明你把 `sourceEventSeqs` 设计成有/无的理由。
8. 一个 10 万条事件的长会话，compaction 每 50 步跑一次。估算 `deriveMessages` 的摊销成本（对照 `packages/core/session/src/index.ts:730-746` 的缓存失效策略），并设计一个"UI 有瞬时结果、又不打断 model 请求"的读取策略。
